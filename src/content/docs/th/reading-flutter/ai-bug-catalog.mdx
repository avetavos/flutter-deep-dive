## State & lifecycle

### 1. ลืม `ProviderScope`

`ref.watch`/`ref.read` ของ Riverpod ต้องการ `ProviderContainer` ให้อ่าน `ProviderScope` คือ widget ที่สร้างมันขึ้นมาและทำให้เข้าถึงได้ ข้าม widget นี้ไป แล้วทุก `ConsumerWidget` จะ throw ทันทีที่มันพยายามอ่าน provider

```dart
// lib/ai-bug-catalog/01-provider-scope.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final nameProvider = Provider<String>((ref) => 'Milo');

class NameOnly extends ConsumerWidget {
  const NameOnly({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final name = ref.watch(nameProvider);
    return Text(name);
  }
}

// AI-generated: forgot to wrap the app in ProviderScope.
Widget buggyApp() => const MaterialApp(home: Scaffold(body: NameOnly()));
```

**อาการ — `flutter test` ที่ fail จริง จับสดสำหรับโมดูลนี้:**

```dart
// test/ai-bug-catalog/01-provider-scope_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/01-provider-scope.dart';

void main() {
  testWidgets('no ProviderScope -> throws', (tester) async {
    await tester.pumpWidget(buggyApp());
    final exception = tester.takeException();
    expect(exception, isA<StateError>());
    expect(exception.toString(), contains('No ProviderScope found'));
  });
}
```

```text
✓ no ProviderScope -> throws
00:00 +1: All tests passed!
```

exception ที่แท้จริงคือ `StateError` ที่มีข้อความ **"Bad state: No ProviderScope found"**

**ทางแก้:**

```dart
Widget fixedApp() => const ProviderScope(
      child: MaterialApp(home: Scaffold(body: NameOnly())),
    );
```

**จับได้โดย:** ผลลัพธ์จริงของ `riverpod_lint` rule `missing_provider_scope` (พิสูจน์สด ๆ ใน **[Verification Tools](/flutter/th/reading-flutter/verification-tools/)**) หรือการ crash บนหน้าจอแรกสุดที่อ่าน provider

### 2. `setState` หลัง `await` โดยไม่เช็ค `mounted`

`State` สามารถถูก dispose ได้ (user นำทางออกไป, list item ถูกเลื่อนออกจาก list ที่สร้างแบบ lazy) ในขณะที่ `Future` ที่มันเริ่มไว้ยังค้างอยู่ พอมัน resolve แล้วเรียก `setState` ก็ไม่มี widget เหลือให้ rebuild

```dart
// lib/ai-bug-catalog/02-mounted-guard.dart
import 'package:flutter/material.dart';

class BuggyLoader extends StatefulWidget {
  const BuggyLoader({super.key, required this.future});
  final Future<String> future;
  @override
  State<BuggyLoader> createState() => _BuggyLoaderState();
}

class _BuggyLoaderState extends State<BuggyLoader> {
  String _text = 'loading';
  @override
  void initState() {
    super.initState();
    // AI-generated: no `mounted` guard after the await.
    widget.future.then((value) => setState(() => _text = value));
  }

  @override
  Widget build(BuildContext context) => Text(_text);
}
```

**อาการ — `flutter test` ที่ fail จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
setState() called after dispose(): _BuggyLoaderState#5aa37(lifecycle state: defunct, not mounted)
This error happens if you call setState() on a State object for a widget that no longer appears in
the widget tree (e.g., whose parent widget no longer includes the widget in its build). This error
can occur when code calls setState() from a timer, from an animation callback, or after an
asynchronous operation (such as an awaited network request or other Future) completes after the
widget has been removed from the tree.
The preferred solution is to cancel the timer or stop listening to the animation in the dispose()
callback. Another solution is to check the "mounted" property of this object before calling
setState() to ensure the object is still in the tree.
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:**

```dart
// lib/ai-bug-catalog/02-mounted-guard-fixed.dart
import 'package:flutter/material.dart';

class FixedLoader extends StatefulWidget {
  const FixedLoader({super.key, required this.future});
  final Future<String> future;
  @override
  State<FixedLoader> createState() => _FixedLoaderState();
}

class _FixedLoaderState extends State<FixedLoader> {
  String _text = 'loading';
  @override
  void initState() {
    super.initState();
    widget.future.then((value) {
      if (!mounted) return;
      setState(() => _text = value);
    });
  }

  @override
  Widget build(BuildContext context) => Text(_text);
}
```

```dart

    await tester.pumpWidget(const MaterialApp(home: SizedBox()));
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติเลย — `flutter analyze` เห็นการเรียก method ที่ถูกต้องสมบูรณ์ไม่ว่ากรณีไหน มีแค่ widget ที่ถูก dispose กลาง `await` เท่านั้นที่เผยมันออกมา ไม่ว่าในชุด test **[Testing](/flutter/th/tooling-and-production/testing/)** หรือใน production

### 3. `setState` ถูกเรียกจาก `build()` ของ sibling (cross-sibling)

widget ที่เรียก callback แบบ synchronous จากภายใน `build()` ของตัวมันเอง และ callback นั้นเรียก `setState` บน widget *อื่น* ที่ยังอยู่กลาง build จะชน guard "อย่าแก้ไขสิ่งที่กำลัง build อยู่" ของ Flutter

```dart
// lib/ai-bug-catalog/03-setstate-during-build.dart
import 'package:flutter/material.dart';

class Reporter extends StatelessWidget {
  const Reporter({super.key, required this.onBuild});
  final VoidCallback onBuild;
  @override
  Widget build(BuildContext context) {
    // AI-generated: reports "I built" straight from build(), synchronously.
    onBuild();
    return const SizedBox.shrink();
  }
}

class BuggyParent extends StatefulWidget {
  const BuggyParent({super.key});
  @override
  State<BuggyParent> createState() => _BuggyParentState();
}

class _BuggyParentState extends State<BuggyParent> {
  int _count = 0;
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        Text('$_count'),
        if (_count == 0) Reporter(onBuild: () => setState(() => _count++)),
      ],
    );
  }
}
```

**อาการ — ผลลัพธ์จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
setState() or markNeedsBuild() called during build.
This BuggyParent widget cannot be marked as needing to build because the framework is already in the
process of building widgets. A widget can be marked as needing to be built during the build phase
only if one of its ancestors is currently building. This exception is allowed because the framework
builds parent widgets before children, which means a dirty descendant will always be built.
The widget on which setState() or markNeedsBuild() was called was:
  BuggyParent
The widget which was currently being built when the offending call was made was:
  Reporter
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** เลื่อน `setState` ให้พ้น build phase ปัจจุบันด้วย `addPostFrameCallback`

```dart
// lib/ai-bug-catalog/03-setstate-during-build-fixed.dart
import 'package:flutter/material.dart';

class FixedParent extends StatefulWidget {
  const FixedParent({super.key});
  @override
  State<FixedParent> createState() => _FixedParentState();
}

class _FixedParentState extends State<FixedParent> {
  int _count = 0;
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        Text('$_count'),
        if (_count == 0)
          _Reporter(
            onBuild: () => WidgetsBinding.instance
                .addPostFrameCallback((_) => setState(() => _count++)),
          ),
      ],
    );
  }
}

class _Reporter extends StatelessWidget {
  const _Reporter({required this.onBuild});
  final VoidCallback onBuild;
  @override
  Widget build(BuildContext context) {
    onBuild();
    return const SizedBox.shrink();
  }
}
```

```text
✓ deferring to addPostFrameCallback does not throw
00:00 +1: All tests passed!
```

**จับได้โดย:** framework เอง ทันทีและเสียงดัง — แต่เฉพาะตอนที่ widget ตัวนี้ build จริงในขณะที่เป้าหมายของมันยังกลาง build เท่านั้น test ที่ pump แค่ครั้งเดียวและไม่เคย trigger เส้นทางการ report จะพลาดมันไปเลย

### 4. field `late` ถูกอ่านก่อนที่จะถูกกำหนดค่า

`late` เลื่อนการ initialize ของ field ออกไปแต่ไม่ได้เปลี่ยน *เวลา* ที่ผู้เรียกคาดหวังจะอ่านมัน — AI assistant ที่ก็อป field `late` มาโดยไม่ตรวจสอบทุก branch ที่อาจอ่านมันก่อนที่ method ซึ่งกำหนดค่าจะรัน ship crash จริงตอนอ่านครั้งแรก ไม่ใช่ตอนเขียนครั้งแรก

```dart
// lib/ai-bug-catalog/04-late-field.dart
class Session {
  // AI-generated: assumed `configure()` always runs before `token` is read,
  // but nothing enforces that ordering.
  late String token;

  void configure(String value) => token = value;
}
```

**PROOF:**

```dart
// test/ai-bug-catalog/04-late-field_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/04-late-field.dart';

void main() {
  test('reading a late field before it is set throws LateInitializationError', () {
    final session = Session();
    expect(() => session.token, throwsA(isA<Error>()));
  });

  test('configuring first makes the read safe', () {
    final session = Session()..configure('abc123');
    expect(session.token, 'abc123');
  });
}
```

```text
✓ reading a late field before it is set throws LateInitializationError
✓ configuring first makes the read safe
00:00 +2: All tests passed!
```

**ทางแก้:** ทำให้ field เป็น nullable แล้วเช็ค `null`, ให้ค่า default จริง หรือให้ constructor บังคับรับค่าแทนขั้นตอน `configure()` แยกต่างหาก

**จับได้โดย:** ไม่มีอะไร static เลย — `late` เป็นสัญญาให้ compiler ไม่ใช่การรับประกันที่ analyzer เช็ค มีแค่การอ่านจริงบน instance ที่ยังไม่ configure เท่านั้นที่ throw และมัน throw ตอน READ ไม่ใช่ตอนที่ assignment ถูกข้ามไป ซึ่งทำให้ stack trace ชี้ไปที่บรรทัดที่ดูไร้พิษภัยห่างไกลจากบั๊กจริง

### 5. `StateProvider`/`StateNotifierProvider` ถูก import ราวกับยังเป็น Riverpod 3 API ระดับบนสุด

ข้อมูลฝึกสอน AI ครอบคลุม Riverpod 2 ที่ `StateProvider` และ `StateNotifierProvider` อยู่แถวหน้าใน export หลัก `flutter_riverpod.dart` Riverpod 3 ย้ายทั้งคู่ (บวก `ChangeNotifierProvider`) ไปไว้หลัง import `legacy.dart` ที่ชัดเจน — พวกมันยังมีอยู่จริง แค่ไม่ได้อยู่ตรงที่ AI assistant ที่ฝึกจาก docs เก่าคาดหวัง

```dart
// lib/ai-bug-catalog/05-state-provider.dart — @expect-error StateProvider moved behind package:flutter_riverpod/legacy.dart in Riverpod 3; the main export no longer has it
import 'package:flutter_riverpod/flutter_riverpod.dart';

// AI-generated (trained on Riverpod 2 docs).
final counterProvider = StateProvider<int>((ref) => 0);
```

**อาการ — `flutter analyze` diagnostic จริง จับสดกับ `flutter_riverpod` 3.4.3:**

```text
error • The function 'StateProvider' isn't defined. Try importing the library that defines
'StateProvider', correcting the name to the name of an existing function, or defining a function
named 'StateProvider' • lib/ai-bug-catalog/05-state-provider.dart:5:25 • undefined_function
```

**ทางแก้ analyze สะอาด:**

```dart
// lib/ai-bug-catalog/05-state-provider-fixed.dart
import 'package:flutter_riverpod/legacy.dart';

// Still works in Riverpod 3, but only via the explicit legacy import --
// prefer NotifierProvider/@riverpod codegen for new code instead.
final counterProvider = StateProvider<int>((ref) => 0);
```

**จับได้โดย:** `flutter analyze` — แต่เฉพาะเมื่อผู้อ่านรู้แล้วว่าต้องมองหา เพราะข้อความ error เอ่ยชื่อ function จริงที่ไม่มีอยู่จริง ๆ ภายใต้ import นั้น โดยไม่มีคำใบ้เลยว่ามันย้ายไป ไม่ใช่หายไป

## Widget tree & keys

### 6. ไม่มี `key` บน list ของ children แบบ stateful ที่เรียงใหม่ได้

ถ้าไม่มี `key` Flutter จับคู่ widget ที่ rebuild กับ `State` ของมันด้วย **type และตำแหน่ง** ไม่ใช่ identity เรียงลำดับ list ใหม่ แล้ว `State` object แต่ละตัวจะติดอยู่กับตำแหน่งบนจอแทนที่จะตามข้อมูลของมันไป

```dart
// lib/ai-bug-catalog/06-missing-key.dart
import 'package:flutter/material.dart';

class ColorBox extends StatefulWidget {
  const ColorBox({super.key, required this.label});
  final String label;
  @override
  State<ColorBox> createState() => _ColorBoxState();
}

class _ColorBoxState extends State<ColorBox> {
  bool _tapped = false;
  @override
  Widget build(BuildContext context) {
    return GestureDetector(
      onTap: () => setState(() => _tapped = true),
      child: Text(_tapped ? '${widget.label} (tapped)' : widget.label),
    );
  }
}

// AI-generated: no key, so Flutter matches by TYPE + POSITION, not identity.
class BuggyList extends StatelessWidget {
  const BuggyList({super.key, required this.labels});
  final List<String> labels;
  @override
  Widget build(BuildContext context) {
    return Column(children: [for (final l in labels) ColorBox(label: l)]);
  }
}
```

**PROOF:**

```dart
// test/ai-bug-catalog/06-missing-key_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/06-missing-key.dart';

void main() {

    await tester.pumpWidget(const MaterialApp(home: BuggyList(labels: ['Milo', 'Rex'])));
    await tester.tap(find.text('Milo'));
    await tester.pump();

    // SAME State object for position 0 -- the "tapped" flag follows the
    // POSITION, not Milo.
    await tester.pumpWidget(const MaterialApp(home: BuggyList(labels: ['Rex', 'Milo'])));
    expect(find.text('Rex (tapped)'), findsOneWidget);
    expect(find.text('Milo (tapped)'), findsNothing);
  });
}
```

```text
✓ no key: tapped state sticks to POSITION, not the item
00:00 +1: All tests passed!
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** `ValueKey` ต่อรายการผูก `State` เข้ากับข้อมูล ไม่ใช่ตำแหน่ง

```dart
// lib/ai-bug-catalog/06-missing-key-fixed.dart
import 'package:flutter/material.dart';

class ColorBox extends StatefulWidget {
  const ColorBox({super.key, required this.label});
  final String label;
  @override
  State<ColorBox> createState() => _ColorBoxState();
}

class _ColorBoxState extends State<ColorBox> {
  bool _tapped = false;
  @override
  Widget build(BuildContext context) {
    return GestureDetector(
      onTap: () => setState(() => _tapped = true),
      child: Text(_tapped ? '${widget.label} (tapped)' : widget.label),
    );
  }
}

class FixedList extends StatelessWidget {
  const FixedList({super.key, required this.labels});
  final List<String> labels;
  @override
  Widget build(BuildContext context) {
    return Column(children: [for (final l in labels) ColorBox(key: ValueKey(l), label: l)]);
  }
}
```

```text
✓ ValueKey: tapped state stays attached to the correct item
00:00 +1: All tests passed!
```

**จับได้โดย:** ไม่มีอะไรอัตโนมัติเลย — มัน render ถูกต้องในรอบแรกทุกครั้ง มีแค่การเรียงใหม่-แล้วตรวจสอบด้วยมือระหว่างรีวิว (หรือ regression test ที่ seed ขั้นตอนการเรียงใหม่ไว้) เท่านั้นที่จับมันได้

### 7. `GlobalKey` ตัวเดียวกันถูกใช้ซ้ำข้าม sibling widget

AI assistant ที่หยิบ `GlobalKey` ระดับโมดูลตัวเดียวมาหมายถึง "รายการที่กำลังถูกเลือกอยู่" — โดยสมมติว่าจะมี widget เดียวเท่านั้นที่ถือมันในแต่ละครั้ง — จะพังทันทีที่ widget สองตัวที่ถือ key นั้นมีอยู่ใน frame เดียวกัน

```dart
// lib/ai-bug-catalog/07-global-key-reused.dart
import 'package:flutter/material.dart';

// AI-generated: ONE GlobalKey reused for "the featured item".
final featuredKey = GlobalKey();

class BuggyTwoPanes extends StatelessWidget {
  const BuggyTwoPanes({super.key});
  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        Container(key: featuredKey, width: 100, height: 100, color: Colors.blue),
        Container(key: featuredKey, width: 100, height: 100, color: Colors.red),
      ],
    );
  }
}
```

**อาการ — `flutter test` ที่ fail จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
Duplicate keys found.
If multiple keyed widgets exist as children of another widget, they must have unique keys.
Row(direction: horizontal, mainAxisAlignment: start, crossAxisAlignment: center) has multiple
children with key [GlobalKey#52079].
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** `UniqueKey()` (หรือไม่ใส่ key เลยถ้า identity ข้าม rebuild ไม่สำคัญ) ต่อ widget

```dart
// lib/ai-bug-catalog/07-global-key-reused-fixed.dart
import 'package:flutter/material.dart';

class FixedTwoPanes extends StatelessWidget {
  const FixedTwoPanes({super.key});
  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        Container(key: UniqueKey(), width: 100, height: 100, color: Colors.blue),
        Container(key: UniqueKey(), width: 100, height: 100, color: Colors.red),
      ],
    );
  }
}
```

```text
✓ a distinct key per widget does not throw
00:00 +1: All tests passed!
```

**จับได้โดย:** framework เอง ทันทีและเสียงดัง ในนาทีที่ widget สองตัวถือ key เดียวกันมีอยู่ในการ build เดียว — แต่เฉพาะการจัดวางแบบนั้น (sibling หรือสอง branch ที่ build ใน frame เดียวกัน) `GlobalKey` ที่ใช้ซ้ำข้าม build ที่ไม่เคยซ้อนทับกันในเวลาสามารถซ่อนได้นานกว่านั้นมาก


**อาการ — `flutter test` ที่ fail จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** `Builder` สร้าง context ใหม่ที่เป็น descendant ของ `Scaffold` จริง ๆ

### 9. `ListView` ได้รับความสูงไม่มีขอบเขตจาก `Column` ธรรมดา

`Column` ให้ children ของมัน **ความสูงไม่มีขอบเขต** ตามแกนหลัก `ListView` ต้องการความสูงมีขอบเขตเพื่อรู้ว่า viewport ของมันใหญ่แค่ไหน วางอันหนึ่งตรง ๆ ในอีกอันโดยไม่มีอะไรคั่นกลาง แล้ว layout จะล้มเหลว

```dart
// lib/ai-bug-catalog/09-unbounded-listview.dart
import 'package:flutter/material.dart';

// AI-generated: a ListView dropped straight into a Column.
class BuggyPage extends StatelessWidget {
  const BuggyPage({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const Text('Header'),
        ListView(children: const [Text('one'), Text('two'), Text('three')]),
      ],
    );
  }
}
```

**อาการ — ผลลัพธ์จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
Vertical viewport was given unbounded height.
Viewports expand in the scrolling direction to fill their container. In this case, a vertical
viewport was given an unlimited amount of vertical space in which to expand. This situation
typically happens when a scrollable widget is nested inside another scrollable widget.
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** `Expanded` ให้ `ListView` ความสูงมีขอบเขต — เท่าที่เหลือใน `Column` **กติกาที่แท้จริง แม่นยำ ๆ:** ancestor ที่ให้ความสูงไม่มีขอบเขต (แกนหลักของ `Column`) ต้องการกล่องที่มีขอบเขตอยู่ตรงไหนสักที่ระหว่างมันกับ scrollable/flexible child ทิศทางย้อนกลับ — `Column` *ข้างใน* `ListView` — ไม่ต้องการอะไรเพิ่มเลย: scrollable ให้ children ของมัน cross-axis ที่มีขอบเขตและ main-axis ที่ไม่มีขอบเขตอยู่แล้ว ซึ่งตรงกับที่ `Column` ขนาดตามธรรมชาติต้องการพอดี

```dart
// lib/ai-bug-catalog/09-unbounded-listview-fixed.dart
import 'package:flutter/material.dart';

class FixedPage extends StatelessWidget {
  const FixedPage({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const Text('Header'),
        Expanded(
          child: ListView(children: const [Text('one'), Text('two'), Text('three')]),
        ),
      ],
    );
  }
}

// The reverse needs NO extra widget:
class ColumnInsideListView extends StatelessWidget {
  const ColumnInsideListView({super.key});
  @override
  Widget build(BuildContext context) {
    return ListView(children: [Column(children: const [Text('a'), Text('b'), Text('c')])]);
  }
}
```

```text
✓ Expanded around the ListView fixes it
✓ a Column INSIDE a ListView needs no extra widget at all
00:00 +2: All tests passed!
```

**จับได้โดย:** framework เอง ทันทีและเสียงดัง ความละเอียดอ่อนที่ต้องจับในรีวิวคือทิศทาง — pattern การแก้แบบเดียวกันมักถูก apply เกินความจำเป็นกับกรณีย้อนกลับ ซึ่งไม่เคยต้องการมันเลย

## Async & isolate

### 12. `Future` ถูกสร้างตรง ๆ ใน `build()`

การเรียก async function ข้างใน `build()` สร้าง `Future` ใหม่ — และการเรียก network/database ใหม่ — ทุกครั้งที่ rebuild ไม่ใช่ครั้งเดียวต่อ "การโหลด" เชิง logic

```dart
// lib/ai-bug-catalog/12-future-in-build.dart
import 'package:flutter/material.dart';

int fetchCount = 0;
Future<String> fetchName() async {
  fetchCount++;
  return 'Milo';
}

// AI-generated: calls the async function directly inside build().
class BuggyName extends StatelessWidget {
  const BuggyName({super.key, required this.tick});
  final int tick; // forces a distinct widget per pump, to prove the rebuild count
  @override
  Widget build(BuildContext context) {
    return FutureBuilder<String>(
      future: fetchName(), // new Future every single build()
      builder: (context, snapshot) => Text(snapshot.data ?? 'loading'),
    );
  }
}
```

**PROOF:**

```dart

    await tester.pumpWidget(MaterialApp(home: BuggyName(tick: 1)));
    await tester.pumpWidget(MaterialApp(home: BuggyName(tick: 2)));

  });

```

```text

```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** สร้าง `Future` ครั้งเดียว ใน `State` ไม่ใช่ใน `build()`


### 13. closure ของ `compute()` capture `BuildContext`

`compute()` ของ Dart สมัยใหม่รันบน `Isolate.run` ซึ่งสามารถส่ง closure ที่ประพฤติตัวดีข้าม isolate boundary ได้จริง — closure ที่ capture `int` ธรรมดา แม้แต่ instance method ที่ bind ไว้ ข้ามได้สบายบน Dart 3.13.4 ที่คอร์สนี้ pin ไว้ สิ่งที่ยังข้ามไม่ได้คือทุกอย่างที่เข้าถึงได้จาก widget tree: `BuildContext` เข้าถึง `Zone` ได้ทางอ้อม และ `Zone` ไม่เคย sendable เลย

```dart
// lib/ai-bug-catalog/13-compute-context.dart
import 'package:flutter/material.dart';
import 'package:flutter/foundation.dart';

// AI-generated: captures `context` to log something mid-computation.
class BuggySummary extends StatelessWidget {
  const BuggySummary({super.key});
  @override
  Widget build(BuildContext context) {
    int withContext(List<int> xs) {
      debugPrint('${context.widget}'); // captures `context` -> unsendable
      return xs.reduce((a, b) => a + b);
    }
    compute(withContext, const [1, 2, 3]).then((r) => debugPrint('result: $r'));
    return const SizedBox();
  }
}
```

**อาการ — ผลลัพธ์จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
Invalid argument(s): Illegal argument in isolate message: object is unsendable -
Library:'dart:async' Class: _CustomZone@5048458 (see restrictions listed at `SendPort.send()`
documentation for more information)
 <- _parentZone in Instance of 'AutomatedTestWidgetsFlutterBinding' (from package:flutter_test/src/binding.dart)
 <- _binding in Instance of '_BindingPipelineManifold' (from package:flutter/src/rendering/binding.dart)
 <- ... (a long ownership chain from the captured BuildContext down to a real Zone)
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** top-level function ที่รับแค่ข้อมูลล้วน ๆ ชัดเจน — ไม่มี `BuildContext`, ไม่มี `Zone`, ไม่มีอะไรผูกกับ binding ของ isolate นี้เอง

```dart
// lib/ai-bug-catalog/13-compute-context-fixed.dart
import 'package:flutter/foundation.dart';

int _sum(List<int> xs) => xs.reduce((a, b) => a + b);

Future<int> fixedSummarize(List<int> values) => compute(_sum, values);
```

```text
✓ a top-level function with only plain data crosses the isolate boundary fine
00:00 +1: All tests passed!
```

**จับได้โดย:** ไม่มีอะไรจนกว่าการเรียก `compute()` จะรันจริง — โค้ดนี้ compile ผ่านสะอาดสมบูรณ์ และแม้แต่ closure ที่ capture ตัวแปร local ธรรมดาก็จะรันได้สบาย ซึ่งนั่นแหละคือสิ่งที่ทำให้มันแก้ไขผิดพลาด (มากไปหรือน้อยไป) ได้ง่าย กติกาไม่ใช่ "อย่า capture อะไรเลย" แต่คือ "อย่า capture อะไรก็ตามที่เข้าถึงได้จาก Element tree หรือ binding"

### 14. `StreamController` แบบ single-subscription ถูก listen สองครั้ง

`StreamController()` default เป็น single-subscription การเรียก `.listen()` ครั้งที่สองที่เป็นอิสระบน stream เดียวกัน — โค้ดชิ้นหนึ่งสำหรับ UI อีกชิ้นสำหรับ analytics เป็นต้น — จะ throw มันไม่ได้สร้าง subscriber ตัวที่สองแบบเงียบ ๆ เหมือนที่ broadcast stream ทำ

```dart
// lib/ai-bug-catalog/14-stream-double-listen.dart — @expect-error a single-subscription Stream throws on the second .listen() -- see the real "Bad state" below
import 'dart:async';

// AI-generated: default StreamController, assumed multiple listeners are fine.
StreamController<int> buggyController() => StreamController<int>();
```

**อาการ — ผลลัพธ์จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
Bad state: Stream has already been listened to.
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** `.broadcast()` อนุญาตให้มี listener อิสระหลายตัวอย่างชัดเจน

```dart
// lib/ai-bug-catalog/14-stream-double-listen-fixed.dart
import 'dart:async';

StreamController<int> fixedController() => StreamController<int>.broadcast();
```

```dart
// test/ai-bug-catalog/14-stream-double-listen-fixed_test.dart

```

### 15. `go_router`: route ที่มีพารามิเตอร์ถูกประกาศก่อน route แบบ static

### 16. `context.go()` ถูกใช้ในจุดที่ต้องการ `context.push()`

`go()` **แทนที่** ตำแหน่งปัจจุบันใน route stack `push()` **เพิ่ม** เข้าไป การใช้ `go()` สำหรับสิ่งที่ควรเป็น navigation แบบดำดิ่งลึก (จาก list ไปหน้า detail เป็นต้น) ทำให้ user ไม่มี "ย้อนกลับ" ให้กด

```dart
// lib/ai-bug-catalog/16-go-vs-push.dart
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';

GoRouter buildRouter() => GoRouter(
      initialLocation: '/a',
      routes: [
        GoRoute(path: '/a', builder: (c, s) => const _Page('A')),
        GoRoute(path: '/b', builder: (c, s) => const _Page('B')),
      ],
    );

class _Page extends StatelessWidget {
  const _Page(this.label);
  final String label;
  @override
  Widget build(BuildContext context) => Scaffold(body: Text('Page $label'));
}
```

**PROOF — เปรียบเทียบความลึกของ stack โดยตรง:**

**จับได้โดย:** ไม่มีอะไรอัตโนมัติเลย — การเรียกทั้งสองแบบ navigate ไปยังปลายทางถูกต้อง มีแค่การเช็ค `Navigator.canPop()`/กดย้อนกลับหลังจากนั้นเท่านั้นที่เผย history entry ที่หายไป

### 17. `redirect` อ่าน state ภายนอกโดยไม่มี `refreshListenable`

callback `redirect` ของ `go_router` default จะทำงานซ้ำเฉพาะตอนเกิด **navigation event** เท่านั้น ถ้ามันอ่าน state ภายนอก (auth flag) ที่เปลี่ยนไปโดย*ไม่มี* navigation event เกิดขึ้นพร้อมกัน router จะไม่มีวันรู้เลย

```dart
// lib/ai-bug-catalog/17-redirect-refresh.dart
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';

class AuthState extends ChangeNotifier {
  bool loggedIn = false;
  void logIn() {
    loggedIn = true;
    notifyListeners();
  }
}

// AI-generated: redirect reads auth.loggedIn, but nothing re-evaluates
// redirects when that value changes outside of navigation.
GoRouter buggyRouter(AuthState auth) => GoRouter(
      initialLocation: '/login',
      redirect: (context, state) {
        if (!auth.loggedIn && state.matchedLocation != '/login') return '/login';
        if (auth.loggedIn && state.matchedLocation == '/login') return '/home';
        return null;
      },
      routes: [
        GoRoute(path: '/login', builder: (c, s) => const Text('login')),
        GoRoute(path: '/home', builder: (c, s) => const Text('home')),
      ],
    );
```

**PROOF:**

```dart
        if (auth.loggedIn && state.matchedLocation == '/login') return '/home';
        return null;
      },
      routes: [
        GoRoute(path: '/login', builder: (c, s) => const Text('login')),
        GoRoute(path: '/home', builder: (c, s) => const Text('home')),
      ],
    );
```

### 19. `dart:io`/`Platform.isIOS` ถูกใช้แบบไม่มีเงื่อนไขในโค้ดที่ต้อง build สำหรับ web ด้วย

การ implement `dart:io` สำหรับ web compile ผ่านสะอาด — web compiler ships facade จริงที่ type-complete ให้มัน ยืนยันได้จากการอ่าน `io_patch.dart` ของ SDK เองสำหรับเป้าหมาย `js_runtime` ที่ body ของทุก member คือ `throw UnsupportedError(...)` การ build ไม่มีวันล้มเหลว ทุก member แค่ throw ทันทีที่มันรันจริง

```dart

import 'package:flutter/material.dart';

// AI-generated: reaches for dart:io directly to check the platform.
class BuggyPlatformBadge extends StatelessWidget {
  const BuggyPlatformBadge({super.key});
  @override
  Widget build(BuildContext context) {
    final label = Platform.isIOS ? 'iOS' : 'Other'; // throws on web, at runtime
    return Text(label);
  }
}
```

**อาการ — จับสดสำหรับโมดูลนี้:**

```text
$ flutter build web --release
Compiling lib/main.dart for the Web...
✓ Built build/web
```

build สำเร็จโดยไม่มี warning เกี่ยวกับ `dart:io` **เลยสักคำ** ความล้มเหลวมีอยู่จริงแต่เข้าถึงได้แค่ตอน runtime ในเบราว์เซอร์จริง ในนาทีที่ `Platform.isIOS` รัน — ยืนยันตรง ๆ จาก web-target patch ของ SDK ที่ shipped จริง ที่ `_Platform._operatingSystem()` (สิ่งที่ `Platform.isIOS` อ่านในที่สุด) ถูก implement เป็น `throw UnsupportedError("Platform._operatingSystem")`

**ทางแก้ พิสูจน์แล้วว่า build สะอาด:** `kIsWeb` เป็นค่าคงที่ที่ปลอดภัยตอน compile-time จาก `package:flutter/foundation.dart` — เช็คมันก่อนเลย ก่อนอะไรก็ตามที่แตะ `Platform`

```dart
// lib/ai-bug-catalog/19-dartio-web-fixed.dart

  if (kIsWeb) return 'Web';
  return Platform.isIOS ? 'iOS' : 'Other';
}
```

**จับได้โดย:** ไม่มีอะไรเลย — ไม่ใช่ analyzer, ไม่ใช่ build, แม้แต่ `flutter build web --wasm` (ก็พิสูจน์แล้วว่า compile snippet นี้ผ่านสะอาด จับสดสำหรับโมดูลนี้เช่นกัน) มีแค่การรันจริงบนเป้าหมาย web จริงเท่านั้นที่เผยมันออกมา

### 20. `MethodChannel.invokeMethod` ที่ไม่มี native handler ลงทะเบียนไว้

การเรียก platform channel method สมมติว่ามี native implementation ลงทะเบียนไว้บน platform ที่กำลังรันอยู่ — จริงก็ต่อเมื่อมี plugin จริง (หรือ mock ของ test เอง) ต่อสายไว้จริง ๆ เท่านั้น

```dart
// lib/ai-bug-catalog/20-missing-plugin.dart
import 'package:flutter/services.dart';

// AI-generated: assumes SOME native implementation exists.
const _channel = MethodChannel('com.example/battery');

Future<int> buggyBatteryLevel() {
  return _channel.invokeMethod<int>('getBatteryLevel').then((v) => v ?? -1);
}
```

**อาการ — ผลลัพธ์จริง ไม่มีการแก้ไข จับสดสำหรับโมดูลนี้:**

```text
MissingPluginException(No implementation found for method getBatteryLevel on channel com.example/battery)
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** ใน test ให้ลงทะเบียน mock handler ใน production ให้มี implementation จริงเฉพาะ platform (plugin จริง หรือโค้ดเฉพาะ platform ที่ลงทะเบียนในโปรเจกต์ native)

```dart
import 'package:flutter/services.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/20-missing-plugin.dart';
```

### 21. `FlutterError.onError` ถูกตั้งโดยไม่มี `runZonedGuarded` (หรือกลับกัน)

`FlutterError.onError` ยิงเฉพาะ error ที่ FRAMEWORK ดักจับได้เท่านั้น — ระหว่าง build, layout, และ paint error ที่ throw จาก `Future` ธรรมดา, `Timer`, หรือโค้ด async ล้วน ๆ นอกจุด try/catch ของ framework เองไม่มีวันไปถึงมันเลย

```dart
// lib/ai-bug-catalog/21-zone-errors.dart
import 'dart:async';

// AI-generated: sets FlutterError.onError, assumes that's "global error
// handling" done -- it is not, for anything outside the framework.

  return Future<void>(() => throw StateError('boom from a bare Future'));
}
```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:** `runZonedGuarded` ห่อทั้ง zone ดักจับ error ที่ `FlutterError.onError` ไม่เคยเห็น

```dart
// lib/ai-bug-catalog/21-zone-errors-fixed.dart
import 'dart:async';

  runZonedGuarded(body, onError);
}
```

```dart

```

```text

00:00 +1: All tests passed!
```

**จับได้โดย:** ไม่มีอะไร static เลย และนี่คือกับดักที่แหลมคมที่สุดในกลุ่มนี้: `FlutterError.onError` เพียงลำพัง ดู*เหมือน*ว่าครอบคลุม error ทั้งหมด (มันดักจับ crash ของ framework จริงที่มองเห็นได้ระหว่าง development) ซึ่งนั่นแหละคือเหตุผลที่ช่องว่างสำหรับโค้ด async ล้วน ๆ ไม่ถูกสังเกตจนกว่า error ที่ไม่ถูกดักจับจริง ๆ จะไปถึง production โดยไม่มีรายงานเลย `PlatformDispatcher.onError` (3.3+) เป็นทางเลือก/ส่วนเสริมสมัยใหม่ที่ควรรู้ไว้เช่นกัน ดักจับ error ที่ระดับ platform-dispatcher

```text
dispose() was called on the mixin, that Ticker was still active. The Ticker must be disposed before

```

**ทางแก้ พิสูจน์แล้วว่าผ่าน:**

```dart
// lib/ai-bug-catalog/22-animation-controller-fixed.dart
import 'package:flutter/material.dart';

class FixedSpinner extends StatefulWidget {
  const FixedSpinner({super.key});
  @override
  State<FixedSpinner> createState() => _FixedSpinnerState();
}

class _FixedSpinnerState extends State<FixedSpinner> with SingleTickerProviderStateMixin {
  late final AnimationController _controller =
      AnimationController(vsync: this, duration: const Duration(seconds: 1))..repeat();

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) =>
      RotationTransition(turns: _controller, child: const Icon(Icons.sync));
}
```

### 23. `Opacity(opacity: 1.0)` ยังคงจอง compositing layer จริง

doc comment ของ widget `Opacity` เองบอกว่า "ค่า 1.0 และ 0.0 ถูกวาดด้วย fast path" — ซึ่งจริง แต่อธิบายแค่ต้นทุนตอน PAINT เท่านั้น อ่าน source จริงของ `RenderOpacity`: `isRepaintBoundary => alwaysNeedsCompositing` และ `alwaysNeedsCompositing => child != null && _alpha > 0` นั่นเป็น TRUE สำหรับ `opacity: 1.0` (alpha 255) พอ ๆ กับ `opacity: 0.5` — มีแค่ `opacity: 0.0` (alpha 0) เท่านั้นที่ข้าม compositing ไปทั้งหมด `Opacity(opacity: 1.0)` ไม่ฟรี มันคือ repaint boundary จริงพร้อม `OpacityLayer` จริง

**PROOF — อ่านตรง ๆ จาก `RenderObject` ที่มีชีวิต ไม่ใช่สมมติจาก doc comment:**

```dart
// test/ai-bug-catalog/23-opacity-layer_test.dart
import 'package:flutter/material.dart';
import 'package:flutter/rendering.dart';
import 'package:flutter_test/flutter_test.dart';

void main() {
  testWidgets('Opacity(opacity: 1.0) is STILL a repaint boundary', (tester) async {
    await tester.pumpWidget(
      const MaterialApp(home: Opacity(opacity: 1.0, child: ColoredBox(color: Colors.blue))),
    );
    final render = tester.renderObject<RenderOpacity>(find.byType(Opacity));
    expect(render.isRepaintBoundary, isTrue);
    expect(render.alwaysNeedsCompositing, isTrue);
  });

  testWidgets('Opacity(opacity: 0.0) is the ONE value that skips compositing entirely', (tester) async {
    await tester.pumpWidget(
      const MaterialApp(home: Opacity(opacity: 0.0, child: ColoredBox(color: Colors.blue))),
    );
    final render = tester.renderObject<RenderOpacity>(find.byType(Opacity));
    expect(render.isRepaintBoundary, isFalse);
    expect(render.alwaysNeedsCompositing, isFalse);
  });
}
```

```text
✓ Opacity(opacity: 1.0) is STILL a repaint boundary
✓ Opacity(opacity: 0.0) is the ONE value that skips compositing entirely
00:00 +2: All tests passed!
```

**ทางแก้:** ถ้า opacity เป็นค่าคงที่ตอน compile-time `1.0` (widget ที่ถูกแสดง/ซ่อนแบบมีเงื่อนไขด้วยการสลับมันออกไปทั้งหมด เป็นต้น) ข้าม `Opacity` ไปเลย — คืนค่า child ตรง ๆ หรือใช้ `Visibility`/ternary ที่เอา widget ออกแทนที่จะทำให้มืดลง เก็บ `Opacity`/`AnimatedOpacity`/`FadeTransition` ไว้สำหรับ opacity ที่เปลี่ยนแปลงจริง ๆ

**จับได้โดย:** ไม่มีอะไรอัตโนมัติเลย และนี่คือการแก้ไขที่ละเอียดอ่อนจริง ๆ: `Opacity(opacity: 1.0)` ไม่ crash และไม่แม้แต่ render ผิด — มันแค่จ่ายค่า layer ที่ปกติไม่จำเป็นตลอดเวลา และ doc comment ของ framework เองก็อ่านได้ (ผิด ๆ) ว่าบอกเป็นอย่างอื่น

### 27. `switch` ที่ไม่ครบทุกกรณีบน `sealed class`

AI assistant ที่ฝึกจากสไตล์เก่า "abstract class + เช็คด้วย `is`" สำหรับ state union บางครั้งยังลืม case แม้กำลังใช้ `sealed class` + `switch` expression สมัยใหม่ — แต่ในกรณีนี้ analyzer สามารถ PROVE ได้จริงว่า switch ไม่ครบ ตอน compile time เพราะ class เป็น sealed

```dart
// lib/ai-bug-catalog/27-non-exhaustive-switch.dart — @expect-error non_exhaustive_switch_expression -- see the real diagnostic below
sealed class LoadState {}
class Loading extends LoadState {}
class Loaded extends LoadState {
  Loaded(this.data);
  final String data;
}
class LoadError extends LoadState {
  LoadError(this.message);
  final String message;
}

// AI-generated: forgot the LoadError case entirely.
String buggyDescribe(LoadState state) {
  return switch (state) {
    Loading() => 'loading',
    Loaded(:final data) => 'loaded: $data',
  };
}
```

**อาการ — `flutter analyze` diagnostic จริง จับสด:**

```text
error • The type 'LoadState' isn't exhaustively matched by the switch cases since it doesn't match
the pattern 'LoadError()'. Try adding a wildcard pattern or cases that match 'LoadError()' •
non_exhaustive_switch_expression
```

**ทางแก้ analyze สะอาด:**

```dart
// lib/ai-bug-catalog/27-non-exhaustive-switch-fixed.dart
```

**จับได้โดย:** `flutter analyze` เป็น ERROR จริงหนักแน่น (ไม่ใช่แค่ lint ที่ความมั่นใจของ AI สามารถโบกมือผ่านได้) นี่คือ exhaustiveness checking ของ Dart 3 เอง และเป็นข้อโต้แย้งที่หนักแน่นที่สุดในทั้ง catalog นี้สำหรับการใช้ state union แบบ `sealed class` แทนสไตล์ `abstract class` เก่า: subtype ตัวที่สี่ที่เพิ่มเข้ามาภายหลังทำให้ switch ที่มีอยู่เดิมทุกตัว compile ไม่ผ่านอีกครั้งจนกว่าจะจัดการมัน
