## โจทย์

prompt ที่ให้ไปคือ: *"หน้าจอ photo gallery: grid รูปที่ scroll ได้และ fade เข้ามา มีขั้นตอน decode เพื่อไม่ให้ UI ค้าง และ upload client แบบแบ่ง chunk พร้อม progress panel ด้านล่าง"* สิ่งที่ตามมาคือดราฟต์แรกที่ดูโอเคเมื่อกวาดตาผ่าน ๆ -- มันใช้ `CustomScrollView`/`SliverGrid` แทน `GridView` ธรรมดา (เลย *ดู* เหมือนเข้าใจเรื่อง sliver) ใช้ `compute()` สำหรับงาน "หนัก" (เลย *ดู* เหมือนเข้าใจเรื่อง isolate) และทำ animation ให้แต่ละ tile ตอนเข้ามา มี **bug จริง 10 ตัว** หลายตัวเป็นแบบที่ไม่มีทางโผล่มาให้เห็นตอน scroll ดูรูปแค่ไม่กี่รูปผ่าน ๆ ให้อ่านตามที่ **[review checklist](/flutter/th/reading-flutter/review-checklist/)** แนะนำ: ความถูกต้องก่อน (โค้ด isolate/async ทำงานจริงไหม) แล้วค่อย lifecycle (อะไร leak) แล้วค่อย layout แล้วค่อยขอบของแต่ละแพลตฟอร์ม ทุก claim ด้านล่างรันจริงใน probe ของคอร์สนี้ (Flutter 3.47.5) -- `flutter analyze` จริง, `flutter test` จริง, `flutter build web` จริง และการจับเวลาจริงบน Mac เครื่องนี้

```dart
import 'dart:typed_data';

/// A cheap-looking "compute the average brightness for a placeholder color"
/// loop -- the kind of pure-Dart pixel work an AI reaches for instead of a
/// real decode library, and runs directly on whichever isolate calls it.
int averageBrightness(Uint8List rgba) {
  var total = 0;
  for (var i = 0; i < rgba.length; i += 4) {
    total += (rgba[i] + rgba[i + 1] + rgba[i + 2]) ~/ 3;
  }
  return rgba.isEmpty ? 0 : total ~/ (rgba.length ~/ 4);
}
```

## เดินรีวิวทีละบั๊ก

### 1. closure ของ `compute()` capture `ReceivePort`

`decodePhotoReportingProgress` closure ครอบ `progress` ซึ่งเป็น `ReceivePort` เพื่อ "รายงาน progress กลับมา" `compute()` ส่ง argument ของมันไปยัง background isolate เป็น isolate message -- และตัว closure เองก็เป็นส่วนหนึ่งของ message นั้นด้วย `ReceivePort` เป็น handle ที่ผูกกับ isolate โดยตรง (native) ที่ก็อปข้ามไปไม่ได้:

```dart
// test/gallery_app/decode_worker_test.dart
import 'dart:isolate';

import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/gallery_app/decode_worker.dart';

void main() {
  test('compute() closure capturing a ReceivePort throws the real isolate-message error', () async {
    final port = ReceivePort();
    addTearDown(port.close);

    await expectLater(
      decodePhotoReportingProgress(100, port),
      throwsA(
        isA<ArgumentError>().having(
          (e) => e.toString(),
          'message',
          contains('Illegal argument in isolate message'),
        ),
      ),
    );
  });
}
```

```text
✓ compute() closure capturing a ReceivePort throws the real isolate-message error

00:00 +1: All tests passed!
```

กลไกเดียวกันเป๊ะพิสูจน์ไว้แล้วด้วยการจับ `ReceivePort` แบบเดียวกันใน **[Isolates & compute()](/flutter/th/async-and-performance/isolates-and-compute/)**; closure ของ `compute()`/`Isolate.run` ต้อง capture แค่ข้อมูลธรรมดาที่ส่งข้าม isolate ได้เท่านั้น (หรือไม่ capture อะไรเลย -- เลือกใช้ฟังก์ชันระดับบนสุดหรือ `static` ดีกว่า)

<SpotTheBug code={`Future<int> decodePhotoReportingProgress(int bytesLength, ReceivePort progress) {
  return compute((int len) {
    final capturedPort = progress; // captures a non-sendable object
    return _fakeDecodedByteCount(len);
  }, bytesLength);
}`}>
`progress` อยู่นอก closure ที่ส่งเข้า `compute()` Dart จึง serialize มันเป็นส่วนหนึ่งของ closure นั้นเพื่อส่งให้ background isolate -- และ `ReceivePort` (เหมือน `Socket`, `Timer` หรือ class instance ส่วนใหญ่ที่ถือ native resource) ไม่มีรูปแบบที่ส่งข้าม isolate ได้เลย ทางแก้คือฟังก์ชันที่ไม่ capture อะไรเลยนอกจาก parameter ของตัวเอง -- ฟังก์ชันระดับบนสุด หรือ closure ที่สร้างจาก primitive/collection ล้วน ๆ
</SpotTheBug>

### 2. งานใกล้เคียง decode ที่รันแบบ synchronous บน isolate ที่เรียกมัน

`averageBrightness` ใน `thumbnail_analysis.dart` -- ตั้งใจไว้เพื่อสร้างสีตัวแทนคร่าว ๆ ก่อนรูปจริงจะพร้อม -- เป็น loop Dart แบบ synchronous ทีละพิกเซล ไม่มี `compute()`/`Isolate.run` ห่ออยู่เลย เรียกมันจาก `build()` หรือ frame callback บนรูปความละเอียดเต็มแล้ว isolate นั้นจะค้างตลอด loop:

```dart
// test/gallery_app/thumbnail_analysis_timing_test.dart
import 'dart:typed_data';

import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/gallery_app/thumbnail_analysis.dart';

void main() {
  test('averageBrightness on a full-resolution photo blows the 16.6ms frame budget when run on the calling isolate', () {
    // A believable 12MP RGBA buffer (4000x3000x4 bytes).
    final rgba = Uint8List(4000 * 3000 * 4);
    final stopwatch = Stopwatch()..start();
    averageBrightness(rgba);
    stopwatch.stop();
    print('averageBrightness(12MP) took ${stopwatch.elapsedMilliseconds}ms on this Mac');
    expect(stopwatch.elapsedMilliseconds, greaterThan(16),
        reason: 'a per-pixel Dart loop over a full-resolution photo run '
            'directly on the calling isolate blows the ~16.6ms frame '
            'budget on its own -- called from build() or a frame '
            'callback, this is a dropped frame, not just slow code');
  });
}
```

```text
averageBrightness(12MP) took 25ms on this Mac

00:00 +1: All tests passed!
```

วัดได้บน Mac เครื่องนี้ **25ms** สำหรับ buffer 12 เมกะพิกเซลเดียว -- เกินงบเฟรม **~16.6ms** ที่พิสูจน์ไว้ใน **[Render pipeline](/flutter/th/layout-and-rendering/render-pipeline/)** ไปแล้ว ก่อนที่จะมีงาน decode จริงหรือเครื่องที่ช้ากว่านี้เข้ามาเกี่ยวข้องด้วยซ้ำ ทางแก้คือ `compute()` ตัวเดียวกับที่ไฟล์นี้ import อยู่แล้วที่อื่น แค่ใช้ให้ถูก: ห่อการเรียกฟังก์ชันบริสุทธิ์ ไม่ capture อะไรเลย

### 3. `AnimationController` ไม่เคยถูก dispose

`_PhotoTileState` สร้าง `AnimationController` แล้วสั่งให้เริ่มทำงาน แต่ไม่มี `dispose()` override เลยสักนิด:

```dart
// test/gallery_app/photo_tile_leak_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/gallery_app/photo_tile.dart';

void main() {
  testWidgets('a PhotoTile with no dispose() throws the real Ticker leak error on removal', (tester) async {
    late AnimationController leaked;
    await tester.pumpWidget(MaterialApp(
      home: PhotoTile(color: Colors.red, onControllerReady: (c) => leaked = c),
    ));
    await tester.pump(const Duration(milliseconds: 50));

    await tester.pumpWidget(const MaterialApp(home: SizedBox()));

    final error = tester.takeException();
    expect(error, isA<FlutterError>());
    print(error.toString());

    leaked.dispose(); // avoid also failing on "ticker still active at end of test"
  });

  testWidgets('the inline builder child rebuilds every animation tick', (tester) async {
    tileBodyBuildCount = 0;
    late AnimationController controller;
    await tester.pumpWidget(MaterialApp(
      home: PhotoTile(color: Colors.red, onControllerReady: (c) => controller = c),
    ));
    final firstCount = tileBodyBuildCount;
    await tester.pump(const Duration(milliseconds: 50));
    await tester.pump(const Duration(milliseconds: 50));
    print('tileBodyBuildCount first=$firstCount after 2 ticks=$tileBodyBuildCount');
    expect(tileBodyBuildCount, greaterThan(firstCount),
        reason: '_TileBody is constructed fresh inside builder on every '
            'tick -- AnimatedBuilder\'s own child param, unused here, '
            'exists specifically to avoid this');
    controller.dispose();
  });
}
```

```text
_PhotoTileState#75ce5(ticker active) was disposed with an active Ticker.
_PhotoTileState created a Ticker via its SingleTickerProviderStateMixin, but at the time dispose() was called on the mixin, that Ticker was still active. The Ticker must be disposed before calling super.dispose().
Tickers used by AnimationControllers should be disposed by calling dispose() on the AnimationController itself. Otherwise, the ticker will leak.
```

ข้อความ error จริงเดียวกันเป๊ะที่พิสูจน์ไว้แล้วใน **[Animations](/flutter/th/async-and-performance/animations/)** -- scroll grid รูปแล้วทุก tile ที่เคย build ตัวนี้ขึ้นมาจะ leak `Ticker` ตอนที่มัน scroll ออกจากช่วงที่ build ไว้แล้วถูก dispose

### 4. `Opacity` + `AnimatedBuilder` ที่สร้าง child แบบ inline

callback `builder` ของ `AnimatedBuilder` สร้าง `_TileBody` ตรง ๆ แทนที่จะส่งผ่าน parameter `child` ของ `AnimatedBuilder` เอง -- มันเลย rebuild ทุก tick ของ animation ไม่ใช่แค่ repaint เท่านั้น test ที่สองใน fence เดียวกันด้านบนพิสูจน์เรื่องนี้:

```text
tileBodyBuildCount first=1 after 2 ticks=3

00:00 +2: All tests passed!
```

ตาม **[Render pipeline](/flutter/th/layout-and-rendering/render-pipeline/)** `Opacity` กับ `AnimatedOpacity`/`FadeTransition` มีต้นทุน compositing layer *เท่ากัน* เมื่อค่าไม่เป็นศูนย์ -- สิ่งที่ widget ที่สร้างมาเฉพาะทางอย่าง `FadeTransition` เพิ่มให้ไม่ใช่ layer ที่ถูกกว่า แต่คือการไม่ rebuild subtree ที่ไม่จำเป็นต้องเปลี่ยนทุก tick พิสูจน์แล้วด้านบน

### 5. `cacheExtent` -- deprecated แล้ว

`GalleryGrid` ตั้ง `cacheExtent: 500` ตรง ๆ บน `CustomScrollView` เช็กกับ SDK นี้ (Flutter 3.47.5):

```text
info • 'cacheExtent' is deprecated and shouldn't be used. Use scrollCacheExtent instead. This feature was deprecated after v3.41.0-0.0.pre. Try replacing the use of the deprecated member with the replacement • deprecated_member_use
```

ยืนยันตรงจาก source ของ `package:flutter` เอง (`widgets/scroll_view.dart`): `cacheExtent` มี `@Deprecated('Use scrollCacheExtent instead. This feature was deprecated after v3.41.0-0.0.pre.')` ติดอยู่ ตัวแทนที่ `ScrollCacheExtent` เป็น type จริง -- แต่ **ไม่ได้** ถูก re-export โดย `package:flutter/material.dart` (หรือ `widgets.dart`) เลย มีแค่ `package:flutter/rendering.dart` เท่านั้น ทางแก้เลยต้อง import ตัวนั้นเพิ่มด้วย (ดูโค้ดที่แก้แล้ว)

### 6. ลืม `RepaintBoundary` รอบ tile ที่ animate

ไม่มีอะไรแยก repaint ทุก tick ของ `PhotoTile` ออกจาก sibling ที่นิ่งซึ่งใช้ canvas ร่วมกัน:

```dart
// lib/gallery_app/gallery_repaint_demo.dart
import 'package:flutter/material.dart';

import 'photo_tile.dart';

int badgePaintCount = 0;

class _CountingPainter extends CustomPainter {
  _CountingPainter(this.onPaint);
  final VoidCallback onPaint;
  @override
  void paint(Canvas canvas, Size size) {
    onPaint();
    canvas.drawRect(Offset.zero & size, Paint()..color = Colors.grey);
  }

  @override
  bool shouldRepaint(_CountingPainter oldDelegate) => false;
}

/// A "photo count" badge next to the grid -- never changes on its own.
class CountBadge extends StatelessWidget {
  const CountBadge({super.key});
  @override
  Widget build(BuildContext context) {
    return CustomPaint(size: const Size(24, 24), painter: _CountingPainter(() => badgePaintCount++));
  }
}

/// BUG: no RepaintBoundary between the animating PhotoTile and CountBadge --
/// they share one canvas, so PhotoTile's every-tick repaint forces
/// CountBadge to repaint too even though it never changed.
class GalleryHeaderNoBoundary extends StatelessWidget {
  const GalleryHeaderNoBoundary({super.key, required this.onControllerReady});
  final ValueChanged<AnimationController> onControllerReady;
  @override
  Widget build(BuildContext context) {
    return Row(children: [
      PhotoTile(color: Colors.red, onControllerReady: onControllerReady),
      const CountBadge(),
    ]);
  }
}

/// FIX: PhotoTile gets its own layer -- its repaints stop leaking into CountBadge.
class GalleryHeaderWithBoundary extends StatelessWidget {
  const GalleryHeaderWithBoundary({super.key, required this.onControllerReady});
  final ValueChanged<AnimationController> onControllerReady;
  @override
  Widget build(BuildContext context) {
    return Row(children: [
      RepaintBoundary(child: PhotoTile(color: Colors.red, onControllerReady: onControllerReady)),
      const CountBadge(),
    ]);
  }
}
```


กลไกเดียวกันเป๊ะ (และคู่ที่ใส่ boundary ที่หยุดการ leak) พิสูจน์ไว้ครบในบท **[Render pipeline](/flutter/th/layout-and-rendering/render-pipeline/)** ใน gallery จริง "sibling ที่นิ่ง" คือ tile อื่นทุกตัวที่ใช้ canvas ของ grid ร่วมกัน -- tile ที่ animate อยู่ตัวเดียวไม่มี boundary หมายความว่าทุก tile รอบ ๆ มัน repaint ไปด้วย

กลไกทั้งหมดและทางแก้จริงทั้ง 3 แบบพิสูจน์ไว้ในบท **[Constraints & Layout](/flutter/th/layout-and-rendering/constraints-and-layout/)** ซึ่งมีข้อแก้ไขความเข้าใจผิดที่รีวิวนี้ต้องพูดซ้ำด้วย:

<Callout title="แก้ไขความเข้าใจผิดที่พบบ่อย: Column ข้างใน ListView ไม่พัง">
ถ้าทางแก้ของ AI สำหรับเรื่องนี้ไปในทิศทาง *ตรงกันข้าม* -- ย้าย `Column` เข้าไปข้างใน children ของ `ListView` -- นั่นจะไม่แก้อะไรเลย เพราะรูปแบบนั้นไม่พังตั้งแต่แรกอยู่แล้ว พิสูจน์ตรง ๆ: `ListView(children: [Column(children: [...])])` render ได้ปกติ; item ของ `ListView` ได้รับความสูงแบบ unbounded เพื่อให้มันรายงานขนาดของตัวเองได้ และ `Column` ที่ได้รับความสูงแบบ unbounded จะ fallback ไปตั้งขนาดตามผลรวมของ children แทน การพังจริง ๆ ต้องการให้ *ตัวที่ scroll ได้* เป็นตัวที่ได้รับความสูงแบบ unbounded จากช่องที่ไม่ flexible -- `ListView`/`GridView`/`CustomScrollView` เปล่า ๆ เป็น child ตรง ๆ ของ `Column` โดยไม่ใช่ `Expanded` แบบเดียวกับที่ `UploadPanel` ทำด้านบนเป๊ะ
</Callout>

### 8. `Image` ที่ไม่มี `cacheWidth`/`cacheHeight`

แผนของ AI สำหรับรูปแต่ละรูปใน grid คือ `Image.network(url)` ธรรมดา ไม่มี hint เรื่องขนาด decode เลย จากเอกสารของ widget `Image` เอง (`package:flutter`):

```text
The image is stored in memory in uncompressed form (so that it can be rendered). Large images
will use a lot of memory: a 4K image (3840x2160) will use over 30MB of RAM (assuming 32 bits per
pixel).

The Image.asset, Image.network, Image.file, and Image.memory constructors allow a custom decode
size to be specified through cacheWidth and cacheHeight parameters. The engine will then decode
and store the image at the specified size, instead of the image's natural size.

This can significantly reduce the memory usage. For example, a 4K image that will be rendered at
only 384x216 pixels (one-tenth the horizontal and vertical dimensions) would only use 330KB if
those dimensions are specified using the cacheWidth and cacheHeight parameters, a 100-fold
reduction in memory usage.
```

claim ลดหน่วยความจำ 100 เท่า ยกมาตรงจาก doc comment ของ widget เอง (`packages/flutter/lib/src/widgets/image.dart`) -- ทุก tile ใน grid ที่ decode และแคชรูปที่ความละเอียดกล้องเต็ม ๆ เพื่อไปแสดงเป็น thumbnail 100px คือกรณีที่ parameter นี้มีไว้เพื่อแก้เป๊ะ ๆ doc comment เดียวกันยังบอกด้วยว่า `cacheWidth`/`cacheHeight` ถูก **มองข้าม** สำหรับ `Image.network` โดยเฉพาะบนแพลตฟอร์ม web เพราะ web engine ส่งต่อการ decode ให้ browser จัดการ

### 9. ใช้ `dart:io` แบบไม่มี guard -- compile และ build ผ่านสำหรับ web แต่ throw ตอน runtime

`UploadClient` import `dart:io` แล้วสร้าง `File` โดยไม่มี platform guard เลย เช็กตรงกับ web patch ของ SDK ที่ติดตั้งจริง (`dart-sdk/lib/_internal/js_runtime/lib/io_patch.dart`):

```text
@patch
class _File {
  @patch
  static _lengthFromPath(_Namespace namespace, Uint8List path) {
    throw UnsupportedError("File._lengthFromPath");
  }
  ...
```

`dart:io` เองมี stub declaration จริงที่ import ได้สำหรับ web target -- ดังนั้นมัน **analyze สะอาดและ `flutter build web` ผ่านจริง** รันจริงกับไฟล์นี้เป๊ะ ๆ:

```text
Compiling lib/main.dart for the Web...
Font asset "MaterialIcons-Regular.otf" was tree-shaken, reducing it from 1645184 to 7736 bytes (99.5% reduction).
Compiling lib/main.dart for the Web...                             18.8s
✓ Built build/web
```

ปัญหาจะโผล่มาก็ต่อเมื่อ `uploadInChunks` รันจริงบน web build เท่านั้น: `File('...').length()` เรียกตรงเข้า `_lengthFromPath` ซึ่ง web patch แทนที่ด้วย `throw UnsupportedError(...)` แบบไม่มีเงื่อนไข build ที่ผ่านไม่ใช่หลักฐานว่า feature ทำงานได้บนทุกแพลตฟอร์มที่ build ไปด้วย

### 10. สร้าง `Future` ข้างใน `build()` -- upload progress รีเซ็ตทุกครั้งที่มี rebuild ที่ไม่เกี่ยวข้อง

`UploadProgressView.build` เรียก `_uploadAndGetProgress(id)` ตรง ๆ ข้างใน `build` สร้าง `Future` ใหม่เอี่ยม (และเริ่ม "upload" ใหม่) ทุกครั้งที่ widget นี้ rebuild ไม่ว่าจะด้วยเหตุผลอะไรก็ตาม:

```dart
// test/gallery_app/upload_progress_view_test.dart

import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/gallery_app/upload_progress_view.dart';

void main() {
  testWidgets('a Future created inside build() re-fires the upload on every rebuild', (tester) async {
    uploadStartCount = 0;
    final rebuildTrigger = ValueNotifier<int>(0);

    await tester.pumpWidget(MaterialApp(
      home: ValueListenableBuilder<int>(
        valueListenable: rebuildTrigger,
        builder: (context, value, child) => UploadProgressView(id: 'photo-1'),
      ),
    ));
    expect(uploadStartCount, 1, reason: 'one initial build');

    rebuildTrigger.value++; // forces an unrelated rebuild of the parent
    await tester.pump();
    await tester.pump(const Duration(milliseconds: 20));

    print('uploadStartCount=$uploadStartCount after one unrelated rebuild');
    expect(uploadStartCount, 2,
        reason: 'build() ran again for a reason that has nothing to do '
            'with this upload, and _uploadAndGetProgress(id) was called '
            'again because it is called directly inside build()');
  });
}
```

## สิ่งที่เปลี่ยนและเหตุผล

| # | Bug | Fix |
|---|---|---|
| 1 | closure ของ `compute()` capture `ReceivePort` | ไม่ capture อะไรนอกจากข้อมูลธรรมดา -- พิสูจน์แล้ว: ไม่งั้นได้ `Illegal argument in isolate message` |
| 2 | loop งานใกล้ decode ทีละพิกเซลรันบน isolate ที่เรียกมัน | `compute()` ตัวเดียวกัน ใช้ให้ถูก -- พิสูจน์แล้ว: 25ms > งบเฟรม 16.6ms ถ้าไม่แก้ |
| 3 | `AnimationController` ไม่เคย dispose | override `dispose()` -- พิสูจน์แล้ว: ไม่งั้นได้ `was disposed with an active Ticker` |
| 4 | `Opacity`/`AnimatedBuilder` มี child แบบ inline | `FadeTransition` -- พิสูจน์แล้ว: child ไม่ rebuild ทุก tick อีกแล้ว |
| 5 | `cacheExtent` (deprecated) | `scrollCacheExtent` (ต้องการ `package:flutter/rendering.dart`) |
| 6 | ไม่มี `RepaintBoundary` รอบ tile ที่ animate | `RepaintBoundary` -- พิสูจน์แล้ว: sibling ที่นิ่งหยุด repaint |
| 7 | `ListView` เปล่า ๆ เป็น child ของ `Column` | `Expanded(child: ListView(...))` -- พิสูจน์แล้ว: ไม่พังเพราะ unbounded height อีกแล้ว |
| 8 | `Image.network` ไม่มี hint ขนาด decode | `cacheWidth`/`cacheHeight` -- ตามเอกสาร ลดหน่วยความจำได้ถึง 100 เท่า |
| 9 | `dart:io` `File` ใช้แบบไม่มี guard | guard ด้วย `kIsWeb` ก่อนแตะ `File` -- แก้ได้บางส่วน; แก้เต็มใน worked review 3 |
| 10 | สร้าง `Future` ข้างใน `build()` | สร้างครั้งเดียวใน `initState`/field แบบ `late final` -- พิสูจน์แล้ว: รอดจาก rebuild ที่ไม่เกี่ยวข้อง |

## สิ่งที่ reviewer เขียนใน PR

> โครงดี แต่ต้องแก้ก่อน ship -- มี 10 เรื่อง:
>
> 1. **closure ของ `compute()` capture `ReceivePort`** อันนี้ throw `Illegal argument in isolate message` ทุกครั้ง มีแค่ข้อมูลธรรมดาเท่านั้นที่ข้ามไป background isolate ได้
> 2. **`averageBrightness` รันแบบ synchronous บน isolate ไหนก็ตามที่เรียกมัน** วัดได้ 25ms สำหรับ buffer 12MP บนเครื่องผม -- นั่นคือเฟรมที่หลุดไปเลยถ้าถูกเรียกจาก `build()` ห่อมันด้วย `compute()` เหมือนที่ decoder ทำอยู่แล้ว (เกือบ) ก็ได้
> 3. **ไม่มี `dispose()` บน `AnimationController` ของ `PhotoTile`** scroll grid แล้วทุก tile ที่เคย build ตัวนี้ขึ้นมาจะ leak `Ticker`
> 4. **`AnimatedBuilder` build `_TileBody` แบบ inline** ส่งผ่าน `child` แทนดีกว่า -- ตอนนี้มันถูกสร้างใหม่ทุกเฟรมของ animation
> 5. **`cacheExtent` deprecated แล้วตั้งแต่ 3.41** -- `scrollCacheExtent` มาแทนที่ และต้อง import คนละตัว (`package:flutter/rendering.dart`)
> 6. **ไม่มี `RepaintBoundary` บน tile** ใน grid จริง หมายความว่า tile ที่ animate ตัวเดียวจะบังคับให้ tile อื่นทุกตัวที่ใช้ canvas ร่วมกัน repaint ไปด้วย
> 7. **`ListView` ใน `Column` ไม่มี `Expanded` ใน `UploadPanel`** พังจริง `Vertical viewport was given unbounded height`
> 8. **`Image.network` ไม่มี `cacheWidth`/`cacheHeight`** ตามเอกสารของ Flutter เอง นี่คือความต่างของหน่วยความจำถึง 100 เท่าสำหรับ grid tile ขนาด thumbnail
> 9. **`File` ของ `dart:io` ใช้โดยไม่มี platform guard** build ผ่านสำหรับ web แต่ throw `UnsupportedError` ทันทีที่รันจริงบนนั้น
> 10. **เรียก `_uploadAndGetProgress` ตรง ๆ ใน `build()`** rebuild ที่ไม่เกี่ยวข้องอะไรก็เรียก upload ซ้ำ
>
> ไม่มีข้อไหนต้องออกแบบใหม่เลย -- ยินดี pair กันแก้

## Mental Model

มีรูปแบบ 3 อย่างที่วนซ้ำตลอดรีวิวนี้ อย่างแรก: **"ดูเหมือนเข้าใจ isolate" ไม่ใช่ "เข้าใจ isolate จริง"** -- `compute()` โผล่มา 2 ครั้งใน PR นี้ ครั้งหนึ่งพังเพราะ capture `ReceivePort` อีกครั้งหายไปเลยจากฟังก์ชันที่ต้องการมันชัด ๆ และทั้งคู่ไม่โผล่ให้เห็นจนกว่าจะทดสอบเจาะจงเรื่องนี้ อย่างที่สอง: **แอปที่ compile และ build ผ่านไม่ใช่แอปที่ใช้งานได้จริง** -- bug 5 กับ 8 analyzer มองเห็นได้ (deprecation, doc comment) แต่ bug 9 compile และ build ผ่านสำเร็จสำหรับแพลตฟอร์มที่มันใช้งานไม่ได้จริง ซึ่งเป็นกับดักที่ร้ายกว่า build ล้มเหลวตรง ๆ เสียอีก อย่างที่สาม: **ทุก leak/กับดักในรีวิวนี้มองไม่เห็นจากการทดสอบด้วยมือสั้น ๆ** -- tile ไม่กี่ตัวบนหน้าจอไม่มีทาง leak ticker มากพอให้สังเกตเห็น rebuild ครั้งเดียวไม่ค่อยเร็วพอให้เห็น progress bar รีเซ็ต และไม่มีใคร scroll ไปถึง tile 999 ด้วยมือ ทั้ง 10 bug ต้องการ test ที่เจาะจงหรือข้อเท็จจริงที่มีเอกสารรองรับถึงจะโผล่ออกมา ซึ่งตรงกับประเด็นของ review checklist เป๊ะ

## Trade-offs

| ตัวเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| `compute()` สำหรับงานที่ใช้ CPU หนัก | ทำให้ isolate ที่เรียกยังตอบสนองอยู่ -- พิสูจน์แล้วด้วยการจับเวลาจริงด้านบน | closure ต้องไม่มีอะไรที่ส่งข้าม isolate ไม่ได้เลย; ผิดกติกาได้ง่ายโดยไม่มี error จนกว่าจะรันจริง |

## Common Misconceptions

- **"ถ้า `flutter build web` ผ่าน แอปก็ใช้งานได้บน web"** พิสูจน์แล้วว่าผิดด้านบน: `UploadClient` compile และ build สะอาดสำหรับ web แล้ว throw `UnsupportedError` ทันทีที่ `uploadInChunks` รันจริงบนนั้น build ที่เขียวพิสูจน์แค่ว่าโค้ด type-check ผ่านและ bundle ได้ -- ไม่ได้บอกอะไรเลยว่ามันทำอะไรตอน runtime บนแพลตฟอร์มนั้น
- **"`Column` ข้างใน `ListView` คือการซ้อนที่อันตราย ไม่ใช่ทางกลับกัน"** แก้ไขแล้วด้านบนด้วย test ตรง ๆ: `ListView(children: [Column(...)])` ไม่พัง การพังจริง ๆ ต้องการให้ *ตัวที่ scroll ได้* เป็นตัวที่ได้รับความสูงแบบ unbounded จากช่องที่ไม่ flexible
- **"`Opacity` ข้างใน `AnimatedBuilder` ถูกกว่า `FadeTransition` เพราะมัน 'ง่ายกว่า'"** ทั้งคู่จองต้นทุน compositing layer เท่ากันเป๊ะเมื่อค่าไม่เป็นศูนย์ (พิสูจน์แล้วใน Render pipeline) ความต่างที่พิสูจน์ตรงนี้คือเวอร์ชันเขียนมือ rebuild child ของมันทุก tick ด้วย ซึ่ง parameter `child` ของ `FadeTransition` หลีกเลี่ยงได้
- **"`cacheWidth`/`cacheHeight` สำคัญเท่ากันทุกแพลตฟอร์ม"** ตาม doc comment ของ widget เอง มันถูกมองข้ามโดยเฉพาะสำหรับ `Image.network` บน web เพราะ web engine ส่งต่อการ decode ให้ browser จัดการ
