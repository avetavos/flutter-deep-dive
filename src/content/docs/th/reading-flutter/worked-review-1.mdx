```dart
final onboarding = OnboardingState();

final todoRouter = GoRouter(
  initialLocation: '/onboarding',
  redirect: (context, state) {
    final onboardingPath = state.matchedLocation == '/onboarding';
    if (!onboarding.completed && !onboardingPath) return '/onboarding';
    return null;

  routes: [
    GoRoute(
      path: '/onboarding',
      builder: (context, state) => OnboardingScreen(onboarding: onboarding),

    StatefulShellRoute.indexedStack(
      builder: (context, state, navigationShell) =>
          TodoShellScaffold(navigationShell: navigationShell),

        ]),
```

## เดินรีวิวทีละบั๊ก

### 1. ไม่มี `ProviderScope` -- `ConsumerWidget` ทุกตัวจะ throw ทันทีที่อ่าน provider

`main.dart` ไม่เคยห่อ `TodoApp` ด้วย `ProviderScope` เลย `OnboardingScreen` ไม่แตะ provider เลยสักตัว ดังนั้น test ของ AI เอง (รวมถึงการดูหน้าแรกด้วยตาเปล่า) จึงไม่มีทางเจอปัญหานี้ -- มันจะ crash ก็ต่อเมื่อ navigation ไปถึง `ConsumerWidget` ตัวจริงเท่านั้น พิสูจน์ตรงนี้โดยทำ onboarding ให้เสร็จแล้วไปที่ `/todos`:

```text
StateError: Bad state: No ProviderScope found
```

<SpotTheBug code={`void main() {
  runApp(const TodoApp());
}`}>
เป็นกับดักเดียวกับที่พิสูจน์ไว้ใน **[Provider & Riverpod](/flutter/th/state-management/provider-and-riverpod/)** เป๊ะ ๆ: `ref.watch`/`ref.read` ทุกตัวต้องการ `ProviderContainer` ที่เข้าถึงได้ผ่าน `ProviderScope` และ Riverpod ไม่ได้สร้างให้อัตโนมัติ วิธีแก้คือบรรทัดเดียวที่ root: `runApp(const ProviderScope(child: TodoApp()))`
</SpotTheBug>

### 2. ลืม `part 'todos_provider.g.dart';` -- compile error จริง แยกออกมาอีกตัว

โค้ด `todos_provider.dart` ที่ shipped จริงด้านบนไม่มีปัญหานี้ (มี `part` directive อยู่แล้ว) แต่ความผิดพลาดแบบเดียวกันเคยโผล่มาใน revision ก่อนหน้าของ class ตัวเดียวกันนี้เอง และพบบ่อยพอที่จะแยกมาพูดต่างหาก นี่คือ `flutter analyze` output จริง ไม่ได้ตัดต่อ สำหรับ snippet ในหัวข้อก่อนหน้า:

```text
error • Classes can only extend other classes. Try specifying a different superclass, or removing the extends clause • extends_non_class
warning • The method doesn't override an inherited method • override_on_non_overriding_member
error • Undefined name 'state'. Try correcting the name to one that is defined, or defining the name • undefined_identifier
error • Undefined name 'state'. Try correcting the name to one that is defined, or defining the name • undefined_identifier
```

`_$TodosNotifier` ไม่มีอยู่จริงถ้าไม่มี `part` directive ดึงไฟล์ generated ที่นิยามมันเข้ามา -- analyzer จึงอ่าน `extends _$TodosNotifier` ว่าเป็นการ extend ชื่อที่ไม่มีนิยาม และ `state` (ที่ `_$TodosNotifier` ควรจะให้มา) ก็ undefined เหมือนกัน สองครั้ง เพราะใช้สองครั้งในบรรทัดเดียวกัน

### 3. ลำดับ route: `/todos/:id` ประกาศก่อน `/todos/new`

ในสาขา (branch) Todos นั้น `router.dart` ประกาศ route แบบมีพารามิเตอร์สำหรับ details **ก่อน** route ตัวอักษรตรง ๆ `/todos/new` go_router จะจับคู่ตาม route list ของ branch นั้นจากบนลงล่าง ใครแมตช์ก่อนชนะ:

```dart
// test/todo_app/route_order_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/todo_app/router.dart';

void main() {
  testWidgets('"/todos/new" is swallowed by ":id" declared first -- NewTodoScreen never builds', (tester) async {
    onboarding.complete();
    await tester.pumpWidget(
      ProviderScope(child: MaterialApp.router(routerConfig: todoRouter)),
    );
    todoRouter.go('/todos/new');
    await tester.pumpAndSettle();

    expect(find.byType(TextField), findsNothing,
        reason: 'NewTodoScreen (which has a TextField) never built');
    expect(find.text('Not found'), findsOneWidget,
        reason: '":id" matched first with id="new" -- TodoDetailsScreen '
            'looked up a todo with id "new", found none, and shows '
            '"Not found" instead of the new-todo form');
  });
}
```

```text
✓ "/todos/new" is swallowed by ":id" declared first -- NewTodoScreen never builds

00:00 +1: All tests passed!
```

กับดักเดียวกันนี้พิสูจน์ไว้แล้วกับคู่ route ระดับบนสุดใน **[Declarative routing](/flutter/th/navigation/declarative-routing/)**; มันใช้ได้เหมือนกันทุกประการกับ route ที่ประกาศอยู่ใน list ของ `StatefulShellBranch` ตัวใดตัวหนึ่ง

### 4. ใช้ `context.go` ทั้งที่ควรใช้ `push` -- back stack หายไป

`TodosListScreen` เปิดหน้า details ด้วย `context.go('/todos/${todo.id}')` `go` จะตั้งตำแหน่งปัจจุบันของ router ใหม่เลย ไม่ได้ push ทับสิ่งที่มีอยู่:

```dart
// test/todo_app/go_vs_push_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/todo_app/router.dart';
import 'package:my_app/todo_app/todos_provider.dart';

void main() {
  testWidgets('tapping a todo uses context.go -- the Todos list is gone from the back stack', (tester) async {
    onboarding.completed = false;
    final container = ProviderContainer();
    addTearDown(container.dispose);
    container.listen(todosProvider, (_, _) {}); // keep alive: todosProvider is .autoDispose by default
    container.read(todosProvider.notifier).add('Buy milk'); // id '0'

    await tester.pumpWidget(
      UncontrolledProviderScope(
        container: container,
        child: MaterialApp.router(routerConfig: todoRouter),
      ),
    );
    onboarding.complete();
    todoRouter.go('/todos');
    await tester.pumpAndSettle();

    await tester.tap(find.text('Buy milk'));
    await tester.pumpAndSettle();
    expect(find.text('not done'), findsOneWidget, reason: 'details screen opened');

    expect(find.byTooltip('Back'), findsNothing,
        reason: 'context.go() replaced the list route instead of pushing '
            'on top of it -- the back stack lost the Todos list entirely');
  });
}
```

```text
✓ tapping a todo uses context.go -- the Todos list is gone from the back stack

00:00 +1: All tests passed!
```

### 5. `redirect` แต่ไม่มี `refreshListenable` -- onboarding เสร็จแล้วแอปไม่รู้เรื่อง

`redirect` ระดับบนสุดใน `router.dart` เช็ก `onboarding.completed` แต่ไม่มีอะไรบอกให้ router รัน `redirect` ใหม่เมื่อ `onboarding` เองเปลี่ยนค่า -- มีแค่ navigation เท่านั้นที่ทำให้ประเมินใหม่:

```dart
// test/todo_app/redirect_no_refresh_test.dart
```

### 8. `ref.watch` ใน `onPressed` -- ไม่ throw แต่ก็ยังผิดอยู่ดี

ปุ่ม submit ของ `NewTodoScreen` อ่าน `ref.watch(todosProvider.notifier)` จากข้างใน callback แทนที่จะเป็น `ref.read` สมมติฐานทั่วไปคือมันน่าจะ throw ทันที เหมือนที่ `ref.listen` ทำ (`ref.listen can only be used within the build method of a ConsumerWidget` ซึ่งเป็น `assert` จริงใน source ของ `flutter_riverpod` เอง) แต่ `watch` **ไม่มี assertion แบบนั้นเลย** -- เช็กตรงจาก package ที่ติดตั้งจริง พิสูจน์ด้วยตัวนับ build: แตะปุ่มที่เรียก `ref.watch` ไม่ throw และไม่ทำให้ rebuild ทันที -- แต่มันแอบลงทะเบียน subscription ที่ `build()` จริง ๆ ควรจะเคลียร์ทิ้งไป ดังนั้นการเปลี่ยนแปลง state อื่นที่ไม่เกี่ยวข้องในภายหลังจะทำให้เกิด rebuild ที่ไม่มีอะไรใน `build()` เรียกร้องเลย:

```dart
// lib/wr1_examples/watch_in_callback.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final counterProvider = NotifierProvider<CounterNotifier, int>(CounterNotifier.new);

  @override

    buildCount++;

      onPressed: () {
        final count = ref.watch(counterProvider); // AI comment: "grab the latest count"
        debugPrint('count: $count');
      },
      child: const Text('tap'),
    );
  }
}
```

### 9. ลืม `.autoDispose` บน `selectedTodoProvider` -- state ของ todo ทุกตัวที่เคยเปิดดูจะถูกแคชไว้ตลอดไป

`todo_details_provider.dart` เป็น `Provider.family` ที่เขียนมือ ไม่ใช่ตัวที่ generate -- มันจึงไม่ได้พฤติกรรม `.autoDispose`-by-default ของ `@riverpod` เลยสักนิด พิสูจน์ด้วย `ProviderObserver` ที่คอยดู `didDisposeProvider`:

### 10. `setState` หลัง `await` ที่ไม่มี guard, ไม่เช็ก `mounted`

`TodoDetailsScreen._confirmView` await ผลลัพธ์ที่ดีเลย์ไว้ แล้วเรียก `setState` แบบไม่มีเงื่อนไข ถ้าหน้านี้ถูกเอาออกจาก tree ระหว่างที่ `Future` นั้นยังค้างอยู่ (todo ของมันถูกลบจากอีกแท็บหนึ่ง, stack ของ branch เปลี่ยน) widget ก็ถูก dispose ไปแล้วตอนที่ผลลัพธ์กลับมา นี่คือกลไกเดียวกันเป๊ะที่พิสูจน์ไว้ครบทุกขั้นตอนแล้วในส่วน `mounted`-guard ของบท **[setState and lifecycle](/flutter/th/state-management/setstate-and-lifecycle/)** ทำซ้ำที่นี่สำหรับรูปแบบเฉพาะของหน้านี้:

```dart
    setState(() => _confirmation = label);
  }

  @override

      body: Column(
        children: [
          Text(todo?.done == true ? 'done' : 'not done'),
          if (_confirmation != null) Text(_confirmation!),
          ElevatedButton(onPressed: _confirmView, child: const Text('confirm view')),
        ],
      ),
    );
  }
```

| # | Bug | Fix |
|---|---|---|
| 1 | ไม่มี `ProviderScope` ที่ root | `runApp(const ProviderScope(child: TodoApp()))` -- พิสูจน์แล้ว: ถ้าไม่มี จะได้ `Bad state: No ProviderScope found` |
| 2 | ลืม `part 'todos_provider.g.dart';` | มี `part` directive จริง -- ไม่งั้นจะได้ `extends_non_class` + `undefined_identifier` |
| 3 | `/todos/:id` ประกาศก่อน `/todos/new` | ประกาศ `/todos/new` ก่อน -- พิสูจน์แล้ว: route ตัวอักษรตรง ๆ ชนะตอนนี้ |
| 4 | `context.go` เพื่อเปิด details | `context.push` -- พิสูจน์แล้ว: `/todos` ยังอยู่บน back stack, ปุ่ม Back โผล่มา |
| 5 | `redirect` ไม่มี `refreshListenable` | `refreshListenable: onboarding` -- พิสูจน์แล้ว: แค่ `onboarding.completed` เปลี่ยนก็ redirect ได้แล้ว |
| 6 | `StateNotifierProvider` ไม่มี `legacy.dart`, ปนกับ codegen ที่อื่น | ลบทิ้ง -- migrate เป็น `Notifier`/`@riverpod` เหมือนส่วนอื่นของแอป |
| 7 | `ref.read` ใน `TodosListScreen.build` | `ref.watch` -- พิสูจน์แล้ว: list rebuild หลัง `add()` แล้ว |
| 8 | `ref.watch` ใน `onPressed` | `ref.read` -- พิสูจน์แล้ว: ไม่มี subscription/rebuild leak หลอน ๆ อีกแล้ว |
| 9 | `selectedTodoProvider` เขียนมือ ไม่มี `.autoDispose` | provider แบบ `@riverpod` function ตัวจริง -- พิสูจน์แล้ว: ถูก dispose ทันทีที่ listener สุดท้ายปิด |
| 10 | `setState` หลัง `await` ที่ไม่มี guard | เติม `if (!mounted) return;` ก่อน `setState` |

## สิ่งที่ reviewer เขียนใน PR

> โครงสร้างโอเคเลย แต่ merge แบบนี้เลยไม่ได้ -- มี 10 เรื่อง เรียงตามลำดับที่จะกัดจริง ๆ:
>
> 1. **ไม่มี `ProviderScope`** test ของคุณเองไม่เคยไปถึง `ConsumerWidget` เลยเลยผ่าน -- แต่หน้าจริงหน้าแรกจะ throw `Bad state: No ProviderScope found` ห่อ `TodoApp` ด้วย `ProviderScope` ที่ root
> 2. **`TodosNotifier` shipped ไปโดยไม่มี `part` directive** ใน revision ก่อนหน้า -- `extends _$TodosNotifier` resolve ไม่ได้ถ้าไม่มีมัน เช็กให้ดีว่าทุกไฟล์ `@riverpod` มี `part '<file>.g.dart';` อยู่ต่อจาก import ทันที
> 3. **ลำดับ route** `/todos/:id` ประกาศก่อน `/todos/new` ใน branch Todos -- `/todos/new` เลยไปแมตช์ route แบบ id ก่อน route ตัวอักษรตรง ๆ ต้องมาก่อน route แบบพารามิเตอร์เสมอ
> 4. **`context.go` สำหรับ details** ทำให้ `/todos` หลุดจาก back stack -- ผู้ใช้กลับไป list ไม่ได้ ใช้ `context.push` แทน
> 5. **`redirect` ไม่มี `refreshListenable`** ใช้ได้ดีกับ flow ของปุ่มเอง (มันเรียก `go()` เอง) แต่ทางอื่นที่ทำให้ onboarding เสร็จ -- session ที่ restore, background callback -- จะทำให้ผู้ใช้ติดอยู่ที่หน้า onboarding ตลอดไป ต่อ `refreshListenable: onboarding` เข้าไป
> 6. **`StateNotifierProvider` ต้องการ `package:flutter_riverpod/legacy.dart`** ใน Riverpod 3 -- ไม่ได้อยู่ใน barrel หลักแล้ว แต่เพราะแอปนี้ใช้ `@riverpod` อยู่แล้วทุกที่ migrate ตัวนี้ไปด้วยเลยดีกว่า ไม่ต้องไปปลดล็อก legacy import
> 7. **`ref.read` ใน `TodosListScreen.build`** list ไม่อัปเดตหลังเพิ่ม todo ควรเป็น `ref.watch`
> 8. **`ref.watch` ใน `onPressed`** ไม่ throw (นั่นเป็นหน้าที่ของ `ref.listen`) แต่มันทิ้ง subscription ค้างไว้ที่ทำให้เกิด rebuild ที่ไม่เกี่ยวข้องภายหลัง ควรเป็น `ref.read` -- มันคือ action ที่ทำครั้งเดียว ไม่ใช่อะไรที่ต้อง subscribe
> 9. **`selectedTodoProvider` ไม่เคย dispose** มันเขียนมือ ไม่ได้ generate เลยข้าม `.autoDispose` ไปทั้งหมด -- todo ID ทุกตัวที่เคยเปิดดูจะถูกแคชไว้ตลอดอายุแอป generate ด้วย `@riverpod` แทน
> 10. **ลืมเช็ก `mounted`** ใน `_confirmView` ถ้าหน้านี้หายไปกลางที่ await อยู่ `setState` จะ throw `setState() called after dispose()`
>
> ไม่มีข้อไหนต้องออกแบบใหม่เลย -- ยินดี pair กันแก้

## Mental Model

มีแค่ 2 ใน 10 bug นี้ (2, 6) ที่ analyzer จับได้ฟรี ๆ ในรูปของ compile error -- ทั้งคู่คือความผิดพลาดแบบเดียวกันแค่ห่มเสื้อคนละแบบ: ทั้ง codegen และ legacy API ต่างต้องการ import/directive เพิ่ม ซึ่ง AI assistant ที่เทรนมาจาก snippet และไฟล์ Riverpod ยุคก่อน 3.0 เป็นส่วนใหญ่ มักลืมง่ายมาก อีก 8 ตัวที่เหลือคอมไพล์และรันได้สบายบน path เดียวที่ AI ทดสอบจริง: `ConsumerWidget` ที่อยู่ลึกในทรีจนการทดสอบด้วยตาเปล่าไปไม่ถึง, ลำดับ route ที่สำคัญก็ต่อเมื่อลองเส้นทางตัวอักษรตรง ๆ เท่านั้น, bug ที่เกี่ยวกับ `push` ที่มองไม่เห็นจนกว่าจะเช็กหาปุ่ม Back, `redirect` ที่ถูกกลบด้วยปุ่มเดียวที่เรียก `go()` เอง, `ref.watch`/`ref.read` สลับกันในแบบที่ไม่ throw ทั้งคู่, provider ที่ "ผิด" ก็ต่อเมื่อเฝ้าดูมันตอน dispose เท่านั้น และ guard เรื่อง lifecycle ที่สำคัญก็ต่อเมื่อมีอะไรบางอย่าง dispose จริง ๆ กลาง await เท่านั้น นี่คือรูปแบบเดียวกับ worked review ทุกบทในโมดูลนี้: **compiler คือพื้นไม่ใช่เพดาน** -- มันจับ directive ที่หายไปกับชื่อที่ไม่นิยามได้ แต่ไม่มีทางจับได้ว่า "โค้ดที่ valid ทางเทคนิคนี้ทำสิ่งที่ผิดภายใต้เงื่อนไขที่ยังไม่มีใครบังเอิญไปกระตุ้นมัน"

## Trade-offs

| ตัวเลือก | ข้อดี | ต้นทุน |
|---|---|---|
| `@riverpod` codegen ทุกที่ | ค่าเริ่มต้น `.autoDispose` สม่ำเสมอ, boilerplate น้อยลง | provider แบบ family/details ทุกตัวต้อง generate จริง ๆ -- เขียนมือแล้ว opt out เงียบ ๆ โดยไม่รู้ตัว |
| `StatefulShellRoute.indexedStack` | แต่ละแท็บมี back stack และ state ของหน้าเป็นของตัวเอง | ทุก branch อยู่ใน memory ตลอด; state ที่ leak (bug 9) ก็ leak แยกต่อ branch เหมือนกัน |
| `redirect` + `refreshListenable` | ตอบสนองการเปลี่ยน state ได้โดยไม่ต้องเรียก navigation เพิ่ม | ต้องต่อและดูแล object เพิ่มอีกหนึ่งตัว (`Listenable`) |
| `push` สำหรับ drill-down, `go` สำหรับกระโดดระดับแท็บ | back stack คาดเดาได้ | เผลอใช้ `go` เป็นความเคยชินได้ง่ายทุกที่ รวมถึงจุดที่ควรใช้ `push` |

## Common Misconceptions

- **"`ref.watch` ที่เรียกนอก `build` จะ throw เหมือน `ref.listen`"** พิสูจน์แล้วด้านบน: ไม่จริง source ของ `flutter_riverpod` เอง assert `debugDoingBuild` แค่ใน `listen` เท่านั้น ไม่มีใน `watch` เลย -- `watch` แอบลงทะเบียน subscription ที่ build pass จริง ๆ ควรจะเคลียร์ทิ้ง กลายเป็น rebuild leak แทนที่จะ crash
- **"provider `.family` ที่เขียนมือปลอดภัยพอ ๆ กับตัวที่ generate"** พิสูจน์แล้วด้านบน: `@riverpod` มี `.autoDispose` เป็นค่าเริ่มต้น; `Provider.family` ที่เขียนมือไม่ได้ opt in อะไรเลยนอกจากคุณจะเขียน `.autoDispose.family` เอง การข้าม codegen ไปเพราะ "แค่ provider อีกตัวเดียว" จะทำให้ค่าเริ่มต้นนั้นหายไปเงียบ ๆ
- **"ถ้า test ของ AI ผ่าน หน้าที่มันอ้างว่าทดสอบก็โอเคแล้ว"** widget test ของ AI pump แค่ `OnboardingScreen` ซึ่งไม่แตะ provider เลย -- มันไม่พิสูจน์อะไรเกี่ยวกับ bug 1 เลย ทั้งที่เป็น bug เดียวที่ทำให้ทุกหน้าอื่นในแอป crash
- **"ลำดับ route ใน `StatefulShellBranch` ไม่สำคัญเหมือน route ระดับบนสุด"** พิสูจน์แล้วด้านบน: มันเป็นพฤติกรรม first-match-wins แบบเดียวกันเป๊ะ แค่ scope อยู่ที่ route list ของ branch นั้นเอง
