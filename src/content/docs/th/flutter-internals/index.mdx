## โมดูลนี้มีไว้ทำอะไร

ทุกโมดูลก่อนหน้านี้ในคอร์สสอนให้คุณ*ใช้*Flutter: สร้าง widget, จัดการ state, navigate, จัด layout หน้าจอ, ship build ไม่มีข้อไหนต้องรู้ว่า `setState` ทำอะไรจริง ๆ ข้างใต้, "relayout boundary" คืออะไร, ทำไม PSO ของ Impeller ถึง "precompiled", หรือ `gen_snapshot` สร้างอะไรจริง ๆ ช่องว่างนั้นแหละคือจุดที่คำอธิบาย Flutter ที่ฟังดูมั่นใจ (ไม่ว่ามนุษย์หรือ AI เขียน) ผิดพลาดในแบบที่ `flutter analyze` เพียงอย่างเดียวจับไม่ได้ — ข้อกล่าวอ้างที่ฟังดูสมเหตุสมผลอย่าง "UI thread กับ raster thread รวมกันแล้ว" หรือ "isolate แต่ละตัวมี heap แยกกันโดยสิ้นเชิง" อ่านดูน่าเชื่อถือจนกว่าคุณจะตรวจ source จริงหรือรันคำสั่งจริง

โมดูลนี้ตอบคำถามภายในห้าข้อ แต่ละข้อพิสูจน์กับ source จริงของ Flutter 3.47.5 / Dart 3.13.4 ที่ติดตั้งไว้ (revision `6a19cca564`) หรือคำสั่งจริงที่รันบน Mac เครื่องนี้ ไม่เคยยืนยันจากความจำ:

1. **เกิดอะไรขึ้นจริง ๆ ระหว่าง widget rebuild กับ pixel เปลี่ยน?** ([The Three Trees, From the Source](/flutter/th/flutter-internals/three-trees/) — `Widget.canUpdate`, ตาราง 4 กรณีจริงของ `Element.updateChild`, `RenderObjectWidget` ที่เขียนเองพิสูจน์ว่า `createRenderObject`/`updateRenderObject`/`performLayout`/`paint` คือ hook สี่ตัวที่กระตุ้นแยกกันได้ และการ reparent ด้วย `GlobalKey` พิสูจน์ด้วย `identical()`)
2. **อะไรที่เปลี่ยน "widget เรียก `setState`" ให้เป็น "เฟรมหนึ่งรันจริง" และตามลำดับไหน?** ([Build Scheduling and Frames](/flutter/th/flutter-internals/build-scheduling-and-frames/) — `SchedulerPhase` enum จริง, doc comment 8 ขั้นของ `WidgetsBinding.drawFrame` เอง และ test จริงที่พิสูจน์ว่า `setState` แบบซิงโครนัสสองครั้งรวมกันเป็น build เดียว)
3. **สายการเรียก `markNeedsLayout` หยุดไต่ tree ตรงไหนแน่ ๆ?** ([Layout and Paint Internals](/flutter/th/flutter-internals/layout-and-paint-internals/) — กฎ relayout-boundary ที่แน่นอนอ้างจาก source พิสูจน์ด้วยคู่ `RenderBox` ที่เขียนเองและ `debugDumpRenderTree` จริงที่แสดง annotation ของ boundary ปรากฏและหายไป)
4. **Impeller แทนที่อะไรจริง ๆ และ "UI+raster รวมกันแล้ว" จริงไหม?** ([Impeller and the GPU](/flutter/th/flutter-internals/impeller-and-the-gpu/) — README ของ engine เองและ source ของ `Entity`/`Contents`/`RenderPass` และการแก้ไขจริง: การรวม thread ตั้งแต่ 3.29+ ที่มีเอกสารรองรับคือ UI+**platform** ไม่ใช่ UI+raster)
5. **`flutter build` รันอะไรจริง ๆ และโมเดลหน่วยความจำของ Dart isolate หน้าตาเป็นแบบไหนจริง ๆ?** ([The Dart VM and Isolates](/flutter/th/flutter-internals/dart-vm-and-isolates/) — output แบบ verbose จริงของ `flutter build apk`/`flutter build web`, ELF `libapp.so` จริงที่แกะออกมาตรวจด้วย `file(1)` และหลักฐานสด ๆ ที่ grep เจอว่า branch ของ `kDebugMode` ถูกลบออกจาก release build)

## การพิสูจน์แต่ละอย่างในโมดูลนี้ทำอย่างไร

ทุกข้อกล่าวอ้างระดับ source ด้านล่างอ้าง permalink จริงเข้าไปใน `github.com/flutter/flutter` ที่ revision ที่คอร์สนี้ตรึงไว้ `6a19cca564` (Flutter 3.47.5) หรือ `github.com/dart-lang/sdk` ที่ tag ที่ตรงกัน `3.13.4` — revision เดียวกับที่ `flutter --version` รายงานบน Mac เครื่องนี้ ดังนั้นทุกเลขบรรทัดที่อ้างจะตรงกับที่ลิงก์ไว้ แม้ SDK นี้จะอัปเกรดในอนาคต ทุกข้อกล่าวอ้างระดับ runtime คือการรัน `flutter test` จริงกับ probe ที่ share ของคอร์สนี้ (output ตัดทอนจริง ไม่เคยแต่งขึ้น) และทุกข้อกล่าวอ้างเกี่ยวกับ build pipeline (ข้อความ `--help` ของ CLI ของ [Impeller and the GPU](/flutter/th/flutter-internals/impeller-and-the-gpu/), output ของ `flutter build apk`/`flutter build web -v` ของ [The Dart VM and Isolates](/flutter/th/flutter-internals/dart-vm-and-isolates/)) คือคำสั่งจริงที่รันบน Mac เครื่องนี้ ผ่าน probe หรือแอป scratch จาก `flutter create` แบบใช้แล้วทิ้งสำหรับสิ่งที่ probe ที่ share รันไม่ได้อย่างปลอดภัย (การ build APK/web เต็มรูปแบบ) จุดที่สภาพแวดล้อมนี้ไม่มี device และข้อกล่าวอ้างยืนยันในเครื่องจริง ๆ ไม่ได้ (screenshot ของ DevTools raster-stats, frame trace จริงของ Impeller ใน production) แต่ละบทพูดตรง ๆ แทนที่จะเดา

## Mental Model

ทุกบทในโมดูลนี้คือแนวคิดเดียวกันที่นำไปใช้กับคนละชั้น: **ภายในของ Flutter ไม่ใช่กล่องดำ — มันคือชุด source file และคำสั่งที่รันได้จริงที่ตายตัว ซึ่งจะแสดงกลไกจริงให้คุณเห็นตรง ๆ เสมอ** "rebuild แพง" ไม่ใช่คำขวัญ มันคือการทดสอบสองฟิลด์ที่แน่นอนของ `Widget.canUpdate` พิสูจน์ได้ด้วย spy "relayout boundary หยุดการไต่" ไม่ใช่อุปมา มันคือบรรทัดเดียวตรงตัว `_isRelayoutBoundary = !parentUsesSize || sizedByParent || constraints.isTight || parent == null` พิสูจน์ได้ด้วย counter และ `debugDumpRenderTree` จริง "Impeller กำจัด shader jank" ไม่ใช่การตลาด มันคือ doc comment ของ `ContentContextOptions` เองที่จำกัดจำนวน PSO variant ไว้ที่ "หลายร้อย ไม่ใช่หมื่น" เมื่อคุณรู้ว่า source file หรือคำสั่งไหนพิสูจน์ข้อกล่าวอ้างไหน "เชื่อฉันสิ Flutter ทำงานแบบนี้ข้างใต้" ก็ไม่จำเป็นอีกต่อไป — สำหรับข้อกล่าวอ้างของคุณเอง และสำหรับตัดสินข้อกล่าวอ้างของ AI

## Common Misconceptions

- **"widget rebuild หมายความว่ามี `RenderObject` ใหม่เสมอ"** [The Three Trees](/flutter/th/flutter-internals/three-trees/) พิสูจน์ตรงข้ามด้วย counter จริง: `createRenderObject` รันครั้งเดียว; rebuild ที่ key เดิมจ่ายแค่ค่า `updateRenderObject` เท่านั้น
- **"เรียก `setState` สองครั้งเสมอทำให้เกิด rebuild สองครั้ง"** [Build Scheduling and Frames](/flutter/th/flutter-internals/build-scheduling-and-frames/) พิสูจน์ว่า guard `if (dirty) return;` ของ `Element.markNeedsBuild` เองรวมการเรียกแบบซิงโครนัสสองครั้งให้เหลือ build เดียวเป๊ะ
- **"การทำเครื่องหมาย widget ว่าต้อง layout ทำให้ทุกอย่างข้างบนมัน relayout เสมอ"** [Layout and Paint Internals](/flutter/th/flutter-internals/layout-and-paint-internals/) พิสูจน์ว่า relayout boundary ดูดซับ dirty flag จริง ๆ — `debugDumpRenderTree` จริงยืนยันจากมุมที่สองที่เป็นอิสระ
- **"Impeller รวม UI thread กับ raster thread เข้าด้วยกัน"** [Impeller and the GPU](/flutter/th/flutter-internals/impeller-and-the-gpu/) พิสูจน์ด้วย quote จริงจาก `docs.flutter.dev` ว่าการรวมจริงตั้งแต่ 3.29+ คือ UI+platform บน iOS/Android — raster thread ที่ Impeller/Skia คุยกับ GPU จริง ๆ ไม่เคยถูกรวมกับ UI thread เลย
- **"Dart isolate แต่ละตัวมี heap แยกกันโดยสิ้นเชิง"** [The Dart VM and Isolates](/flutter/th/flutter-internals/dart-vm-and-isolates/) พิสูจน์จาก glossary ของ `dart-lang/sdk` เองว่า isolate ใน group เดียวกัน share heap — แล้วพิสูจน์สด ๆ ว่าการส่ง message ของ `compute()` ยัง copy ไม่ใช่ alias ไม่ว่าจะอย่างไร
