## non-nullable โดย default

Dart มี **sound** null safety: type ไม่สามารถเก็บ `null` ได้เว้นแต่คุณจะบอกชัด ๆ ด้วย `?` นี่คือการันตีแบบแข็ง ไม่ใช่ lint — ถ้า type system บอกว่าค่านั้น non-null จะเป็น null ตอน runtime ไม่ได้จริง ๆ dart.dev บอกตรง ๆ ว่านี่ไม่ใช่ตัวเลือกแล้ว: *["Dart has enforced sound null safety since Dart 3, released in May 2023."](https://dart.dev/null-safety)* — โหมด unsound/legacy แบบเก่าที่ SDK ของคอร์สนี้ (Dart 3.13) เคย opt-in ได้ไม่มีอยู่แล้ว

```dart
int a = 1;      // non-nullable — can never be null
int? b = null;  // nullable — the ? opts in to null

a = null;       // ❌ compile error: a cannot be null
b = 42;         // ✅ a nullable can also hold a real value
```

คำสำคัญคือ "sound": เพราะการันตีนี้แน่นหนา compiler จึง *optimize* ตามได้ และคุณก็ *เชื่อ* type ได้จริง widget property แบบ `String name` จะไม่มาเซอร์ไพรส์คุณด้วย null

## operator สี่ตัวที่คุณจะใช้ทุกวัน

```dart
String? maybeName;

// ?.  — null-aware access: call only if not null, else the whole thing is null
final len = maybeName?.length;        // int? — null if maybeName is null

// ??  — if-null: provide a fallback when the left side is null
final safe = maybeName ?? 'Guest';    // String — never null

// ??= — assign only if currently null
maybeName ??= 'Default';

// !   — null assertion: "I promise this isn't null" (throws if you're wrong)
final definite = maybeName!;          // String — DANGER if it's actually null
```

operator `!` คือตัวที่ต้องเคารพ: `!` สั่งปิดปาก compiler ด้วยการ *assert* ว่า non-null และถ้าคุณผิด จะ throw ตอน runtime ทุก `!` คือการเดิมพันเล็ก ๆ — ใช้เมื่อคุณพิสูจน์ได้ว่าค่านั้น non-null เท่านั้น

### `!` anti-pattern พิสูจน์ด้วย runtime error จริง

```dart
// lib/bang_operator.dart
String shout(String? input) => input!.toUpperCase(); // the anti-pattern: a bet with no proof
```

```dart
// test/bang_operator_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:probe/lessons/dart-foundations__null-safety/bang_operator.dart';

void main() {
  test('! is a runtime bet: it works when the value really is non-null', () {
    expect(shout('hi'), 'HI');
  });

  test('! throws a real, specific error when the bet is wrong', () {
    expect(() => shout(null), throwsA(isA<TypeError>()));
    try {
      shout(null);
      fail('should have thrown');
    } catch (e) {
      expect(e.toString(), contains('Null check operator used on a null value'));
    }
  });
}
```

```text
✓ ! is a runtime bet: it works when the value really is non-null
✓ ! throws a real, specific error when the bet is wrong

00:00 +2: All tests passed!
```

`Null check operator used on a null value` คือ crash log ที่พบบ่อยที่สุดอันหนึ่งของ Flutter บน production — มันแปลว่า `!` ที่ไหนสักแห่งเดิมพันผิด ทุกตัวคือ `?.`/`??`/`if (x == null)` guard ที่ไม่ได้ถูกเขียนไว้

## flow analysis narrow ให้คุณ

คุณแทบไม่ต้องใช้ `!` เพราะ **flow analysis** ของ Dart จะ narrow nullable เป็น non-null หลังผ่านการเช็ค:

```dart
void greet(String? name) {
  if (name == null) return;
  // From here down, Dart KNOWS name is String (not String?) — no ! needed.
  print(name.toUpperCase());
}
```

### Local เทียบกับ field — พิสูจน์ด้วย error จริง และข้อยกเว้นของ Dart 3.2

มีจุดที่กัด Flutter dev อยู่บ่อย: ปกติ promotion ทำงานกับ **local variable** ไม่ใช่กับ instance field หรือ getter เพราะ field อาจเปลี่ยนค่าระหว่างเช็คกับใช้งาน (method อื่นอาจรันแทรกกลาง) field แบบ public ที่ mutable จะไม่ถูก promote เลย — การเช็คไม่ช่วยอะไรกับการอ่านถัดไป เป็น error จริง:

```dart
// @expect-error real unchecked_use_of_nullable_value diagnostic, captured below
class Greeter {
  String? name;

  String greet() {
    if (name != null) {
      // ❌ `name` is a FIELD, not a local — flow analysis does not promote
      // it (it could change between the check and this read, e.g. via
      // another method or a getter with side effects).
      return 'Hello, ${name.length}'; // still String?, not promoted to String
    }
    return 'Hello, stranger';
  }
}
```

```text
error • The property 'length' can't be unconditionally accessed because the receiver can be 'null'.
Try making the access conditional (using '?.') or adding a null check to the target ('!') •
unchecked_use_of_nullable_value
```

วิธีแก้แบบดั้งเดิมคือ copy field มาเป็น local ก่อน แล้วค่อยเช็ค local นั้น (ซึ่ง analyzer เชื่อ เพราะ local เปลี่ยนแปลงกลางคันไม่ได้จริง) แต่ Dart 3.2 เพิ่มข้อยกเว้นจริง ๆ [ยืนยันโดยหน้า non-promotion-reasons ของ dart.dev](https://dart.dev/tools/non-promotion-reasons): field แบบ **private และ final** ที่ไม่มี declaration ขัดแย้งกัน *promote ได้จริง* เพราะความเสี่ยง "อาจเปลี่ยนค่า" พวกนั้นไม่มีผลกับมันเลย:

```dart
class Greeter2 {
  final String? _name; // private + final — DOES get promoted (Dart 3.2+)
  Greeter2(this._name);

  String greet() {
    if (_name != null) {
      return 'Hello, ${_name.length}'; // promoted to String here — no error
    }
    return 'Hello, stranger';
  }
}
```

`flutter analyze` บน `Greeter2` รายงานศูนย์ปัญหา — เป็นการปรับปรุงจริงของ Dart ปัจจุบันเหนือกว่าคำแนะนำเก่าที่บอกให้ "copy ไปเป็น local เสมอ"

## `late`: สัญญาว่าจะ initialize ก่อนใช้

`late` บอกว่า "อันนี้จะเป็น non-null ตอนที่มีใครอ่าน แค่ตอนประกาศยังไม่มีค่า" มีประโยชน์กับค่าที่ set ใน `initState` หรือคำนวณครั้งเดียว — [setState & the Lifecycle](/flutter/th/state-management/setstate-and-lifecycle/) พิสูจน์ต้นทุนจริงตอน runtime ของการผิดสัญญานั้นไปแล้ว (`LateInitializationError`) สำหรับ `late final` field ที่ยังไม่ได้ assign หลัง `initState`

```dart
late final String config;   // no value yet, but promised before first read
// If you read it before assigning, you get a LateInitializationError.
```

ใช้ `late` อย่างประหยัด — เพราะเป็นการแลกการันตีตอน compile-time ไปเป็นตอน runtime `late` ที่ใช้ผิดก็คือ `!` ในคราบปลอมนั่นเอง

### Definite assignment analysis พิสูจน์ด้วย diagnostic จริงสองแบบ

ถ้าไม่ใช้ `late` non-nullable local ที่ไม่ถูก assign ทุก path จะเป็น compile error จริงทันที — Dart พิสูจน์ไม่ได้ว่ารับประกันค่าได้ จึงปฏิเสธ local ที่ไม่ใช่ `final` จะได้ diagnostic แบบหนึ่ง:

```dart
// @expect-error real not_assigned_potentially_non_nullable_local_variable diagnostic, captured below
String describe(bool flag) {
  String label; // non-final, non-nullable, no initializer
  if (flag) {
    label = 'yes';
  }
  return label; // no `else` — not assigned on every path
}
```

```text
error • The non-nullable local variable 'label' must be assigned before it can be used. Try giving
it an initializer expression, or ensure that it's assigned on every execution path •
not_assigned_potentially_non_nullable_local_variable
```

local ที่เป็น `final` ที่มีช่องว่างแบบเดียวกันจะได้ diagnostic ที่**ต่างออกไป**จริง ๆ — ใช้คำว่า "potentially unassigned" แทน "must be assigned":

```dart
// @expect-error real read_potentially_unassigned_final diagnostic, captured below
String describe(bool flag) {
  final String label; // not-yet-assigned, non-nullable, final local
  if (flag) {
    label = 'yes';
  }
  return label; // no `else` — not assigned on every path
}
```

```text
error • The final variable 'label' can't be read because it's potentially unassigned at this point.
Ensure that it is assigned on necessary execution paths • read_potentially_unassigned_final
```

ทั้งคู่แก้แบบเดียวกัน: assign ให้ครบทุก path (เพิ่ม `else`) หรือให้ initializer ตั้งแต่แรก

## Null-aware pattern และ collection

Pattern (บทก่อนหน้า) มีรูปแบบ null-aware ของตัวเอง บวกกับ null-aware spread สำหรับ collection:

```dart
// lib/null_patterns.dart

// Null-check pattern: `var x?` matches only if the value is non-null, and
// binds `x` with the non-null type — the pattern-matching equivalent of `!`,
// but as a conditional match instead of a throwing assertion.
String describe(int? maybeValue) => switch (maybeValue) {
  var x? => 'value: $x', // matches non-null, binds int (not int?)
  null => 'nothing',
};

// Null-assert pattern: `expr!` inside a pattern — asserts non-null the way
// the `!` operator does, but as part of destructuring.
(int, int) unwrapPair((int?, int?) pair) {
  final (a!, b!) = pair; // throws if either half is null
  return (a, b);
}

// Null-aware spread (`...?`) and null-aware collection-if guard against a
// nullable list contributing nothing instead of throwing.
List<String> merge(List<String>? maybeExtra) => [
  'base',
  ...?maybeExtra, // spreads only if non-null; a bare `...` would throw on null
];
```

```dart
// test/null_patterns_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:probe/lessons/dart-foundations__null-safety/null_patterns.dart';

void main() {
  test('null-check pattern (var x?) matches non-null and binds the promoted type', () {
    expect(describe(5), 'value: 5');
    expect(describe(null), 'nothing');
  });

  test('null-assert pattern (a!) destructures and throws on a null field', () {
    expect(unwrapPair((1, 2)), (1, 2));
    expect(() => unwrapPair((null, 2)), throwsA(isA<TypeError>()));
  });

  test('null-aware spread (...?) contributes nothing instead of throwing on null', () {
    expect(merge(['x', 'y']), ['base', 'x', 'y']);
    expect(merge(null), ['base']);
  });
}
```

```text
✓ null-check pattern (var x?) matches non-null and binds the promoted type
✓ null-assert pattern (a!) destructures and throws on a null field
✓ null-aware spread (...?) contributes nothing instead of throwing on null

00:00 +3: All tests passed!
```

## `List<String?>` เทียบกับ `List<String>?` และ required named parameter

สอง type นี้ต่างกันจริง ๆ และสลับผิดได้ง่าย:

```dart
// lib/list_nullability.dart
// `List<String?>` — a non-nullable list whose ELEMENTS may be null.
// `List<String>?` — a nullable list whose elements, if the list exists, are
// never null. These are genuinely different types; do not confuse them.

int countNulls(List<String?> items) => items.where((e) => e == null).length;

int lengthOrZero(List<String>? maybeItems) => maybeItems?.length ?? 0;

String greetAll({required String from}) => 'from $from';
```

```dart
// test/list_nullability_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:probe/lessons/dart-foundations__null-safety/list_nullability.dart';

void main() {
  test('List<String?>: the list always exists, but elements may be null', () {
    expect(countNulls(['a', null, 'b', null]), 2);
  });

  test('List<String>?: the list itself may be null, but elements never are', () {
    expect(lengthOrZero(['a', 'b']), 2);
    expect(lengthOrZero(null), 0);
  });

  test('a required named parameter must be supplied — see the lesson for the real missing_required_argument error', () {
    expect(greetAll(from: 'Ada'), 'from Ada');
  });
}
```

```text
✓ List<String?>: the list always exists, but elements may be null
✓ List<String>?: the list itself may be null, but elements never are
✓ a required named parameter must be supplied — see the lesson for the real missing_required_argument error

00:00 +3: All tests passed!
```

การละ argument ที่เป็น `required` คือ compile error จริงทันที ไม่ใช่เรื่องเซอร์ไพรส์ตอน runtime:

```dart
// @expect-error real missing_required_argument diagnostic, captured below
import 'list_nullability.dart';

void demo() {
  greetAll(); // missing the required `from` argument
}
```

```text
error • The named parameter 'from' is required, but there's no corresponding argument. Try adding
the required argument • missing_required_argument
```

Dart เป็น non-nullable โดย default และถูกบังคับแบบ **sound** ตั้งแต่ Dart 3 — โหมด legacy/unsound หมดไปแล้ว (พิสูจน์ด้วย citation ของ dart.dev ข้างบน) `!` คือการเดิมพันตอน runtime — พิสูจน์แล้วข้างบนด้วยข้อความ crash จริง `Null check operator used on a null value` ตอนที่มันแพ้ flow analysis promote **local** ไม่ใช่ field ธรรมดา (พิสูจน์ด้วย error จริง `unchecked_use_of_nullable_value`) — ยกเว้น field แบบ private `final` ตั้งแต่ Dart 3.2 ที่ promote ได้จริง definite-assignment analysis บล็อกการอ่าน non-nullable local ที่ยังไม่ assign ในบาง path ด้วย diagnostic จริงสองแบบต่างกันตาม `final` Pattern มีรูปแบบ null-aware ของตัวเอง (`var x?`, `a!`, `...?`) และ `List<String?>` ไม่ใช่ `List<String>?` — nullability อยู่คนละตำแหน่งใน type
</Callout>

## อ่านโค้ดที่ AI สร้างให้

Dart ที่ AI สร้างภายใต้ time pressure มักเลือกใช้ `!` บ่อยกว่าที่ human reviewer จะยอมรับมาก — เป็นวิธีที่เร็วที่สุดที่จะทำให้เส้นหยักสีแดงหายไป และมัน compile ผ่านด้วย ต้นทุนจะโผล่มาทีหลัง ใน production crash log ไม่ใช่ใน editor

```dart
// AI-generated: "get the user's display name"
String displayName(Map<String, dynamic> json) {
  return json['profile']['displayName'].toString();
  // Three unguarded assumptions stacked: 'profile' exists, it's a Map,
  // and 'displayName' exists on it. Any missing key throws a real,
  // unhandled runtime error — not the friendly Null check operator
  // message, but a TypeError on the failed cast/access chain.
}
```

ก่อนเชื่อ code แบบนี้ ให้เช็ค:

- ทุก `!` — คุณชี้ `if`/`??`/การ validate ก่อนหน้าที่พิสูจน์ non-null ตรงนี้ได้จริงไหม? ถ้าไม่ได้ นี่คือ anti-pattern ที่พิสูจน์แล้วข้างบน ห่างจาก crash จริงแค่ API response ที่ผิดปกติหนึ่งครั้ง
- การเข้าถึง `map['a']['b']['c']` แบบ chain บน `dynamic`/`Map<String, dynamic>` JSON — แต่ละ `[]` คืน `null` ได้ และไม่มี compiler check เลยบน `dynamic` ควรใช้ typed model ที่มี `fromJson` validate ที่ boundary ครั้งเดียวแทน
- การอ่าน field ทันทีหลังเช็ค null บน `this.field` (หรือ `widget.field`) แทนที่จะ copy ไปเป็น local ก่อน — พิสูจน์แล้วข้างบนว่าเป็น analyzer error จริง ไม่ใช่แค่เรื่อง style เว้นแต่ field นั้นจะ private และ final (ข้อยกเว้นของ Dart 3.2 ที่พิสูจน์แล้วข้างบนเช่นกัน)
- function ที่รับ `List<String>?` ทั้งที่จริง ๆ ตั้งใจสื่อว่า "มี list เสมอ แต่บาง entry อาจขาด" (`List<String?>`) — สองแบบใช้แทนกันไม่ได้ พิสูจน์แล้วข้างบน

</SpotTheBug>

## Mental Model

Null safety ไม่ใช่ "ใส่ `?` ทุกที่จนกว่าจะ compile ผ่าน" — มันคือระบบคำสัญญาที่ compiler เช็คให้คุณ ทุก `?` คือค่าที่คุณยอมรับว่าอาจไม่มีอยู่จริง; ทุก type ที่ non-nullable คือคำสัญญา (จากคุณหรือ API ที่คุณเรียก) ว่ามันจะมีอยู่เสมอ `!` คือการขึ้นเงินสัญญานั้นโดยไม่มีหลักฐาน — การเดิมพัน flow analysis คือ compiler *พิสูจน์คำสัญญาให้เอง* สำหรับกรณีแคบและปลอดภัยของ local variable ที่พิสูจน์ได้ว่าเปลี่ยนแปลงกลางคันระหว่างเช็คกับใช้ไม่ได้ — นี่คือเหตุผลตรงที่มันมักไม่ครอบคลุมถึง field และเป็นเหตุผลตรงที่ Dart 3.2 ขยายมันไปถึง private `final` field ได้ เพราะพิสูจน์ได้ว่า field พวกนั้น*ก็*เปลี่ยนแปลงกลางคันไม่ได้เหมือนกัน

## Trade-offs

| ทางเลือก | ประโยชน์ | ต้นทุน |
| --- | --- | --- |
| `!` | พิมพ์น้อยที่สุด compile ผ่านทันที | พิสูจน์แล้วข้างบน: `TypeError` crash จริงแบบไม่มีการจัดการทันทีที่การเดิมพันผิด — ไม่มี safety net ของ compiler เหลืออยู่เลย |
| `?.` / `??` | ไม่ throw เลย ลดระดับอย่างนุ่มนวล | อาจซ่อน bug ที่*ควร*ดังไว้ (ค่าที่เป็น null ทั้งที่ไม่ควรเป็นเลย) ได้เงียบ ๆ |
| copy field มาเป็น local เพื่อ promote | ใช้ได้กับ field ทุกตัวเสมอ | เพิ่มบรรทัด เพิ่มตัวแปรที่ต้องซิงค์กัน — การ promote private-final-field (Dart 3.2) ตัดต้นทุนนี้ออกสำหรับ field ส่วนที่เข้าเงื่อนไข |
| `late` | เลื่อนการ initialize ออกไปหลังประกาศ แต่ยังคง non-nullable ทาง static ทุกที่ที่ใช้ | ลดการันตีเหลือแค่ runtime — อ่านเร็วเกินไปจะ throw `LateInitializationError` พิสูจน์แล้วในบท lifecycle |
| Null-check pattern (`var x?`) | match แบบมีเงื่อนไข ไม่ throw ในฝั่งที่ไม่ match | ใช้ได้แค่ใน pattern context (`switch`, `if-case`) เท่านั้น — ไม่ใช่ของแทน `!` ได้ทุกที่ |

## Common Misconceptions

- **"Dart ยังมีโหมด unsound/legacy null-safety ที่ opt-in ได้อยู่"** พิสูจน์แล้วว่าผิดข้างบนด้วย quote ตรงจาก dart.dev: sound null safety ถูกบังคับแบบไม่มีเงื่อนไขตั้งแต่ Dart 3 (พฤษภาคม 2023) — ไม่มี opt-out ใน Dart 3.13 ของคอร์สนี้
- **"ถ้าเช็ค `if (this.field != null)` field จะปลอดภัยใช้ต่อทันที เหมือน local"** พิสูจน์แล้วว่าผิดข้างบนด้วย error จริง `unchecked_use_of_nullable_value` — จริงแค่ตั้งแต่ Dart 3.2 และแค่สำหรับ field แบบ private, `final` ที่ไม่มี declaration ขัดแย้งกัน field แบบ public หรือ mutable ไม่ถูก promote เลย
- **"`List<String?>` กับ `List<String>?` ความหมายเหมือนกันโดยพื้นฐาน"** พิสูจน์แล้วว่าผิดข้างบน: แบบหนึ่งคือ list ที่มีอยู่เสมอแต่อาจมี entry เป็น null; อีกแบบตัว list เองอาจเป็น null ได้แต่ไม่มี entry เป็น null เลย — `countNulls` กับ `lengthOrZero` ข้างบนมี signature ที่ต่างกันจริง ใช้แทนกันไม่ได้
- **"argument `required` ที่ขาดไปคือ runtime crash แบบ null-pointer เหมือน `!`"** พิสูจน์แล้วว่าผิดข้างบน: มันเป็น **compile-time** error จริงทันที (`missing_required_argument`) — Dart ไม่มีทางให้โปรแกรมรันโดยขาด argument เลย ต่างจาก `!` ที่ความล้มเหลวถูกเลื่อนไปจนกว่า code path นั้นจะรันจริง
