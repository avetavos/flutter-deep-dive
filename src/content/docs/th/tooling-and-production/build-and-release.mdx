## build mode สามแบบ

Flutter compile code เดียวกันสามแบบต่างกันขึ้นกับสิ่งที่คุณต้องการ:

<Mermaid title="build mode สามแบบและ compilation ของตัวเอง" code={modeDiagram} />

export const modeDiagram = `flowchart LR
  debug["debug\nJIT · hot reload · asserts on\n(slow, dev only)"]
  profile["profile\nAOT · perf tools on\n(measure real speed)"]
  release["release\nAOT · asserts off · optimized\n(ship this)"]`;

- **Debug** — JIT-compiled, hot reload, assertion เปิด, service extension ใช้ได้ ช้าและใหญ่ สำหรับ develop เท่านั้น
- **Profile** — AOT-compiled เหมือน release แต่ยังมี performance tooling ติดอยู่ นี่คือที่ที่คุณวัดความเร็วจริงและตามล่า jank (อย่า profile ใน debug — ตัวเลขไม่มีความหมาย)
- **Release** — AOT-compiled, assertion ถูกตัด, debugging ปิด, tree-shaken และ optimize นี่คือสิ่งที่ user ได้รับ

## JIT vs AOT

การแยก debug/release จริง ๆ แล้วคือการแยก compilation:

- **JIT** (Just-In-Time) ใช้ใน debug compile Dart ตอนที่รัน — นั่นคือสิ่งที่ทำให้ hot reload เป็นไปได้ (swap code ใหม่เข้าไปได้ทันที)
- **AOT** (Ahead-Of-Time) ใช้ใน profile และ release compile Dart เป็น native machine code ก่อนที่แอปจะ ship ผลลัพธ์คือ startup ที่เร็วและ performance ที่คาดเดาได้ แลกกับการไม่มี hot reload

**Tree-shaking** เกิดใน AOT build: code ที่ไม่ถูกใช้ (และที่สำคัญ icon glyph ที่ไม่ถูก reference) ถูกตัดออกเพื่อให้ binary เล็ก

## build แต่ละ platform

```bash
flutter build apk --release          # Android APK (direct install/testing)
flutter build appbundle --release    # Android App Bundle (Play Store)
flutter build ipa --release          # iOS archive (App Store)
flutter build web --release          # web bundle
```

แต่ละ target สร้าง artifact คนละแบบจาก Dart source เดียวกัน — framework abstract platform ออกไป ส่วน build step ทำให้ออกมาเป็นจริงบนแต่ละ platform

## Flavors: แอปเดียว หลาย environment

**Flavor** (Android) / **scheme** (iOS) ให้ codebase เดียวสร้าง build แบบ dev, staging และ production ด้วย config ต่างกัน — API endpoint, app ID, icon — โดยไม่ต้องแตก branch ของ code

```bash
flutter run --flavor dev --dart-define=API_URL=https://dev.api.example.com
flutter build apk --flavor prod --dart-define=API_URL=https://api.example.com
```

`--dart-define` ส่ง compile-time constant ที่ code อ่านผ่าน `String.fromEnvironment` — วิธีที่สะอาดในการ inject ค่าแต่ละ environment โดยไม่ commit secret เข้า source

## สิ่งที่แต่ละ platform คาดหวังในปี 2026

คำสั่ง build ยังเหมือนเดิม แต่สิ่งที่มันสร้างข้างล่างเปลี่ยนไปแล้ว มี 4 เรื่องที่สำคัญเวลา ship แอป Flutter 3.47:

- **Impeller เป็น renderer default ทุก platform แล้ว** มันเป็น default บน iOS และ Android มาก่อนหน้านี้ ส่วน Flutter 3.47 ทำให้เป็น default บน macOS, Windows และ Linux ด้วย Impeller compile shader ตอน build แทนที่จะ compile ตอนใช้ครั้งแรก จึงกำจัดปัญหาคลาสสิก "animation กระตุกตอนเล่นรอบแรก" ที่เกิดจากการ compile shader ตอน runtime ของ Skia
- **ขั้นต่ำฝั่ง Apple ขยับขึ้น** Flutter 3.47 ต้องใช้ **iOS 15** (เดิม 13) และ **macOS 12** (เดิม 10.15) เช็กบรรทัด platform ใน `Podfile` และ deployment target บน App Store ก่อน upgrade
- **Swift Package Manager คือทางข้างหน้า** CocoaPods อยู่ใน maintenance mode แล้ว และ plugin iOS ยอดนิยมส่วนใหญ่ migrate ไปแล้ว โปรเจกต์ใหม่ควรใช้ SwiftPM ส่วนของเดิมยังทำงานได้ แต่ plugin ที่ยังไม่ migrate จะกลายเป็นตัวติดขัดในที่สุด
- **โปรเจกต์ Android ใช้ Kotlin ที่มากับ Flutter** ตั้งแต่ 3.44 Kotlin toolchain มาพร้อม Flutter แทนที่จะประกาศแยกในแต่ละโปรเจกต์ โปรเจกต์ Android ที่ generate ออกมาจึงไม่ต้อง pin เวอร์ชัน Kotlin plugin ของตัวเองอีก

มีการเปลี่ยนแปลงก้อนใหญ่กว่านั้นที่กำลังเดินอยู่: **Material และ Cupertino กำลังย้ายออกจาก framework ไปเป็น package แยก `material_ui` และ `cupertino_ui`** (ทั้งคู่อยู่ที่ 1.0 บน pub.dev) ตอนนี้ยังเป็นแบบ opt-in โดยมีแผนจะ deprecate ตัวที่อยู่ใน framework อย่างเป็นทางการ และมี fix สำหรับ migrate ให้:

```bash
dart fix --apply --code=migrate_design_widgets
```

ถ้ายังไม่ทำตอนนี้ก็ไม่มีอะไรพัง — แต่โปรเจกต์ใหม่ที่อยากให้ design system มีเวอร์ชันแยกจาก SDK สามารถเริ่มใช้ package พวกนี้ได้แล้ว

<Callout title="สรุปหนึ่งบรรทัด">

</Callout>
