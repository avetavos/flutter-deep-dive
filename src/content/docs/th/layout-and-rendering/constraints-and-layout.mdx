## กฎเดียว

ถ้าคุณจำอะไรเกี่ยวกับ Flutter layout ไม่ได้เลยนอกจากอย่างเดียว จำอันนี้:

> **Constraints ไหลลง Size ไหลขึ้น Parent กำหนดตำแหน่ง**

Layout คือ pass เดียวที่เดินลงไปใน tree แล้วเดินกลับขึ้นมา parent ส่ง **constraints** ให้แต่ละ child — `BoxConstraints` ที่มี min/max width และ height child แต่ละตัวต้องเลือก **size** ที่สอดคล้องกับ constraints นั้น แล้วรายงานกลับขึ้นไป parent จึง **จัดตำแหน่ง** child ไว้ภายในตัวเอง

<Mermaid title="Layout pass เดียว: ลงด้วย constraints ขึ้นด้วย size" code={ruleDiagram} />

export const ruleDiagram = `flowchart TB
  parent["Parent widget"] -->|"constraints:\nmin/max w, min/max h"| child["Child widget"]
  child -->|"chosen size\n(within constraints)"| parent
  parent -->|"offset\n(where to place child)"| placed["Child placed"]`;

นั่นคือ algorithm ทั้งหมด ที่เหลือคือรายละเอียดว่า widget แต่ละตัว *เลือก* size ของมันอย่างไร และ *ส่ง* constraint อะไรต่อลงไป

## พิสูจน์แล้ว: สามส่วนของกฎ อ่านตรงจาก render tree

`WidgetTester.getSize` และ `getTopLeft` อ่านผล layout จริงที่เกิดขึ้น — ไม่ใช่คำอธิบายของมัน — ดังนั้นกฎข้างบนตรวจสอบได้ตรง ๆ

```dart
// lib/constraints_rule.dart
import 'package:flutter/material.dart';

class CenteredBox extends StatelessWidget {
  const CenteredBox({super.key});
  @override
  Widget build(BuildContext context) {
    return const SizedBox(
      width: 200,
      height: 200,
      child: Center(
        child: SizedBox(width: 50, height: 50, key: ValueKey('child')),
      ),
    );
  }
}
```

```dart
// test/constraints_rule_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/constraints_rule.dart';

void main() {
  testWidgets('constraints go down, sizes go up, the parent sets position', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: Center(child: CenteredBox()))));

    final childFinder = find.byKey(const ValueKey('child'));
    final outerBoxFinder = find.byType(SizedBox).first; // the 200x200 outer box

    // SIZES GO UP: the child chose 50x50 — its OWN size — even though the
    // outer SizedBox is 200x200 and Center gives it loose constraints up to that.
    expect(tester.getSize(childFinder), const Size(50, 50));

    // THE PARENT SETS POSITION: Center placed the 50x50 child in the middle
    // of its own 200x200 box — (200-50)/2 = 75 on each axis.
    final childTopLeft = tester.getTopLeft(childFinder);
    final outerTopLeft = tester.getTopLeft(outerBoxFinder);
    expect(childTopLeft - outerTopLeft, const Offset(75, 75));
  });
}
```

```text
00:00 +1: All tests passed!
```

อ่านตัวอย่างเดียวกันจากบนลงล่าง: `Center` ได้รับ constraint แบบ tight `200x200` จาก `SizedBox` ด้านนอก มันส่ง constraint แบบ **loose** ลงไป — "คุณเป็นอะไรก็ได้ตั้งแต่ 0 ถึง 200x200" `SizedBox` ด้านในต้องการเป๊ะ `50x50` ซึ่งพอดี จึงมีขนาด `50x50` และรายงานกลับขึ้นไป — พิสูจน์ตรง ๆ ด้วย `getSize` `Center` มีขนาด `200x200` (size ของมันเองมาจาก tight constraint ของ parent มันเอง) และจัดตำแหน่ง child `50x50` ไว้ตรงกลาง — พิสูจน์ตรง ๆ ด้วย offset `75,75` เปลี่ยน `Center` เป็น `Align`, `Padding`, หรือ `SizedBox` แล้วมีแค่ constraint ที่ส่งลงไป (ขั้นตอนที่ 2) เปลี่ยน — กฎเองไม่เคยเปลี่ยน

## Constraint แบบ tight เทียบ loose

constraint เป็น **tight** เมื่อ min เท่ากับ max (widget ต้องมีขนาดเป๊ะนั้น) และ **loose** เมื่อ min เป็น 0 (widget เป็นอะไรก็ได้จนถึง max)

```dart
// SizedBox imposes a tight constraint — the child MUST be 50x50.
SizedBox(width: 50, height: 50, child: coloredBox)

// Center imposes a loose constraint — the child may be up to the parent size.
Center(child: coloredBox)
```

นี่คือเหตุผลที่ widget เดียวกันมีพฤติกรรมต่างกันใน parent ต่างกัน: `Container(color: Colors.red)` ที่ไม่มี size กำหนด fill parent ภายใต้ tight constraint แต่หดเหลือ 0 ภายใต้ loose constraint (กฎนี้เป๊ะ พิสูจน์ด้วย `getSize` test จริง อยู่ใน [บทเรียน Core Layout Widgets](/flutter/th/layout-and-rendering/core-layout-widgets/)) widget ไม่ได้เปลี่ยน — constraint ต่างหากที่เปลี่ยน

## พิสูจน์แล้ว: ข้อความจริงของ `RenderFlex overflowed`

ให้ `Row` มีเนื้อหามากกว่าความกว้างที่มีให้ มันไม่หดเนื้อหาลง — มัน overflow และ Flutter รายงานว่ามากเท่าไรเป๊ะ:

```dart
// lib/overflow_demo.dart
import 'package:flutter/material.dart';

class OverflowRow extends StatelessWidget {
  const OverflowRow({super.key});
  @override
  Widget build(BuildContext context) {
    // Two 300-wide boxes in a Row on a 400-wide screen — 200px too wide.
    return const Row(
      children: [
        SizedBox(width: 300, height: 50),
        SizedBox(width: 300, height: 50),
      ],
    );
  }
}
```

```dart
// test/overflow_demo_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/overflow_demo.dart';

void main() {
  testWidgets('a Row wider than its available space throws the real RenderFlex overflow error', (tester) async {
    tester.view.physicalSize = const Size(400, 800);
    tester.view.devicePixelRatio = 1.0;
    addTearDown(tester.view.reset);

    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: OverflowRow())));

    final error = tester.takeException();
    expect(error, isNotNull);
    expect(error.toString(), contains('A RenderFlex overflowed by 200 pixels on the right.'));
  });
}
```

## พิสูจน์แล้ว: การ crash จริงของ unbounded-height — และวิธีแก้จริงสามแบบ

widget บางตัวส่ง constraint แบบ **unbounded** — max เป็น infinity — หมายถึง "คุณใหญ่แค่ไหนก็ได้" `Viewport` ของ scrollable มี bound ใน axis *ขวาง* แต่ต้องรู้ขอบเขต *ของตัวเอง* ใน scroll axis จาก parent — และ `Column` ธรรมดาที่ไม่ใช่ flex ส่ง constraint แบบ **unbounded** ใน main axis ให้ non-flex children ของมัน (เพื่อให้ child แต่ละตัวรายงาน size ตามธรรมชาติของตัวเองได้) ใส่ `ListView` ตรง ๆ ใน `Column` (ไม่ห่อด้วย `Expanded`) แล้ว viewport จะไม่สามารถกำหนดได้ว่ามันควรสูงแค่ไหน:

```dart
// lib/unbounded_height.dart
import 'package:flutter/material.dart';

class UnboundedColumn extends StatelessWidget {
  const UnboundedColumn({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const Text('header'),
        // BUG: a bare ListView as a non-flex child of a Column — the
        // Column gives it unbounded height, and a viewport cannot lay
        // itself out with an infinite extent.
        ListView(
          children: const [
            SizedBox(height: 50, child: Text('a')),
            SizedBox(height: 50, child: Text('b')),
          ],
        ),
      ],
    );
  }
}
```

```dart
// test/unbounded_height_test.dart

import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/unbounded_height.dart';

void main() {

    // This particular assertion fires repeatedly during one failed layout
    // attempt, so tester.takeException() (single-exception only) is not
    // enough here — capture the first report directly via FlutterError.onError.
    FlutterErrorDetails? captured;
    final original = FlutterError.onError;
    FlutterError.onError = (details) => captured ??= details;
    addTearDown(() => FlutterError.onError = original);

    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: UnboundedColumn())));

    expect(captured, isNotNull);
    expect(captured!.exception.toString(), contains('Vertical viewport was given unbounded height.'));
  });
}
```

เวอร์ชันที่พบซ้ำ ๆ (แต่ผิด) ของกับดักนี้เอา `Column` ไปใส่ **ใน** children ของ `ListView` แทนที่จะเป็นทางกลับกัน ทดสอบตรง ๆ: `ListView(children: [Column(children: [Text('a'), Text('b')])])` **ไม่** throw — item ของ `ListView` ได้รับ unbounded height เพื่อให้แต่ละตัวรายงาน size ตามธรรมชาติของตัวเองได้ และ `Column` ที่ได้รับ max height ที่ unbounded เข้ามา จะ fallback ไปมีขนาดเท่ากับผลรวมของ children แทนที่จะพยายาม "fill" พื้นที่ที่เป็นอนันต์ crash จริงต้องการให้ *scrollable* (`ListView`/viewport) เป็นตัวที่ได้รับ unbounded height จาก slot ที่ไม่ใช่ flex — คือ `ListView` เปล่า ๆ เป็น child ตรง ๆ ที่ไม่ใช่ `Expanded` ของ `Column` พิสูจน์แล้วข้างบน ถ้าคุณเคยเห็นตัวอย่างนี้ในทิศทางตรงกันข้าม มันกำลังสาธิตสิ่งที่ไม่ error จริง ๆ
</Callout>

วิธีแก้ทั้งสามข้างล่างแก้ได้จริง — ยืนยันด้วยการ pump แต่ละตัวและ assert `tester.takeException()` เป็น `null`:

```dart
// lib/unbounded_height_fixes.dart
import 'package:flutter/material.dart';

/// Fix 1: Expanded gives the ListView a bounded, finite height — whatever
/// space is left in the Column after its other children.
class FixExpanded extends StatelessWidget {
  const FixExpanded({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const Text('header'),
      Expanded(
        child: ListView(children: const [SizedBox(height: 50), SizedBox(height: 50)]),
      ),
    ]);
  }
}

/// Fix 2: shrinkWrap makes the ListView size itself to its CONTENT instead
/// of asking for the viewport's full scroll extent — but it builds every
/// item up front, losing laziness (see the Slivers & Scrolling lesson).
class FixShrinkWrap extends StatelessWidget {
  const FixShrinkWrap({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const Text('header'),
      ListView(
        shrinkWrap: true,
        children: const [SizedBox(height: 50), SizedBox(height: 50)],
      ),
    ]);
  }
}

/// Fix 3: SizedBox gives the ListView an explicit, finite, tight height.
class FixSizedBox extends StatelessWidget {
  const FixSizedBox({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const Text('header'),
      SizedBox(
        height: 200,
        child: ListView(children: const [SizedBox(height: 50), SizedBox(height: 50)]),
      ),
    ]);
  }
}
```

```dart

    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: FixSizedBox())));

  });
}
```

## พิสูจน์แล้ว: `IntrinsicHeight` มีต้นทุนจริงเป็น measurement pass เพิ่ม

`IntrinsicHeight` กำหนด size ของ child ให้เท่ากับความสูง *intrinsic* (ตามธรรมชาติ) ของ child เอง แม้จะอยู่ใน context อย่าง `Row` ที่ปกติไม่บอกมันแบบนั้น การจะทำแบบนี้ได้ มันต้องถาม child ว่า "คุณอยากสูงแค่ไหน" (intrinsic-dimension query) **ก่อน** layout pass จริงที่กำหนด size ของมันจริง ๆ — พิสูจน์ตรง ๆ ด้วยการ instrument การเรียกทั้งสองแยกกันบน `RenderBox` ที่กำหนดเอง:

```dart
// lib/intrinsic_height_cost.dart
import 'package:flutter/material.dart';

int probeLayoutCount = 0;
int probeIntrinsicCount = 0;

class LayoutProbe extends LeafRenderObjectWidget {
  const LayoutProbe({super.key, required this.height});
  final double height;

  @override
  RenderObject createRenderObject(BuildContext context) => _RenderLayoutProbe(height);

  @override
  void updateRenderObject(BuildContext context, RenderObject renderObject) {
    (renderObject as _RenderLayoutProbe).probeHeight = height;
  }
}

class _RenderLayoutProbe extends RenderBox {
  _RenderLayoutProbe(this._height);
  double _height;
  set probeHeight(double v) => _height = v;

  @override
  double computeMinIntrinsicHeight(double width) {
    probeIntrinsicCount++;
    return _height;
  }

  @override
  double computeMaxIntrinsicHeight(double width) {
    probeIntrinsicCount++;
    return _height;
  }

  @override
  void performLayout() {
    probeLayoutCount++;
    final w = constraints.maxWidth.isFinite ? constraints.maxWidth : 50.0;
    size = constraints.constrain(Size(w, _height));
  }
}
```

```dart
// test/intrinsic_height_cost_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/intrinsic_height_cost.dart';

void main() {
  testWidgets('without IntrinsicHeight: only the real layout pass runs', (tester) async {
    probeLayoutCount = 0;
    probeIntrinsicCount = 0;
    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: LayoutProbe(height: 40))));

    expect(probeLayoutCount, 1);
    expect(probeIntrinsicCount, 0, reason: 'nothing ever asked for this widget\'s intrinsic height');
  });

  testWidgets('with IntrinsicHeight: an extra intrinsic-dimension query happens first', (tester) async {
    probeLayoutCount = 0;
    probeIntrinsicCount = 0;
    await tester.pumpWidget(
      const MaterialApp(home: Scaffold(body: IntrinsicHeight(child: LayoutProbe(height: 40)))),
    );

    expect(probeLayoutCount, 1, reason: 'the real layout pass still only runs once');
    expect(probeIntrinsicCount, greaterThan(0), reason: 'IntrinsicHeight queried the child\'s intrinsic height BEFORE laying it out — a real, extra measurement');
  });
}
```

`probeIntrinsicCount` ค้างที่ `0` สำหรับกรณีธรรมดา และกระโดดสำหรับกรณี `IntrinsicHeight` — เป็น query เพิ่มจริงที่วัดได้ ไม่ใช่การเดา ใน tree ที่ลึก intrinsic query นั้นวนซ้ำผ่านทุก descendant นั่นคือเหตุผลที่ Flutter docs อธิบาย `IntrinsicHeight`/`IntrinsicWidth` ว่า "expensive" และควรหลีกเลี่ยงใน hot path (เช่น ใน scrolling list) — ใช้มันเมื่อคุณต้องการให้ size ของ child ตัวหนึ่งตรงกับความสูงตามธรรมชาติของ sibling จริง ๆ เท่านั้น (กรณีตำราเล่ม: `Column` สองตัวที่มีความสูงตามธรรมชาติไม่เท่ากันใน `Row` เดียวกัน ทั้งคู่ถูก stretch ให้เท่ากับตัวที่สูงกว่า)

## `ConstrainedBox`, `UnconstrainedBox`, และพิสูจน์แล้ว: `OverflowBox` ทำลาย flow ลงจริง

- **`ConstrainedBox`** เพิ่ม constraint *เพิ่มเติม* บนสิ่งที่มันได้รับ — มันทำให้ constraint แน่นขึ้นได้เท่านั้น ทำให้หลวมกว่าที่ parent ของมันเองกำหนดไว้แล้วไม่ได้
- **`UnconstrainedBox`** ให้ child ของมันมีขนาดตัวเองราวกับไม่มี constraint (ละเลย constraint ที่เข้ามาเพื่อจุดประสงค์การกำหนดขนาด) แล้ว align มันภายในพื้นที่ที่ได้รับจริง — มีประโยชน์สำหรับให้ child ละเลย tight constraint ที่มันไม่พอดีชั่วคราว โดยแลกกับความเสี่ยง overflow ถ้า child ใหญ่กว่าพื้นที่ที่มีจริง
- **`OverflowBox`** เป็นตัวทำลาย constraint ที่ตั้งใจที่สุดในสามตัว: มันรายงาน size **ของตัวเอง** ให้ parent ตาม constraint ที่ *มันเอง* ได้รับ แต่ส่งให้ **child** ของมันเป็น constraint ชุด *อื่น* ที่ระบุไว้ชัดเจน — ซึ่งหลวมกว่า (หรือแน่นกว่า) สิ่งที่ `OverflowBox` เองได้รับ ทำให้ child มีขนาดใหญ่กว่ากล่องของ parent ของตัวเองได้

```dart
// lib/overflow_box_demo.dart
import 'package:flutter/material.dart';

class OverflowDemo extends StatelessWidget {
  const OverflowDemo({super.key});
  @override
  Widget build(BuildContext context) {
    return SizedBox(
      width: 100,
      height: 100,
      child: OverflowBox(
        minWidth: 0,
        maxWidth: 200,
        minHeight: 0,
        maxHeight: 200,
        child: SizedBox(width: 150, height: 150, key: const ValueKey('overflowChild')),
      ),
    );
  }
}
```

```dart
// test/overflow_box_demo_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/overflow_box_demo.dart';

void main() {
  testWidgets('OverflowBox reports its own constrained size but lets its child exceed it', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: OverflowDemo())));

    // OverflowBox itself still respects the 100x100 its own parent gave it.
    expect(tester.getSize(find.byType(OverflowBox)), const Size(100, 100));

    // But its CHILD is laid out with the explicit, looser constraints
    // OverflowBox specified (up to 200x200) — genuinely bigger than
    // OverflowBox's own reported size.
    expect(tester.getSize(find.byKey(const ValueKey('overflowChild'))), const Size(150, 150));
  });
}
```

นี่คือข้อยกเว้นเดียวที่ตั้งใจและได้รับการรับรองของ "constraints ไหลลง size ไหลขึ้น" ในฐานะความสัมพันธ์ nesting ที่เข้มงวด — size ที่ `OverflowBox` รายงาน (`100x100` ต่อ parent ของมันเอง) และ size จริงของ child ของมัน (`150x150`) ได้รับอนุญาตให้ไม่ตรงกัน ซึ่งเป็นเหตุผลที่ผล visual overflow ออกนอกกล่องของมันเอง (ปกติตั้งใจ สำหรับ badge หรือของตกแต่งที่ตั้งใจให้ล้นออกนอกขอบเขตทาง logic) — และเป็นเหตุผลที่ `OverflowBox` ควรถูกเลือกใช้โดยตั้งใจ ไม่ใช่ใช้โดยบังเอิญ

## `LayoutBuilder` สำหรับ breakpoint

`LayoutBuilder` (พิสูจน์อย่างลึกซึ้งรวมถึงความต่างของขอบเขต rebuild จาก `MediaQuery.of` ใน [บทเรียน build and BuildContext](/flutter/th/widgets/build-and-buildcontext/)) คือเครื่องมือมาตรฐานสำหรับ react กับ *พื้นที่จริงที่ widget นี้ได้รับ* แทนที่จะเป็นทั้งหน้าจอ ซึ่งเป็นสิ่งที่ breakpoint จริงต้องการ เพราะ widget อาจอยู่ใน sidebar ความกว้างคงที่หรือ split view ที่ "ความกว้างหน้าจอ" เป็นตัวเลขที่ผิดโดยสิ้นเชิง:

```dart
LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth < 600) {
      return const NarrowLayout();
    }
    return const WideLayout();
  },
)
```

<Callout title="สรุปหนึ่งบรรทัด">
Layout คือ pass เดียว: **constraints ไหลลง size ไหลขึ้น parent กำหนดตำแหน่ง** — พิสูจน์แล้วข้างบนตรง ๆ ด้วย `getSize`/`getTopLeft` การ overflow `Row`/`Column` throw error จริงที่มีถ้อยคำแม่นยำ `RenderFlex overflowed by N pixels` — พิสูจน์แล้วข้างบน ตรงกับเลขคณิต overflow เป๊ะ `ListView`/viewport เปล่า ๆ เป็น non-flex child ของ `Column` throw error จริง `Vertical viewport was given unbounded height` (ไม่ใช่ทางกลับกัน — `Column` ใน children ของ `ListView` ไม่ crash แก้ไขแล้วข้างบน) — แก้ด้วย `Expanded`, `shrinkWrap: true`, หรือ `SizedBox` ที่ชัดเจน ยืนยันทั้งสามทำงานจริง `IntrinsicHeight` มีต้นทุนจริงเป็น intrinsic-dimension query เพิ่มก่อน layout pass จริง — พิสูจน์ด้วย call counter `ConstrainedBox`/`UnconstrainedBox` ทำงานภายใน flow constraint ปกติ; `OverflowBox` — พิสูจน์แล้วข้างบน — ทำลายมันโดยตั้งใจ ทำให้ child มีขนาดใหญ่กว่าสิ่งที่ parent ของมันเองรายงานขึ้นไปได้
</Callout>

## Mental Model

`BoxConstraints` คือ **ใบสั่งงาน** ไม่ใช่คำแนะนำ: "สร้างอะไรบางอย่างระหว่าง minimum นี้กับ maximum นี้ ในทั้งสองมิติ" ทุก widget คือผู้รับเหมาที่ต้องส่งมอบ size ที่สอดคล้องกับใบสั่งงานที่ได้รับ — ไม่มี widget ตัวไหนได้รับสิทธิ์ตัดสินใจฝ่ายเดียวว่า "ฉันจะใหญ่กว่านี้แหละ ขอบใจ" ซึ่งเป็นเหตุผลเป๊ะที่ overflow คือ *error* ไม่ใช่การ resize เงียบ ๆ parent ที่ได้รับ size สำเร็จรูปกลับมาจาก child แล้วเป็นคนเดียวที่ตัดสินใจว่าจะวาง *ที่ไหน* — child ไม่มีสิทธิ์ออกเสียงเรื่องตำแหน่งของตัวเอง มีแค่ size ของตัวเอง `OverflowBox` คือหัวหน้าคนงานที่แอบส่งใบสั่งงานคนละใบให้ subcontractor ต่างจากที่เขียนไว้บน building permit — ถูกกฎหมาย แต่นั่นคือเหตุผลเป๊ะที่มันต้องมีชื่อที่บอกแบบนั้น

## Trade-offs

| ทางเลือก | ข้อดี | ต้นทุน |
| --- | --- | --- |
| `Expanded` รอบ scrollable ใน `Column` | ถูกต้อง รักษา laziness (พิสูจน์แล้วว่าไม่ crash) | scrollable กินพื้นที่ที่เหลือทั้งหมด — ไม่เหมาะถ้าต้องการให้มันมีขนาดตามเนื้อหา |
| `shrinkWrap: true` | มีขนาดตามเนื้อหาแทนที่จะ fill | build ทุก item ล่วงหน้า — ต้นทุนพิสูจน์แล้วใน [บทเรียน Slivers & Scrolling](/flutter/th/layout-and-rendering/slivers-and-scrolling/); เลือกผิดสำหรับ list ยาว |
| ความสูง `SizedBox` ที่ชัดเจน | คาดเดาได้ ง่าย ไม่มี trade-off เรื่อง laziness | ต้องรู้/ตัดสินใจความสูงล่วงหน้า — ไม่ responsive กับเนื้อหา |
| `IntrinsicHeight`/`IntrinsicWidth` | ทำให้ sibling มีขนาดตามธรรมชาติที่ตรงกัน | measurement pass เพิ่มจริงที่พิสูจน์แล้ว วนซ้ำผ่าน subtree — หลีกเลี่ยงใน hot/scrolling path |
| `OverflowBox` | ให้ child ล้นออกนอกขอบเขตของ logical parent โดยตั้งใจ | เป็นแค่ visual — hit-testing และ layout ของ SIBLING ไม่ได้รับผลกระทบจากพื้นที่ที่ล้น; ใช้ผิดง่ายสำหรับ layout จริง (แทนที่จะเป็น decoration) |

## Common Misconceptions

- **"widget ตัดสินใจใหญ่กว่า constraint ที่กำหนดได้เอง"** พิสูจน์แล้วว่าผิดข้างบน: `RenderFlex overflowed` คือ hard error เพราะ Flutter บังคับใช้ contract ของ constraint เป๊ะ — `Row`/`Column` จะไม่ขยายตัวเงียบ ๆ
- **"Column ใน ListView คือสาเหตุของ unbounded-height crash"** พิสูจน์แล้วข้างบน (และแก้ไขเทียบกับตัวอย่างผิดที่พบซ้ำ ๆ): ทิศทางนั้นไม่ crash crash จริงต้องการ `ListView` เปล่า ๆ ที่ไม่ใช่ `Expanded` เป็น child ของ `Column`
- **"IntrinsicHeight แทบจะฟรี — แค่ widget เพิ่มขึ้นหนึ่งตัวใน tree"** พิสูจน์แล้วข้างบนด้วย call counter จริง: มันทำ query แยกที่เพิ่มขึ้นจริง (`computeMaxIntrinsicHeight`/`computeMinIntrinsicHeight`) ก่อน layout pass ปกติ ไม่ใช่แค่ "layout เพิ่มอีกหนึ่งครั้ง"
- **"OverflowBox/UnconstrainedBox ละเมิด constraint model ของ Flutter — ต้องเป็นบั๊กแน่ ๆ เมื่อเห็น"** พิสูจน์แล้วข้างบนว่าเป็น escape hatch ที่ตั้งใจและได้รับการรับรอง: size ที่ `OverflowBox` รายงานและ size จริงของ child ของมัน ได้รับอนุญาตให้ไม่ตรงกัน โดยการออกแบบ สำหรับกรณี "decoration ที่ล้นออกนอกกล่อง" เป๊ะ

ก่อนเชื่อโค้ด layout ที่ generate มา ให้เช็ค:

- scrollable (`ListView`, `GridView`, `SingleChildScrollView`) เป็น child ตรง ๆ ของ `Column`/`Row` โดยไม่มี `Expanded`/`Flexible` ห่อไว้หรือเปล่า? นั่นคือ crash จริงที่พิสูจน์แล้วข้างบน
- `IntrinsicHeight`/`IntrinsicWidth` ถูกใช้ภายในสิ่งที่ rebuild/re-layout บ่อย (scrolling list, animation) หรือเปล่า? query เพิ่มที่พิสูจน์แล้วข้างบนจะยิ่งแย่ตรงนั้น
- `OverflowBox`/`UnconstrainedBox` ปรากฏในจุดที่เจตนาจริง ๆ คือ "ทำให้พอดี" แทนที่จะเป็น "ตั้งใจให้ล้นออกนอกกล่อง" หรือเปล่า? ถ้าเป็นแบบแรก วิธีแก้จริงมักเป็น `FittedBox` หรือทบทวน constraint ของ parent ไม่ใช่ override มัน
