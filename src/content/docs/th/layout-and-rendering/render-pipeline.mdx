## ห้า phase ต่อเฟรม

เมื่อ Flutter วาดเฟรม มันรัน pipeline ที่ตายตัว การรู้จัก phase บอกคุณว่าเวลาไปไหนและควรปรับปรุงตรงไหน

<Mermaid title="Render pipeline ต่อเฟรม" code={pipeDiagram} />

export const pipeDiagram = `flowchart LR
  build["1. Build\n(run build methods)"] --> layout["2. Layout\n(constraints down, sizes up)"]
  layout --> paint["3. Paint\n(record draw commands)"]
  paint --> composite["4. Composite\n(assemble layers)"]
  composite --> raster["5. Raster\n(GPU draws pixels)"]`;

1. **Build** — widget ที่ dirty rebuild สร้าง widget description ที่อัปเดตแล้ว
2. **Layout** — pass constraints-ไหลลง/sizes-ไหลขึ้น (พิสูจน์อย่างลึกซึ้งใน [บทเรียน Constraints & Layout](/flutter/th/layout-and-rendering/constraints-and-layout/)) คำนวณ size และ position ของ render object ทุกตัว
3. **Paint** — render object แต่ละตัวบันทึก drawing command (ยังไม่ใช่ pixel) ลงใน `Canvas`/`Picture` render object ตัวไหนได้ **layer** ของตัวเองตรงนี้ — พิสูจน์ตรง ๆ ข้างล่างด้วย `RepaintBoundary` — คือสิ่งที่ทำให้ repaint บางอันถูกในขณะที่บางอันแพง
4. **Composite** — layer ถูกประกอบเข้าเป็น scene graph สุดท้าย
5. **Raster** — GPU วาด pixel จริงจาก scene นั้น นี่คือจุดที่ **Impeller** (ข้างล่าง) เปลี่ยนสิ่งที่เกิดขึ้น

budget ตึง: เพื่อให้ได้ 60fps คุณมี **~16.6ms** ต่อเฟรม (**~8.3ms** ที่ 120Hz) Jank คือเฟรมที่พลาด budget นั้น และเกือบทุกครั้งมาจากงานมากเกินไปใน **build**, **layout**, หรือขั้น **paint/composite** ที่แพงเกินคาด (พิสูจน์ข้างล่างว่าเป็นต้นทุนจริงที่วัดได้ ไม่ใช่ความกังวลลอย ๆ)

## RenderObject ทำงานจริง

Widget เป็น *description* ที่ immutable และเบา object ที่ layout และ paint จริง ๆ คือ **RenderObject** และมันอยู่ใน tree ที่สามของสาม tree ของ Flutter:

- **Widget tree** — configuration ที่ immutable ของคุณ (rebuild บ่อย ถูก)
- **Element tree** — กาวที่ mutable ที่ถือ state และเชื่อม widget กับ render object (พิสูจน์อย่างลึกซึ้ง ด้วยการ spy `createElement`/`didUpdateWidget` ใน [บทเรียน Widgets and the Tree](/flutter/th/widgets/widgets-and-the-tree/))
- **Render tree** — `RenderObject` ที่คำนวณ layout และ paint (แพง; ถูกเก็บและ mutate ไม่ใช่ rebuild)

สำหรับกลไกเต็ม ๆ เบื้องหลังนี้ — `markNeedsLayout`, `markNeedsPaint`, และ render object ที่ dirty ถูก revisit อย่างไร — ดู [Flutter Internals: Layout and Paint](/flutter/th/flutter-internals/layout-and-paint-internals/)

## Impeller: สิ่งที่มันแทนที่จริง ๆ ที่ขั้น raster

**Impeller precompile shader ทั้งหมดและสร้าง pipeline state object (PSO) ทั้งหมดล่วงหน้า ตอน engine-build time** — นี่คือ quote ตรง ๆ จากคำอธิบายวัตถุประสงค์ของ Impeller เองที่ `docs.flutter.dev/perf/impeller`: *"Predictable performance: Impeller compiles all shaders and reflection offline at build time. It builds all pipeline state objects upfront. The engine controls caching and caches explicitly."* นี่คือสิ่งเฉพาะเจาะจงที่มันแทนที่: Skia (renderer default เดิม) compile shader **ตอน runtime** แทน ครั้งแรกที่เจอ draw operation หนึ่ง ๆ — ซึ่งเป็นสาเหตุเป๊ะของ jank คลาสสิก "รอบแรกที่รัน animation ใหม่กระตุก แล้วค่อยลื่น" เพราะการ compile shader ครั้งแรกนั้นเกิดขึ้นสด ๆ บนเฟรมที่ต้องการมันพอดี

สถานะจริงต่อ platform ณ SDK Flutter 3.47 ของคอร์สนี้:

- **iOS**: ตาม `docs.flutter.dev/perf/impeller`, *"Impeller is the **only supported** rendering engine on iOS with no ability to switch to Skia."*
- **Android**: Impeller กลายเป็น default บน device สมัยใหม่ (รองรับ Vulkan) ตั้งแต่ Flutter 3.27 — quote จาก release note ทางการ: *"Impeller is now the default rendering engine on modern Android devices... On older Android devices and devices without Vulkan support, the Skia rendering engine will still be used as before."* opt out ด้วย `flutter run --no-enable-impeller` (หรือ meta-data entry เทียบเท่าใน `AndroidManifest.xml`)
- **macOS, Windows, Linux**: Flutter 3.47 ทำให้ Impeller เป็น default ที่นี่ด้วย — [บทเรียน Build and Release](/flutter/th/tooling-and-production/build-and-release/) ของคอร์สนี้เองระบุไว้ตรง ๆ (ยืนยันกับ `docs.flutter.dev` ระหว่าง Phase 3 review ของคอร์สนี้): *"It became the default on iOS and Android earlier; Flutter 3.47 makes it the default on macOS, Windows, and Linux too."*

`--enable-impeller`/`--no-enable-impeller` คือ flag CLI จริง (ตัวเดียวกันที่ quote ใน release note ของ Flutter เองสำหรับ opt-in ช่วง preview และ opt-out วันนี้บน Android) — แต่หมายเหตุว่าบน iOS ไม่มีอะไรให้ opt out *ไปหา* เลย เพราะ Skia ไม่ได้ ship ที่นั่นอีกต่อไปแล้ว สำหรับสถาปัตยกรรม Impeller เต็ม ๆ (Aiks, Entities, pipeline การ precompile PSO จริง) ดู [Flutter Internals: Impeller and the GPU](/flutter/th/impeller-and-the-gpu/)

## พิสูจน์แล้ว: `RepaintBoundary` แยก repaint ของ subtree หนึ่งจาก sibling ของมันได้จริง

โดย default เมื่อ render object ที่ไม่ใช่ boundary ต้อง repaint Flutter ต้อง re-record `Picture` ที่แชร์กันทั้งก้อนขึ้นไปถึง repaint boundary ที่ใกล้ที่สุด — หมายความว่าทุก sibling ภายใต้ boundary เดียวกันนั้นถูกเรียก `paint()` ใหม่ด้วย แม้จะไม่ได้เปลี่ยนอะไรเลยก็ตาม การห่อ subtree ที่เปลี่ยนบ่อยด้วย `RepaintBoundary` ของตัวเองให้ layer แยกต่างหาก ดังนั้น repaint ของมันจึงไม่บังคับให้ canvas ที่เหลือของ share ถูก re-record อีกต่อไป

```dart
// lib/repaint_boundary_demo.dart
import 'package:flutter/material.dart';

int staticPaintCount = 0;
int spinnerPaintCount = 0;

class _CountingPainter extends CustomPainter {
  _CountingPainter(this.onPaint, this.color);
  final VoidCallback onPaint;
  final Color color;
  @override
  void paint(Canvas canvas, Size size) {
    onPaint();
    canvas.drawRect(Offset.zero & size, Paint()..color = color);
  }

  @override
  bool shouldRepaint(_CountingPainter oldDelegate) => color != oldDelegate.color;
}

/// Never changes on its own — a good proxy for "unrelated sibling content".
class StaticBox extends StatelessWidget {
  const StaticBox({super.key});
  @override
  Widget build(BuildContext context) {
    return CustomPaint(size: const Size(40, 40), painter: _CountingPainter(() => staticPaintCount++, Colors.blue));
  }
}

/// Repaints every time tick changes — the "animating" widget.
class SpinnerBox extends StatefulWidget {
  const SpinnerBox({super.key});
  @override
  SpinnerBoxState createState() => SpinnerBoxState();
}

class SpinnerBoxState extends State<SpinnerBox> {
  int tick = 0;
  void bump() => setState(() => tick++);
  @override
  Widget build(BuildContext context) {
    return CustomPaint(
      size: const Size(40, 40),
      painter: _CountingPainter(() => spinnerPaintCount++, Color.fromARGB(255, tick % 255, 0, 0)),
    );
  }
}

/// No RepaintBoundary around the spinner — both siblings share one canvas.
class NoBoundaryScene extends StatelessWidget {
  const NoBoundaryScene({super.key, required this.spinnerKey});
  final GlobalKey<SpinnerBoxState> spinnerKey;
  @override
  Widget build(BuildContext context) {
    return Column(children: [SpinnerBox(key: spinnerKey), const StaticBox()]);
  }
}

/// The spinner gets its OWN layer — its repaints stop leaking into StaticBox.
class WithBoundaryScene extends StatelessWidget {
  const WithBoundaryScene({super.key, required this.spinnerKey});
  final GlobalKey<SpinnerBoxState> spinnerKey;
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      RepaintBoundary(child: SpinnerBox(key: spinnerKey)),
      const StaticBox(),
    ]);
  }
}
```

```dart
// test/repaint_boundary_demo_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/repaint_boundary_demo.dart';

void main() {
  testWidgets('WITHOUT a boundary, an unrelated sibling repaints too', (tester) async {
    staticPaintCount = 0;
    spinnerPaintCount = 0;
    final key = GlobalKey<SpinnerBoxState>();
    await tester.pumpWidget(MaterialApp(home: Scaffold(body: NoBoundaryScene(spinnerKey: key))));
    expect(staticPaintCount, 1);

    key.currentState!.bump();
    await tester.pump();

    expect(spinnerPaintCount, 2, reason: 'the spinner itself changed, so of course it repaints');
    expect(staticPaintCount, 2, reason: 'StaticBox never changed, yet it was repainted too — same shared canvas');
  });

  testWidgets('WITH a RepaintBoundary, the sibling stops repainting', (tester) async {
    staticPaintCount = 0;
    spinnerPaintCount = 0;
    final key = GlobalKey<SpinnerBoxState>();
    await tester.pumpWidget(MaterialApp(home: Scaffold(body: WithBoundaryScene(spinnerKey: key))));
    expect(staticPaintCount, 1);

    key.currentState!.bump();
    await tester.pump();

    expect(spinnerPaintCount, 2, reason: 'the spinner still repaints — it genuinely changed');
    expect(staticPaintCount, 1, reason: 'StaticBox is now on its own layer boundary — the spinner\'s repaint no longer touches it');
  });
}
```


## พิสูจน์แล้ว: `Opacity` จอง compositing layer จริงแม้ที่ `opacity: 1.0` — มีแค่ `0.0` เท่านั้นที่ฟรีจริง ๆ

doc comment ของ widget `Opacity` เองบอกว่า *"Values one and zero are painted with a fast path. Other values require painting the child into an intermediate buffer, which is expensive."* การอ่าน source จริงของ `RenderOpacity` (`~/flutter/packages/flutter/lib/src/rendering/proxy_box.dart`) แสดงกลไกที่แม่นยำกว่าจริง ๆ: `alwaysNeedsCompositing => child != null && _alpha > 0` — จริงสำหรับ alpha ที่ไม่ใช่ศูนย์ **ใด ๆ** รวมถึง `255` (opacity `1.0`) มีแค่ `opacity: 0.0` (`_alpha == 0`) เท่านั้นที่ข้าม compositing และ painting ไปทั้งหมด พิสูจน์ได้ตรง ๆ ด้วยการตรวจ layer tree จริงที่แต่ละค่า:

```dart
// lib/opacity_layer_demo.dart
import 'package:flutter/material.dart';

class OpacityDemo extends StatelessWidget {
  const OpacityDemo({super.key, required this.opacity});
  final double opacity;
  @override
  Widget build(BuildContext context) {
    return RepaintBoundary(
      child: Opacity(
        opacity: opacity,
        child: Container(width: 40, height: 40, color: Colors.blue),
      ),
    );
  }
}
```

```dart
// test/opacity_layer_demo_test.dart
import 'package:flutter/material.dart';
import 'package:flutter/rendering.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/opacity_layer_demo.dart';

void main() {
  testWidgets('opacity: 1.0 still allocates its own OpacityLayer (alpha 255); only 0.0 omits it', (tester) async {
    await tester.pumpWidget(MaterialApp(home: Scaffold(body: OpacityDemo(opacity: 1.0))));
    final layersAtFull = tester.layers.whereType<OpacityLayer>().toList();
    final ownLayerAtFull = layersAtFull.where((l) => l.alpha == 255).length;

    await tester.pumpWidget(MaterialApp(home: Scaffold(body: OpacityDemo(opacity: 0.5))));
    final layersAtHalf = tester.layers.whereType<OpacityLayer>().where((l) => l.alpha == 128).length;

    await tester.pumpWidget(MaterialApp(home: Scaffold(body: OpacityDemo(opacity: 0.0))));
    final totalLayersAtZero = tester.layers.whereType<OpacityLayer>().length;

    expect(ownLayerAtFull, greaterThan(0), reason: 'opacity: 1.0 (alpha 255) DOES get its own OpacityLayer, contrary to "fully opaque = free"');
    expect(layersAtHalf, 1, reason: 'opacity: 0.5 (alpha 128) gets the same kind of layer, just a different alpha value');
    expect(totalLayersAtZero, lessThan(layersAtFull.length), reason: 'opacity: 0.0 is the one value that genuinely omits this widget\'s own layer');
  });
}
```

```text
00:00 +1: All tests passed!
```

(ตัดจากผล `flutter test test/lessons/layout-and-rendering__render-pipeline/` จริงบนเครื่องนี้)

ใน run นี้ ตัวเลขที่แน่ชัดคือ: `opacity: 1.0` → มี `OpacityLayer` ที่ `alpha: 255` อยู่จริง; `opacity: 0.5` → `OpacityLayer` ที่ `alpha: 128`; `opacity: 0.0` → layer ของ widget นั้นหายไปทั้งหมด (เหลือแค่ layer ambient จาก route-transition ที่เห็นข้างบน) ความเชื่อที่พูดซ้ำ ๆ ว่า "opacity 1.0 ไม่มีต้นทุนเลย เหมือนกับไม่ใช้ Opacity เลย" ไม่ตรงกับสิ่งที่ SDK นี้ทำเป๊ะ — มันยังคงสร้าง compositing boundary และ layer object จริงที่ opacity เต็ม; ความต่างของต้นทุน GPU จริงระหว่าง `1.0` กับค่าเศษส่วนอยู่ที่ว่า layer นั้น *composite* ถูกแค่ไหน (layer alpha-255 เป็น passthrough ง่าย ๆ สำหรับ rasterizer) ไม่ใช่อยู่ที่ว่ามี layer หรือไม่

## `AnimatedOpacity`/`FadeTransition`: กลไก compositing เดียวกัน ไม่ได้รับการยกเว้นจากต้นทุนของมัน

`RenderAnimatedOpacityMixin` ที่อยู่เบื้องหลัง `AnimatedOpacity` (`~/flutter/packages/flutter/lib/src/rendering/proxy_box.dart`) คำนวณ `isRepaintBoundary` แบบเดียวกับที่ `RenderOpacity` ทำ — มันผ่านกลไกการจอง layer เดียวกันเป๊ะที่พิสูจน์แล้วข้างบน แค่ค่า alpha เปลี่ยนทุก animation tick แทนที่จะเปลี่ยนครั้งเดียว สิ่งที่ `AnimatedOpacity`/`FadeTransition` เพิ่มมาเหนือกว่าการทำ `setState` + `Opacity(opacity: value)` เองด้วยมือคือ **การจัดตารางเวลา** ไม่ใช่ส่วนลดจากต้นทุน compositing ที่พิสูจน์แล้วข้างบน: framework ขับเคลื่อนค่าด้วย implicit animation แบบ ticker-based (ไม่ต้องมี `setState` boilerplate เอง, interpolation ที่ถูกต้อง, dispose อัตโนมัติ) แต่ทุกเฟรมระหว่างการ fade ยังต้องจ่ายค่าสำหรับการอัปเดต `OpacityLayer` แบบเดียวกันอยู่ดี

## `ClipRRect` และต้นทุนจริงของ `Clip.antiAliasWithSaveLayer`

`Clip` — enum ที่ clipping widget ทุกตัว (`ClipRRect`, `ClipRect`, `ClipPath`, `ClipOval`, `clipBehavior` ของ `Container`, …) รับ — มี trade-off ทาง performance ที่ระบุไว้ตรง ๆ บนแต่ละค่า quote ตรงคำจาก source ของ `dart:ui` เอง (สะท้อนที่ `api.flutter.dev/flutter/dart-ui/Clip.html`):

- **`Clip.none`**: *"This is the default option for most widgets: if the content does not overflow the widget boundary, don't pay any performance cost for clipping."*
- **`Clip.hardEdge`**: *"Faster than other clipping modes, but slower than none"* — clip โดยไม่ anti-alias ดังนั้นเส้นโค้ง/เส้นเฉียงจะขาด ๆ
- **`Clip.antiAlias`** (default ของ `ClipRRect` เอง): *"Much faster than antiAliasWithSaveLayer, but slower than hardEdge... this clipping can have bleeding edge artifacts."*
- **`Clip.antiAliasWithSaveLayer`**: *"This mode not only clips with anti-aliasing, but also allocates an offscreen buffer. All subsequent paints are carried out on that buffer before finally being clipped and composited back. This is very slow."*

ตัวสุดท้ายคือต้นทุนที่มีเอกสารจริงที่ section นี้พูดถึง: `Clip.antiAliasWithSaveLayer` คือตัวเลือกเดียวที่บังคับ offscreen buffer แบบ `Canvas.saveLayer` จริง ๆ — ต้นทุนคลาสประเภทเดียวกับที่พิสูจน์แล้วข้างบนสำหรับ `Opacity` แบบเศษส่วน — โดยเฉพาะเพื่อหลีกเลี่ยง bleeding-edge artifact ที่ `Clip.antiAlias` อาจมี ใช้มันเฉพาะเมื่อ artifact นั้นมองเห็นได้จริงและยอมรับไม่ได้; `Clip.antiAlias` (default) ถูกต้องสำหรับ rounded-corner clipping ส่วนใหญ่อย่างท่วมท้น

## Frame budget

เพื่อให้ได้ 60fps คุณมี **~16.6ms** ต่อเฟรม; ที่ 120Hz (โทรศัพท์สมัยใหม่หลายรุ่น) ลดลงครึ่งเป็น **~8.3ms** ทุกเทคนิคที่พิสูจน์ในบทเรียนนี้ — `RepaintBoundary` รอบสิ่งที่เปลี่ยนจริง, เลือก `Clip.antiAlias` แทน `Clip.antiAliasWithSaveLayer` เว้นแต่จำเป็นจริง, รู้ว่า `Opacity` มีต้นทุน layer เสมอเมื่อไม่ใช่ศูนย์ — มีไว้เพื่อให้ pipeline build/layout/paint/composite/raster อยู่ในหน้าต่างนั้น พลาดครั้งเดียวมองไม่เห็น พลาดซ้ำ ๆ คือ jank ที่ user เห็นจริง สำหรับกลไก scheduler ที่เปลี่ยน "มีอะไรเปลี่ยนแปลง" ให้กลายเป็น "เฟรมรัน" ดู [Flutter Internals: Layout and Paint](/flutter/th/flutter-internals/layout-and-paint-internals/) และสำหรับสิ่งที่เปลี่ยนที่ขั้น raster โดยเฉพาะ ดู [Flutter Internals: Impeller and the GPU](/flutter/th/impeller-and-the-gpu/)

<Callout title="สรุปหนึ่งบรรทัด">
ทุกเฟรมรัน **build → layout → paint → composite → raster** ภายใน budget ~16.6ms (~8.3ms ที่ 120Hz) **Impeller** — renderer default บน iOS (แต่เพียงผู้เดียว), บน Android สมัยใหม่, และ (ตั้งแต่ 3.47) บน macOS/Windows/Linux ด้วย — แทนที่ runtime shader compilation ของ Skia ด้วย shader และ pipeline state object ที่ precompile ตอน build time ลบ stutter รอบแรกแบบคลาสสิกออกไป `RepaintBoundary` — พิสูจน์แล้วข้างบนด้วย paint counter จริง — หยุด repaint ของ subtree หนึ่งไม่ให้บังคับ sibling ที่ไม่เกี่ยวข้องให้ repaint ด้วยได้จริง `debugDumpRenderTree`/`debugDumpLayerTree` คือ dump ที่ตรวจสอบได้จริงของ tree ที่มีชีวิต ไม่ใช่คำอธิบาย `Opacity` — พิสูจน์แล้วข้างบนด้วยการตรวจ layer tree จริง — จอง compositing layer จริงที่ทุกค่ายกเว้น `0.0` เป๊ะ รวมถึง `1.0`; `AnimatedOpacity` แชร์กลไกเดียวกันนั้น เพิ่มแค่การจัดตารางเวลา ไม่ใช่การยกเว้นต้นทุน `Clip.antiAliasWithSaveLayer` คือ clip mode เดียวที่บังคับ offscreen buffer ที่ช้าจริง ตาม source ที่มีเอกสารของมันเอง
</Callout>

## Mental Model

ห้า phase คือ **สายการผลิตของโรงพิมพ์**: build คือบรรณาธิการที่ตัดสินว่าหน้ากระดาษควรพูดอะไร; layout คือช่างเรียงพิมพ์ที่หาตำแหน่งเป๊ะของทุกคำและทุกภาพ; paint คือการลงหมึกบนแผ่นพิมพ์ — หนึ่งแผ่นต่อ section ที่ไม่ต้องเปลี่ยนไปพร้อมกับอันอื่น (`RepaintBoundary` คือ section ที่ได้แผ่นพิมพ์ของตัวเอง ดังนั้นการลงหมึกใหม่ไม่เคยรบกวนแผ่นรอบข้าง พิสูจน์แล้วข้างบน); composite คือการเรียงซ้อนแผ่นที่ลงหมึกแล้วทั้งหมดตามลำดับที่ถูกต้อง; และ raster คือแท่นพิมพ์จริงที่รันกระดาษผ่านและปล่อยหมึกลง — ขั้นที่ Impeller ทำให้เร็วขึ้นด้วยการคำนวณสูตรหมึกของแผ่นพิมพ์ล่วงหน้า (PSO) แทนที่จะผสมสูตรหมึกใหม่สด ๆ กลางการพิมพ์ ครั้งแรกที่ต้องการสีนั้น (runtime shader compilation ของ Skia)

## Trade-offs

| ทางเลือก | ข้อดี | ต้นทุน |
| --- | --- | --- |
| `RepaintBoundary` รอบ subtree ที่ repaint บ่อย | แยก repaint ของมันจาก sibling — พิสูจน์แล้วข้างบน | แต่ละ boundary คือ layer/memory allocation ของตัวเอง; ใช้มากเกินไปทุกที่เพิ่ม overhead โดยไม่มีประโยชน์ |
| `Opacity` ที่ค่าเศษส่วน | fade แบบ declarative ง่าย ๆ | compositing layer จริงทุกเฟรมที่ไม่ใช่ศูนย์ พิสูจน์แล้วข้างบน — ไม่ฟรีแม้แค่มองผ่าน ๆ |
| `Clip.antiAlias` (default) | เร็ว ขอบเรียบ ถูกต้องสำหรับเกือบทุกกรณี | อาจมี bleeding-edge artifact ในบางกรณีหายาก |
| `Clip.antiAliasWithSaveLayer` | กำจัด bleeding artifact นั้นได้หมด | offscreen buffer จริงตาม doc ของ engine เอง — "very slow" ใช้อย่างตั้งใจ ไม่ใช่ default |
| Impeller (default ของ platform) | ลบ jank จาก shader-compile รอบแรก — กลไกพิสูจน์แล้วข้างบน | ไม่มีอะไรให้ควบคุมโดยตรง — มันเป็น default; `--no-enable-impeller` มีให้ใช้เฉพาะที่ยังมี Skia fallback ship อยู่ (Android) |

## Common Misconceptions

- **"sibling widget ที่ไม่เกี่ยวข้องไม่เคย repaint แค่เพราะอย่างอื่นเปลี่ยน"** พิสูจน์แล้วว่าผิดข้างบน: โดยไม่มี `RepaintBoundary` `staticPaintCount` ไต่จาก `1` เป็น `2` เพียงเพราะ `CustomPainter` ของ sibling เปลี่ยน แชร์ canvas เดียวกัน
- **"Opacity ที่ 1.0 ฟรีสมบูรณ์ เหมือนกับไม่ได้ใช้ Opacity เลย"** พิสูจน์แล้วว่าผิดข้างบนด้วยการตรวจ layer tree จริง: `OpacityLayer` ที่ `alpha: 255` ถูกจองจริง มีแค่ `opacity: 0.0` เท่านั้นที่เป็น fast path จริง
- **"AnimatedOpacity ถูกกว่าการ animate Opacity เอง"** พิสูจน์แล้วข้างบนว่าแชร์กลไก compositing เดียวกันเป๊ะ — ประโยชน์จริงคือการจัดตารางเวลาแบบ ticker-driven ที่ถูกต้อง ไม่ใช่ส่วนลดจากต้นทุน layer ต่อเฟรม
- **"Clip.antiAlias กับ Clip.antiAliasWithSaveLayer เหมือนกันโดยพื้นฐาน แค่ชื่อต่างกัน"** doc comment ของ engine เอง quote ตรง ๆ ข้างบน ชัดเจน: มีแค่ตัวหลังเท่านั้นที่จอง offscreen buffer จริงและถูกอธิบายว่า "very slow" — ทั้งสองไม่ใช่ default ที่ใช้แทนกันได้
- **"Impeller มีผลแค่กับ iOS"** พิสูจน์แล้วข้างบนด้วยสถานะจริงต่อ platform: มันเป็น renderer เดียวบน iOS, default บน Android สมัยใหม่, และ — ตั้งแต่ 3.47 — default บน macOS, Windows, และ Linux ด้วย
