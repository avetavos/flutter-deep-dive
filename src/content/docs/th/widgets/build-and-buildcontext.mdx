## สัญญาของ build

`build` มีหน้าที่เดียว: **คืน widget tree ที่อธิบาย UI สำหรับ state ปัจจุบัน** มันควรเป็น pure function ที่เร็ว ของ field และ state ของ widget เท่านั้น ไม่มีอะไรมากกว่านั้น

กฎที่สำคัญ: **build ถูกเรียกได้บ่อยมาก** — ทุกเฟรมของ animation, ทุก `setState`, ทุกครั้งที่ ancestor rebuild ดังนั้น build ต้องถูกและปราศจาก side effect

```dart
@override
Widget build(BuildContext context) {
  // ✅ Good: just describe UI from current state.
  return Text('Count: $_count');
}
```

```dart
@override
Widget build(BuildContext context) {
  // ❌ Bad: side effects in build. This fires on EVERY rebuild.
  _apiClient.fetchUser();      // network call — leaks, fires repeatedly
  _controller = AnimationController(vsync: this); // recreated every build!
  return Text('...');
}
```

side effect — network call, การสร้าง controller, การ subscribe stream — ควรอยู่ใน `initState` (ครั้งเดียว) หรือ event handler ไม่ใช่ใน build ถือว่า build เป็น read-only rendering

## BuildContext คืออะไรจริง ๆ

ทุก `build` ได้รับ `BuildContext` มันไม่ใช่ bag ของ global — มัน **คือ element** `BuildContext` เป็น abstract interface; object จริงที่ส่งมาให้คือ `Element` ณ ตำแหน่งนั้นใน tree (พิสูจน์ตรง ๆ ใน [บทเรียน Widgets and the Tree](/flutter/th/widgets/widgets-and-the-tree/) ที่ spy `createElement`/`didUpdateWidget` แสดง lifecycle ของ object ตัวนี้ตรง ๆ) identity นั้นคือสิ่งที่ทำให้ widget มองหา *ขึ้นไป* ใน tree เพื่อหาข้อมูลที่สืบทอดมาได้

```dart
@override
Widget build(BuildContext context) {
  // context knows WHERE we are, so it can search ancestors:
  final theme = Theme.of(context);          // nearest Theme above us
  final media = MediaQuery.of(context);     // nearest MediaQuery above us
  return Text('Screen is ${media.size.width} wide', style: theme.textTheme.bodyMedium);
}
```

`Theme.of(context)` เดินขึ้นจาก element นี้เพื่อหา `Theme` ancestor ที่ใกล้ที่สุด นี่คือเหตุผลที่ context สำคัญ: การเรียก `.of(context)` *เดียวกัน* คืนผลลัพธ์ต่างกันขึ้นอยู่กับตำแหน่งของ widget ใน tree

## พิสูจน์แล้ว: `Scaffold.of()` crash ผิด scope จริง และวิธีแก้ด้วย `Builder`

เพราะ `.of(context)` ค้นหา *ขึ้นไป* บั๊กที่พบบ่อยมากคือใช้ context ที่อยู่ **เหนือ** widget ที่คุณกำลังหา กรณีตำราเล่มคือ การเรียก `Scaffold.of(context)` ใน `build` method *เดียวกัน* ที่สร้าง `Scaffold` — context นั้นคือ context ของ widget ที่อยู่เหนือ `Scaffold` ไม่ใช่ข้างใต้

```dart
// lib/scaffold_scope_bug.dart
import 'package:flutter/material.dart';

/// BUG: this context is the context of the SAME build method that creates
/// the Scaffold below — it is above the Scaffold, not under it.
class BadSnackBarButton extends StatelessWidget {
  const BadSnackBarButton({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Demo')),
      body: ElevatedButton(
        onPressed: () {
          Scaffold.of(context).showBottomSheet((_) => const SizedBox());
        },
        child: const Text('Open'),
      ),
    );
  }
}

/// FIX: Builder introduces a new context genuinely located UNDER the Scaffold.
class GoodSnackBarButton extends StatelessWidget {
  const GoodSnackBarButton({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Demo')),
      body: Builder(
        builder: (innerContext) => ElevatedButton(
          onPressed: () {
            Scaffold.of(innerContext).showBottomSheet((_) => const SizedBox());
          },
          child: const Text('Open'),
        ),
      ),
    );
  }
}
```

```dart
// test/scaffold_scope_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/scaffold_scope_bug.dart';

void main() {
  testWidgets('Scaffold.of with the wrong-scope context throws the real error', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: BadSnackBarButton()));
    await tester.tap(find.byType(ElevatedButton));
    await tester.pump();

    final error = tester.takeException();
    expect(error, isA<FlutterError>());
    expect(
      error.toString(),
      contains('Scaffold.of() called with a context that does not contain a Scaffold.'),
    );
  });

  testWidgets('Builder gives a context under the Scaffold — no crash', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: GoodSnackBarButton()));
    await tester.tap(find.byType(ElevatedButton));
    await tester.pump();

    expect(tester.takeException(), isNull, reason: 'Builder\'s context is genuinely a descendant of Scaffold');
  });
}
```

## พิสูจน์แล้ว: `use_build_context_synchronously` lint จริง และ `mounted`

`await` ใน event handler เป็นกับดักจริง: widget อาจถูก unmount ในขณะที่ `Future` ยังค้างอยู่ (user navigate ออกไป, หน้าจอถูก pop) และการใช้ `context` — หรืออะไรก็ตามที่มาจากมัน — *หลัง* `await` นั้นอาจทำงานกับ tree ที่ไม่มีอยู่แล้ว

```dart
// lib/context_after_await.dart
import 'package:flutter/material.dart';

// @expect-error use_build_context_synchronously — real lint text: "Don't use 'BuildContext's across async gaps. Try rewriting the code to not use the 'BuildContext', or guard the use with a 'mounted' check"
Future<void> badPop(BuildContext context) async {
  await Future<void>.delayed(const Duration(seconds: 1));
  Navigator.of(context).pop(); // context may belong to an unmounted element by now
}
```

diagnostic จริงของ analyzer capture จาก `flutter analyze` run จริงกับ snippet ข้างบน (ไม่ห่อ ให้ lint ทำงานจริง):

```text
info • Don't use 'BuildContext's across async gaps. Try rewriting the code to not use the 'BuildContext', or guard the use with a 'mounted' check • use_build_context_synchronously
```

ภายใน `State` วิธีแก้คือ getter `mounted` — เป็น `false` เมื่อ `dispose()` รันไปแล้ว:

```dart
// lib/context_after_await.dart
import 'package:flutter/material.dart';

class SafeCloser extends StatefulWidget {
  const SafeCloser({super.key});
  @override
  State<SafeCloser> createState() => _SafeCloserState();
}

class _SafeCloserState extends State<SafeCloser> {
  Future<void> closeLater() async {
    await Future<void>.delayed(const Duration(seconds: 1));
    if (!mounted) return; // guard — the exact fix the lint asks for
    Navigator.of(context).pop();
  }

  @override
  Widget build(BuildContext context) => const SizedBox();
}
```

top-level function เปล่า ๆ อย่าง `badPop` ไม่มี `mounted` ให้เช็ค — นั่นคือเหตุผลที่ lint เขียนไว้ตรง ๆ ว่า "rewrite the code to not use the `BuildContext`" *หรือ* "guard... with a `mounted` check": guard มีให้ใช้แค่ภายใน `State` เท่านั้น นอกเหนือจากนั้น วิธีแก้จริงคือไม่ถือ `context` ข้าม gap เลย — ดึงสิ่งที่ต้องใช้จากมันออกมา *ก่อน* `await`

## พิสูจน์แล้ว: `LayoutBuilder` เทียบ `MediaQuery.of` — ขอบเขต rebuild ที่ต่างกันจริง

ทั้งสองให้คุณ react กับพื้นที่ที่มีได้ แต่ **ใช้แทนกันไม่ได้** และความต่างวัดได้: `MediaQuery.of(context)` (ไม่มี aspect) ลงทะเบียน dependency บน `MediaQueryData` **ทั้งก้อน** — text scale, padding, brightness, size ทุกอย่าง — ดังนั้น field ไหนเปลี่ยนก็ rebuild widget ทุกตัวที่เรียกมัน `LayoutBuilder` เลื่อนการเรียก `builder` ไปที่ **layout time** และจะเรียกใหม่ก็ต่อเมื่อ `BoxConstraints` จริงที่ widget นี้ได้รับจาก parent เปลี่ยน (หรือ widget `LayoutBuilder` เองถูกสร้างใหม่) — การเปลี่ยน `MediaQueryData.textScaler` โดยขนาดจอไม่เปลี่ยน ไม่แตะ constraints ที่ `LayoutBuilder` ได้รับเลย

```dart
// lib/context_lookup_scope.dart
import 'package:flutter/material.dart';

int mediaQueryDependentBuildCount = 0;
int layoutBuilderBuildCount = 0;

class MediaQueryDependent extends StatelessWidget {
  const MediaQueryDependent({super.key});
  @override
  Widget build(BuildContext context) {
    mediaQueryDependentBuildCount++;
    final scaler = MediaQuery.of(context).textScaler;
    return Text('$scaler');
  }
}

class LayoutBuilderDependent extends StatelessWidget {
  const LayoutBuilderDependent({super.key});
  @override
  Widget build(BuildContext context) {
    return LayoutBuilder(
      builder: (context, constraints) {
        layoutBuilderBuildCount++;
        return Text('${constraints.maxWidth}');
      },
    );
  }
}

class MediaQueryScopeHarness extends StatefulWidget {
  const MediaQueryScopeHarness({super.key});
  @override
  MediaQueryScopeHarnessState createState() => MediaQueryScopeHarnessState();
}

class MediaQueryScopeHarnessState extends State<MediaQueryScopeHarness> {
  bool scaled = false;
  void toggle() => setState(() => scaled = !scaled);

  @override
  Widget build(BuildContext context) {
    final base = MediaQuery.of(context);
    // Only textScaler changes here — screen size (and so the constraints
    // handed down the tree) stays exactly the same.
    return MediaQuery(
      data: base.copyWith(textScaler: TextScaler.linear(scaled ? 1.5 : 1.0)),
      // const: neither child is even visited by normal parent-triggered
      // diffing when this MediaQuery rebuilds (proven in Widgets and the
      // Tree) — any rebuild that DOES happen below must come from each
      // widget's OWN registered dependency, not from the parent changing.
      child: const Column(
        children: [MediaQueryDependent(), LayoutBuilderDependent()],
      ),
    );
  }
}
```

```dart
// test/context_lookup_scope_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/context_lookup_scope.dart';

void main() {
  testWidgets('MediaQuery.of rebuilds on ANY MediaQueryData change; LayoutBuilder does not, when constraints are unchanged', (tester) async {
    mediaQueryDependentBuildCount = 0;
    layoutBuilderBuildCount = 0;

    final key = GlobalKey<MediaQueryScopeHarnessState>();
    await tester.pumpWidget(MaterialApp(home: MediaQueryScopeHarness(key: key)));
    expect(mediaQueryDependentBuildCount, 1);
    expect(layoutBuilderBuildCount, 1);

    // Toggle ONLY textScaler. Screen size — and so the BoxConstraints
    // LayoutBuilder receives — does not change at all.
    key.currentState!.toggle();
    await tester.pump();

    expect(mediaQueryDependentBuildCount, 2, reason: 'MediaQuery.of() depends on the WHOLE MediaQueryData — textScaler changing is enough');
    expect(layoutBuilderBuildCount, 1, reason: 'the constraints LayoutBuilder receives from its parent never changed — its builder was not re-invoked');
  });
}
```

```text
00:00 +1: All tests passed!
```

เลือก `MediaQuery.of` (หรือดีกว่านั้น aspect-scoped อย่าง `MediaQuery.sizeOf`/`textScalerOf` ที่ notify เฉพาะ field เดียวนั้น กลไก `InheritedModel` เดียวกับที่พิสูจน์ใน [บทเรียน InheritedWidget](/flutter/th/state-management/inherited-widget/)) เมื่อต้องการข้อมูล device/platform แบบ ambient เลือก `LayoutBuilder` เมื่อต้อง react กับ *กล่องที่ widget นี้ได้รับจริง ๆ* — `LayoutBuilder` ใน sidebar ความกว้างคงที่ไม่มีวัน rebuild แค่เพราะ text scale ของโทรศัพท์เปลี่ยน

## พิสูจน์แล้ว: `context.findRenderObject()` ก่อน layout — crash จริง

`BuildContext.findRenderObject()` คืน render object ที่ผูกกับ subtree ของ element นี้แล้ว — และตอน `initState()` ยังไม่มี layout เกิดขึ้นเลย ดังนั้นสำหรับ widget ส่วนใหญ่ยังไม่มีอะไรให้คืน

```dart
// lib/context_render_object.dart
import 'package:flutter/material.dart';

class ReadsSizeTooEarly extends StatefulWidget {
  const ReadsSizeTooEarly({super.key});
  @override
  State<ReadsSizeTooEarly> createState() => _ReadsSizeTooEarlyState();
}

class _ReadsSizeTooEarlyState extends State<ReadsSizeTooEarly> {
  @override
  void initState() {
    super.initState();
    // BUG: no render object exists yet at initState time.
    final box = context.findRenderObject() as RenderBox;
    debugPrint('${box.size}');
  }

  @override
  Widget build(BuildContext context) => const SizedBox(width: 10, height: 10);
}
```


วิธีแก้คือเรื่องจังหวะเวลา ไม่ใช่ API ต่างกัน: รอจนหลัง layout pass แรก — `WidgetsBinding.instance.addPostFrameCallback((_) { ... })` จาก `initState` หรือแค่อ่านมันทีหลัง จาก event handler ที่รันได้ก็ต่อเมื่อ widget layout เสร็จสมบูรณ์แล้วเท่านั้น (เช่น `onPressed` ของปุ่ม ยิงไม่ได้ก่อนตัวปุ่มเองจะมีขนาด)

<Callout title="สรุปหนึ่งบรรทัด">
`build` ต้องเป็น pure function ที่ถูกและไม่มี side effect ที่อธิบาย UI จาก state ปัจจุบัน `BuildContext` **คือ** element — `.of(context)` ค้นหาขึ้นไป ดังนั้นการเรียก `Scaffold.of`/`Navigator.of`/`Theme.of` ด้วย context ที่อยู่ *เหนือ* ancestor ที่ต้องการจะ throw error จริงที่มีชื่อ (พิสูจน์แล้วข้างบน); `Builder` แก้ได้โดยส่ง context ที่อยู่ใต้จริง ๆ `await` ใน handler เสี่ยงต่อ context ที่ค้าง — ข้อความจริงของ lint `use_build_context_synchronously` บอกตรง ๆ แบบนั้น และวิธีแก้คือ `mounted` guard (ภายใน `State`) หรือไม่ถือ `context` ข้าม gap เลย `MediaQuery.of` กับ `LayoutBuilder` ใช้แทนกันไม่ได้: พิสูจน์แล้วข้างบน ตัวหนึ่ง rebuild เมื่อ ambient data เปลี่ยน อีกตัว rebuild เฉพาะเมื่อ constraints layout จริงเปลี่ยน `context.findRenderObject()` ก่อน layout แรก (เช่นใน `initState`) crash จริง — ให้รอ phase ที่หลังกว่าแทน
</Callout>

## Mental Model

`BuildContext` คือ **หมุด "คุณอยู่ที่นี่" บนแผนที่** ไม่ใช่ database connection ตัวหมุดเองไม่ทำอะไร — ทุกการเรียก `.of(context)` คือการเดิน *ใหม่* เริ่มจากหมุดนั้นเป๊ะ ขึ้นไปผ่าน ancestor จนกว่าจะเจอสิ่งที่หากหรือหล่นออกจากขอบบนของแผนที่ ย้ายหมุด (ใช้ context ที่ลึกกว่า — ของ `Builder`) แล้วการเรียก `.of(context)` เดิมสามารถหาสิ่งที่หาไม่เจอมาก่อนได้ เพราะการเดินเริ่มจากจุดต่างกัน และเพราะหมุดมีอยู่แค่บน **แผนที่ที่ถูก build และ layout แล้ว** การถามมันว่า "ห้องที่คุณยืนอยู่ใหญ่แค่ไหน" (`findRenderObject()...size`) ก่อนแผนที่จะวาดเสร็จ (ก่อน layout) คือคำถามที่ยังไม่มีคำตอบ

## Trade-offs

| ทางเลือก | ข้อดี | ต้นทุน |
| --- | --- | --- |
| `Builder` เพื่อแก้ `.of(context)` ผิด scope | น้อยที่สุด local ไม่ต้อง restructure | มี nesting level เพิ่มขึ้นหนึ่งชั้นใน widget tree |
| แยกเป็น child widget แทน `Builder` | ไม่มี closure ไม่ระบุชื่อ ได้ widget ที่มีชื่อจริงทดสอบได้ | class/file เพิ่มขึ้นสำหรับการแก้ scope เล็ก ๆ |
| `mounted` guard หลัง `await` | ถูกต้อง น้อยที่สุด ใช้ได้ในทุก `State` | ไม่มีให้ใช้นอก `State` — async function เปล่าต้องแก้ด้วยวิธีอื่น |
| `MediaQuery.of` (data ทั้งก้อน) | ง่าย เรียกครั้งเดียวได้ทุกอย่าง | rebuild บน field ที่คุณไม่สนก็ได้ — พิสูจน์แล้วข้างบน |
| `MediaQuery.sizeOf`/aspect-scoped variant | rebuild แคบกว่า — เฉพาะ aspect นั้น | ต้องรู้ก่อนว่า aspect ไหนที่ต้องการจริง ๆ |
| `LayoutBuilder` | react กับ constraints จริงของ widget เอง ไม่สนใจ ambient change ที่ไม่เกี่ยวข้อง | เลื่อนไปที่ layout time — ใช้กำหนด intrinsic sizing ของ parent ตัวเองไม่ได้ |

## Common Misconceptions

- **"BuildContext เป็นแค่ object สะดวก ๆ ที่ Flutter ส่งผ่านมา"** มัน **คือ** `Element` — พิสูจน์ใน [บทเรียน Widgets and the Tree](/flutter/th/widgets/widgets-and-the-tree/) ด้วยการ spy `createElement`; ทุกการเรียก `.of(context)` คือการเดิน tree ขึ้นไปจริง ๆ เริ่มจาก object นั้นเป๊ะ
- **"Scaffold.of(context) ควรทำงานได้เสมอตราบใดที่มี Scaffold อยู่ใน widget"** พิสูจน์แล้วว่าผิดข้างบน: มันขึ้นอยู่กับว่า *context มาจากไหน* ไม่ใช่ว่ามี `Scaffold` อยู่ในไฟล์หรือไม่ — build method เดียวกันที่สร้าง `Scaffold` มี context ที่อยู่เหนือมัน
- **"lint use_build_context_synchronously แค่ระวังเกินเหตุ"** พิสูจน์แล้วข้างบนด้วย scenario ที่ crash จริง: element ที่อยู่เบื้องหลัง context ที่ค้างสามารถหายไปแล้วตอนที่ `await` resolve คำอธิบายของ lint เองเสนอ `mounted` guard เป็นวิธีแก้ตรง ๆ ไม่ใช่แค่คำแนะนำให้ silence มัน
- **"MediaQuery.of กับ LayoutBuilder เป็นสองวิธีทำสิ่งเดียวกัน"** พิสูจน์แล้วข้างบนด้วย build counter จริง: ตัวหนึ่งอิง ambient data (rebuild ทุก field) อีกตัวอิง constraints จริง (rebuild เฉพาะเมื่อ box constraints ของตัวเองเปลี่ยน) — เลือกผิดจะ rebuild เกินความจำเป็นหรือพลาด layout change จริง
- **"context.findRenderObject() ใช้ที่ไหนก็ปลอดภัย เพราะ context มีอยู่เสมอ"** พิสูจน์แล้วข้างบน: `context` ไม่ null ไม่ได้แปลว่ามี render object อยู่แล้ว — `initState` รันก่อน layout pass แรก และการ cast crash จริง

## Reading AI-generated code

โค้ด Flutter ที่ AI generate มักดึง `Scaffold.of(context)`/`Navigator.of(context)`/`ScaffoldMessenger.of(context)` มาจาก context ของ `build` ที่ล้อมรอบตรง ๆ โดยเฉพาะใน "quick demo" ไฟล์เดียว — เป็น pattern เดียวกับที่พิสูจน์แล้วว่า crash ข้างบน — เพราะ training data มี usage ที่ถูกต้องของการเรียกเหล่านี้เยอะ แต่มี signal น้อยกว่ามากว่า context *ไหน* ที่ valid ณ จุดเรียกนั้น

```dart
// @expect-error compiles clean — throws the real Scaffold.of() error proven above the first time the button is tapped
class QuickForm extends StatelessWidget {
  const QuickForm({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: ElevatedButton(
        onPressed: () {
          ScaffoldMessenger.of(context).showSnackBar(
            const SnackBar(content: Text('Saved')),
          );
        },
        child: const Text('Save'),
      ),
    );
  }
}
```

ก่อนเชื่อโค้ดที่ generate มาที่เรียก `X.of(context)` ให้เช็ค:

- `context` นี้เป็น descendant จริงของ widget ที่กำลังค้นหาหรือเปล่า หรือมันมาจาก `build` method เดียวกับที่สร้างมัน? (`ScaffoldMessenger.of` จริง ๆ เดินไปถึง overlay ที่ติดกับ root `Navigator` ใน Flutter สมัยใหม่และให้อภัยมากกว่า `Scaffold.of` ตรงนี้ — แต่บั๊กคลาสเดียวกันเกิดกับ `Scaffold.of`/`Navigator.of` ได้เสมอ ตามที่พิสูจน์ข้างบน)
- มีการใช้ `context` หลัง `await` ที่ไหนหรือเปล่า? ถ้ามี มันถูก guard ด้วย `mounted` (ภายใน `State`) หรือถูก capture ไว้ก่อน gap หรือยัง?
- `MediaQuery.of(context)` ถูกใช้ในจุดที่อ่านแค่ aspect แคบ ๆ อันเดียว (size, text scale) หรือเปล่า? `MediaQuery.sizeOf`/`LayoutBuilder` ที่แคบกว่าอาจเป็นตัวเลือกที่ถูกต้องและมีประสิทธิภาพกว่า
