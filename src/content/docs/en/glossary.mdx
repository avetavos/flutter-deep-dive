Flutter's vocabulary spans several layers at once: the Dart language itself (null safety, records, patterns, class modifiers) that every other layer is written in; the three trees (widget, element, render) that explain almost everything about performance; state management (`setState`, `InheritedWidget`, Riverpod, BLoC) built directly on top of that element tree; navigation (`Navigator`, go_router) and platform channels for reaching outside Dart entirely; the constraints-based layout algorithm and the paint/composite/raster pipeline underneath every pixel; and the tooling and production concerns (testing, builds, crash reporting) that turn a widget tree into a shipped app. When a lesson uses a term you're unsure about, or unsure whether it still holds for Flutter 3.47.5 / Dart 3.13, look it up here — every definition below is sourced from a lesson that proved it with a real `flutter analyze`/`flutter test` run or a real, quoted SDK source/doc, not from memory.

## A

| Term | Meaning | Lesson |
|------|---------|--------|
| AnimatedOpacity / FadeTransition | Implicit animation wrappers around the same `RenderOpacity`/layer mechanism proven for the plain `Opacity` widget — they add ticker-driven scheduling and automatic disposal, **not** an exemption from paying for a real compositing layer on every non-zero alpha frame during the fade. | [Render Pipeline](/flutter/en/layout-and-rendering/render-pipeline/) |
| AnimatedSwitcher | Cross-fades between two widgets when its child changes; whether it animates at all is decided by the child's **key** — same key means "same widget updated in place," no transition; a different key means "different widget," and the switch animates. | [Animations](/flutter/en/async-and-performance/animations/) |
| AnimationController | Drives an **explicit** animation: `vsync: this` (needs a `TickerProviderStateMixin`), `.value` walks 0→1 over `duration` — proven directly with `tester.pump(Duration)` landing on exact intermediate values (`0.50` at the halfway point with `Curves.linear`). Forgetting `controller.dispose()` throws a real, debug-mode-only assert: `"was disposed with an active Ticker"`, from `SingleTickerProviderStateMixin.dispose()` in the installed Flutter 3.47.5 SDK. | [Animations](/flutter/en/async-and-performance/animations/) |
| analysis_options.yaml (`strict-casts` / `strict-inference` / `strict-raw-types`) | Three analyzer `language` options — off by default, not part of any lint package — that catch implicit `dynamic` leaking into typed code. Each has a distinct, real diagnostic: `strict-casts` gives `invalid_assignment` on an implicit `dynamic → int` narrowing; `strict-raw-types` gives `strict_raw_type` on a bare `List`; `strict-inference` gives `inference_failure_on_collection_literal` on an uninferred `[]`. This course's own probe runs with all three enabled. | [Project & Tooling](/flutter/en/tooling-and-production/project-and-tooling/) |
| async / await | `async` makes a function return a `Future<T>`; `await` unwraps it and lets errors surface as normal, `try`/`catch`-able exceptions — proven directly against a rejected `Future`. You rarely `await` inside `build`; hand the `Future` to a `FutureBuilder` instead. | [Async in Dart](/flutter/en/dart-foundations/async-in-dart/) |
| AsyncNotifier / `AsyncValue.when` | Riverpod's async-state provider: `build()` returns a `Future<T>`, and `ref.watch` exposes an `AsyncValue<T>` you branch on with `.when(data:, error:, loading:)`. Riverpod 3 gives every provider an automatic retry policy (`ProviderContainer.defaultRetry`, exponential backoff, capped retries) — a thrown error stays `AsyncLoading(error: ..., retrying: true)`, not `AsyncError`, for as long as retries are in flight, which is a real, proven trap for a widget test expecting an immediate error state. | [Provider & Riverpod](/flutter/en/state-management/provider-and-riverpod/) |
| `.autoDispose` | A Riverpod provider modifier that disposes provider state once its last listener unsubscribes, instead of caching it for the app's whole lifetime — the default for a family/parameterized provider to avoid leaking one cached instance per parameter value forever. | [Provider & Riverpod](/flutter/en/state-management/provider-and-riverpod/) |
| `AutomaticKeepAliveClientMixin` | Opts a specific list item's `State` out of the normal "dispose once scrolled off-screen" laziness — proven with a real round trip: scroll `8000px` away and back, and the keep-alive item's `State` is the *same instance* (same id), while a plain `State` item is a genuinely new one. Costs the memory laziness normally buys; use only for state expensive to rebuild. | [Slivers & Scrolling](/flutter/en/layout-and-rendering/slivers-and-scrolling/) |

## B

| Term | Meaning | Lesson |
|------|---------|--------|
| `BackgroundIsolateBinaryMessenger` | Lets a platform channel call run from a background isolate (inside `compute()`/`Isolate.run`) instead of only the root isolate — needs `ensureInitialized(token)` first, with `token` a `RootIsolateToken` obtained on the root isolate via `ServicesBinding.rootIsolateToken` before spawning. Skipping it throws: the instance is "invalid until `ensureInitialized` is executed," per the installed 3.47.5 SDK's own doc comment. | [Platform Channels](/flutter/en/navigation/platform-channels/) |
| `base` (class modifier) | Forbids `implements` outside the declaring library while still allowing `extends` — real `invalid_use_of_type_outside_library` error: *"can't be implemented outside of its library because it's a base class."* Guarantees every instance genuinely *is* the real type via inheritance, never a lookalike built to match the interface shape. | [Classes & Mixins](/flutter/en/dart-foundations/classes-and-mixins/) |
| BLoC / `Bloc` | A pattern enforcing strict one-direction data flow: the UI sends events in, a `Bloc<Event, State>` emits states out, the UI rebuilds from those states — never mutating state directly. `flutter_bloc` (**9.1.1**) ships both `Bloc` (explicit `Event` classes) and the simpler `Cubit`. | [BLoC & Patterns](/flutter/en/state-management/bloc-and-patterns/) |
| `BlocBuilder` / `buildWhen` | `BlocBuilder<B, S>` rebuilds on every new state by default; `buildWhen: (previous, current) => ...` narrows that — proven with a build counter: four `Increment` events that keep the state's `runtimeType` the same produce zero rebuilds, and only the fifth event (a genuine type change) triggers one. Same role as `InheritedModel`'s aspects or Riverpod's `.select()`. | [BLoC & Patterns](/flutter/en/state-management/bloc-and-patterns/) |
| `BlocListener` | Runs a one-shot side effect (navigation, a `SnackBar`) in response to a new state, without itself rebuilding any widget — proven to fire exactly once, with the exact triggering state value, across five events. | [BLoC & Patterns](/flutter/en/state-management/bloc-and-patterns/) |
| `blocTest` | `bloc_test` (**10.0.0**)'s helper: `build`s the bloc, drives it with `act`, and asserts the **exact ordered list** of emitted states with `expect: () => [...]` — no widget involved. `seed:` starts from a specific state without replaying the events that would normally reach it. Requires the state class to extend `Equatable` (below), or value-equal states compare unequal and every assertion fails. | [BLoC & Patterns](/flutter/en/state-management/bloc-and-patterns/) |
| `BuildContext` | Not a bag of globals — it **is** the `Element` at that position in the tree (proven by spying `createElement`). This identity is what lets `.of(context)` search *upward* for an ancestor; using a context that sits above the ancestor you're looking for (e.g. `Scaffold.of(context)` in the same `build` that creates the `Scaffold`) throws a real, named error — `Builder` is the standard fix, introducing a genuinely descendant context. | [Build & BuildContext](/flutter/en/widgets/build-and-buildcontext/) |
| `build` / rebuild / dirty | `setState` (or an ancestor's rebuild) marks an element **dirty**; on the next frame Flutter calls `build` again on every dirty element. `build` must stay pure and fast — no side effects, no controller creation, no network calls — because it can run every frame of an animation, not just once. | [setState & Lifecycle](/flutter/en/state-management/setstate-and-lifecycle/) |

## C

| Term | Meaning | Lesson |
|------|---------|--------|
| `cacheWidth` / `cacheHeight` | `Image`'s decode-time resize hint, in physical pixels: decoding a large source image at its full resolution just to display it at thumbnail size wastes memory and decode time, so passing the actual display size here caps what the image decoder allocates. | [Rebuilds & Performance](/flutter/en/async-and-performance/rebuilds-and-performance/) |
| `catchError` vs. `.then(onValue, onError:)` | Genuinely different, proven directly: `onError` on `.then` only catches an error from the future being chained onto, **not** one thrown inside `onValue` itself; `.catchError(...)` chained *after* `.then()` catches errors from either. Mixing them up is a real, silent error-swallowing bug. | [Async in Dart](/flutter/en/dart-foundations/async-in-dart/) |
| `ChangeNotifierProvider` | Provider's binding of `InheritedWidget` + `ChangeNotifier`: `notifyListeners()` triggers a rebuild of the underlying `InheritedWidget`; `context.watch<T>()` is `dependOnInheritedWidgetOfExactType` with nicer syntax, `context.read<T>()` is the no-dependency lookup. | [InheritedWidget](/flutter/en/state-management/inherited-widget/) |
| class modifiers (`sealed` / `final` / `base` / `interface` / `mixin class`) | Five Dart 3.0 modifiers restricting how a class can be used **outside the library that declares it** — see each modifier's own entry. All four of `sealed`/`base`/`interface`/`final` share the **same** analyzer error code, `invalid_use_of_type_outside_library` — only the message text differs; grep CI output on the code, not the message. | [Classes & Mixins](/flutter/en/dart-foundations/classes-and-mixins/) |
| `Clip` / `Clip.antiAliasWithSaveLayer` | The clip-behavior enum every clipping widget takes: `Clip.none` (free, the default for most), `Clip.hardEdge` (fast, jagged edges), `Clip.antiAlias` (`ClipRRect`'s own default — smooth, possible bleeding-edge artifacts), and `Clip.antiAliasWithSaveLayer` — the one mode that genuinely forces an offscreen `Canvas.saveLayer` buffer, "very slow" per `dart:ui`'s own source. Reach for it only when `Clip.antiAlias`'s artifact is visible and unacceptable. | [Render Pipeline](/flutter/en/layout-and-rendering/render-pipeline/) |
| code generation (`@riverpod`, `build_runner`, `.g.dart`) | `riverpod_generator`/`riverpod_annotation` (**4.0.7**) write the provider boilerplate (`.autoDispose`, correct typing, `ref` wiring) from an annotated function or `Notifier`/`AsyncNotifier` class via `part 'x.g.dart'` — run with `dart run build_runner build`. This course's harness doesn't run `build_runner`, so a lesson using codegen ships the real generated `.g.dart` content as its own file. | [Provider & Riverpod](/flutter/en/state-management/provider-and-riverpod/) |
| `compute()` | Flutter's wrapper for running a pure function on a background isolate. Reading the installed Flutter 3.47.5 SDK source directly disproves the common claim that it adds "isolate-pool management" over `Isolate.run` — on native, `compute(fn, arg)` **is, literally**, `Isolate.run(() => fn(arg))` plus a debug label. On web it is a completely different function: `await null;` then `callback(message)` **on the same thread** — no isolate at all, confirmed by `api.flutter.dev`: *"On web platforms this will run `callback` on the current eventloop."* A closure passed to `compute()` that captures a native handle (a `ReceivePort`, a `BuildContext`) throws a real `ArgumentError: Illegal argument in isolate message: object is unsendable`. | [Isolates & compute()](/flutter/en/async-and-performance/isolates-and-compute/) |
| `const` canonicalization | A `const` widget/record/value expression is a single canonicalized object — `identical(const (1,2), const (1,2))` is `true`, proven directly for both records and widgets. Flutter's element-update path short-circuits on `identical(oldWidget, newWidget)`, so a `const` child is never diffed or rebuilt while its non-const sibling rebuilds on every parent rebuild — this is strictly stronger than a manual memoization check, and free. | [Widgets and the Tree](/flutter/en/widgets/widgets-and-the-tree/) |
| `ConnectionState` | The four-value enum an `AsyncSnapshot` carries: `none` (only for a literal `null` future/stream), `waiting` (subscribed, no result yet), `active` (`StreamBuilder` only — at least one event arrived, stream still open), `done` (future completed, or stream closed). `FutureBuilder` only ever produces `waiting`/`done` in practice — there's no "active" state for a one-shot value. | [Futures & Streams in the UI](/flutter/en/async-and-performance/futures-streams-in-ui/) |
| `ConstrainedBox` / `UnconstrainedBox` / `OverflowBox` | `ConstrainedBox` adds extra min/max bounds on top of the incoming constraint; `UnconstrainedBox` lets its child ignore the incoming constraint and size to its own natural size (can overflow visibly, deliberately); `OverflowBox` genuinely breaks the down-flow rule, imposing a *different* constraint range on its child than what it itself received. | [Constraints & Layout](/flutter/en/layout-and-rendering/constraints-and-layout/) |
| constraints (tight / loose / unbounded) | **Tight**: min equals max, the child must be exactly that size (`SizedBox`). **Loose**: min is 0, the child may be anything up to max (`Center`). **Unbounded**: max is infinity, "be as big as you want" — a plain `Column` gives its non-flex children unbounded main-axis height, which is exactly what crashes a bare `ListView` placed there (below). | [Constraints & Layout](/flutter/en/layout-and-rendering/constraints-and-layout/) |
| `context.go` vs `context.push` vs `Navigator.push` | `context.go(path)` **replaces** the current location (whatever go_router's route table says that location's stack should be — no back-stack between siblings); `context.push(path)` adds an entry on top, tracked by go_router as an `ImperativeRouteMatch`; raw `Navigator.of(context).push(...)` grows the same underlying Flutter stack but go_router's own notion of "current location" never sees it — proven directly: after an imperative push, `GoRouter`'s `currentConfiguration.uri` is still the old path. | [Declarative Routing](/flutter/en/navigation/declarative-routing/) |
| `covariant` | Marks a subclass override parameter as accepting a more specific type than its supertype's signature declares, trading a compile-time guarantee for a runtime `TypeError` if the actual call passes the wrong subtype — used on `didUpdateWidget(covariant MyWidget oldWidget)` throughout this course. | [Classes & Mixins](/flutter/en/dart-foundations/classes-and-mixins/) |
| Cubit | The simpler half of `flutter_bloc`: no `Event` classes, just methods that call `emit(newState)` directly. Start here; reach for full `Bloc` (explicit events) only when a documented, loggable list of every possible input earns back the extra ceremony. | [BLoC & Patterns](/flutter/en/state-management/bloc-and-patterns/) |
| Curve / `Curves` | Reshapes linear animation time into natural motion (`Curves.easeInOut`, `Curves.elasticOut`, …); both `TweenAnimationBuilder` and an `AnimationController`-driven `CurvedAnimation` take one. Still fully testable via `tester.pump(Duration)` — assert against `Curves.easeInOut.transform(0.5)` rather than the raw linear value. | [Animations](/flutter/en/async-and-performance/animations/) |
| `CustomScrollView` | Composes multiple sliver types (`SliverAppBar`, `SliverToBoxAdapter`, `SliverGrid`, `SliverList`) into one continuous scroll — proven directly: each sliver stays independently lazy even inside the composed view (13 of 1000 `SliverList` rows built on one measured run). | [Slivers & Scrolling](/flutter/en/layout-and-rendering/slivers-and-scrolling/) |

## D

| Term | Meaning | Lesson |
|------|---------|--------|
| `dart fix --dry-run` / `dart fix --apply` | Applies the analyzer's own registered auto-fixes. `--dry-run` shows what *would* change without touching anything — proven with real output for `use_full_hex_values_for_flutter_colors`. Not every lint is auto-fixable: `avoid_unnecessary_containers` is a real, live diagnostic that `dart fix --dry-run` reports **zero** proposed fixes for, since removing a `Container` while re-parenting its child is a structural edit outside the fix registry. | [Project & Tooling](/flutter/en/tooling-and-production/project-and-tooling/) |
| `dart:ffi` | The lower-level mechanism for calling a native **C** library directly (no Kotlin/Swift glue) — quoting `dart.dev`'s C-interop docs: *"Dart... apps... can use `dart:ffi`... to call native C APIs, and to read, write, allocate, and deallocate native memory."* Different tool than platform channels: channels talk to a platform SDK through native glue you write; `dart:ffi` talks straight to a C ABI. | [Platform Channels](/flutter/en/navigation/platform-channels/) |
| `dart:io` vs. web (`kIsWeb`, conditional import) | A common but wrong assumption: `flutter build web` fails outright on `import 'dart:io'`. Proven false — `dart:io`'s classes exist as real, type-checkable stubs on the web compiler (confirmed from the installed SDK's `io_patch.dart`), so a build with `Platform.isIOS`/`File.readAsString()` wired into `main()` **succeeds**, even with `--wasm`; the bug ships silently through `flutter analyze` and both build targets and only surfaces as a real `UnsupportedError` the first time a user's browser actually runs that code path. `kIsWeb` (a compile-time `bool`) or a conditional import (`import 'io_impl.dart' if (dart.library.js_interop) 'web_impl.dart';`) are the real guards. | [Project & Tooling](/flutter/en/tooling-and-production/project-and-tooling/) |
| `--dart-define` / `--dart-define-from-file` | Passes a compile-time constant your code reads with `String.fromEnvironment('KEY', defaultValue: ...)` — proven directly: run `flutter test --dart-define=API_URL=...` and the constant reads exactly that value at compile time, not a runtime environment lookup. `--dart-define-from-file=config.json` passes a whole file of key/value pairs at once, for a flavor needing many values. | [Build & Release](/flutter/en/tooling-and-production/build-and-release/) |
| definite assignment analysis | The analyzer's proof that a non-nullable local is assigned on **every** code path before it's read. A non-`final` local missing a path gets `not_assigned_potentially_non_nullable_local_variable`; a `final` local with the same gap gets a different, real diagnostic — `read_potentially_unassigned_final` — both proven with real `flutter analyze` output. | [Null Safety](/flutter/en/dart-foundations/null-safety/) |
| `didChangeDependencies` | Runs right after `initState`, and again whenever an inherited dependency this `State` reads actually changes — the safe place to read `InheritedWidget`/`Provider`/`Theme.of` data that setup depends on (`initState` itself can't reliably read inherited widgets). | [setState & Lifecycle](/flutter/en/state-management/setstate-and-lifecycle/) |
| `didUpdateWidget` | Called when the parent rebuilds and hands this `State` a new widget **config** of the same type/key — proven to run **before** the `build` it triggers, via a real logged order. `covariant` widens the parameter type from the supertype signature to the concrete widget type. | [setState & Lifecycle](/flutter/en/state-management/setstate-and-lifecycle/) |
| `dispose` | Called once Flutter confirms an element was *not* reinserted elsewhere after `deactivate` — clean up controllers, cancel subscriptions here. Forgetting it is the classic Flutter memory leak, proven concretely for a leaked `AnimationController`'s `Ticker`. | [setState & Lifecycle](/flutter/en/state-management/setstate-and-lifecycle/) |
| `dependOnInheritedWidgetOfExactType` vs. `getInheritedWidgetOfExactType` vs. `findAncestorWidgetOfExactType` | Only `dependOnInheritedWidgetOfExactType` **registers a dependency** and auto-rebuilds the caller on update — proven with a build-count test: after an ancestor `InheritedWidget` update, the `dependOn` reader's build count moves from 1→2, while the `get`/`findAncestor` readers stay at 1. `getInheritedWidgetOfExactType` is the same O(1) cached lookup with no subscription (a one-time read); `findAncestorWidgetOfExactType` walks the **widget** tree directly (O(depth), works for any `Widget`, not just `InheritedWidget`). | [InheritedWidget](/flutter/en/state-management/inherited-widget/) |
| DevTools | The browser-based suite for inspecting a running app — widget inspector, performance/timeline view, memory view, network view. This course's environment has no device to attach it to, so every DevTools claim in this course is docs-cited, not screenshotted. | [Project & Tooling](/flutter/en/tooling-and-production/project-and-tooling/) |

## E

| Term | Meaning | Lesson |
|------|---------|--------|
| Element / element tree | The **living instance** of a widget at a tree position — persists across rebuilds, holds `State`, decides whether a new widget updates it in place (`update`/`didUpdateWidget`) or tears it down (`unmount` + fresh `createElement`). `BuildContext` **is** the element (proven by spying its identity). Middle of the three trees, between the cheap widget tree and the expensive render tree. | [Widgets and the Tree](/flutter/en/widgets/widgets-and-the-tree/) |
| Equatable | `package:equatable` (**3.0.0**) gives a class value-equality (`==`/`hashCode`) from a declared `props` list instead of Dart's default identity equality — required for `blocTest`'s `expect: () => [...]` to compare emitted states by value; without it, two separately-constructed equal-looking states are unequal and every assertion fails. | [BLoC & Patterns](/flutter/en/state-management/bloc-and-patterns/) |
| `EventChannel` | Where `MethodChannel` is one call/one reply, `EventChannel` delivers a **stream** of native events (sensor data, connectivity) — maps to a Dart `Stream` via `receiveBroadcastStream()`. `flutter_test`'s `setMockStreamHandler(channel, MockStreamHandler.inline(onListen: ...))` mocks it, proven to deliver events in order then close. | [Platform Channels](/flutter/en/navigation/platform-channels/) |
| exhaustiveness | The analyzer's proof that a `switch` over a `sealed` class or `enum` handles every possible case, at compile time — proven directly by deleting one case and getting a real `non_exhaustive_switch_expression`/`non_exhaustive_switch_statement` diagnostic. This is what makes `sealed` + `switch` sound: the analyzer can enumerate every subtype only because no other library can add one. | [Dart Language Tour](/flutter/en/dart-foundations/dart-language-tour/) |
| `Expanded` vs. `Flexible` | Both split a `Row`/`Column`'s remaining space by flex factor, but hand the child a different constraint: `Expanded` (`FlexFit.tight`) forces the child to fill its full share regardless of its natural size — proven: a 50px-wide child stretched to 300px. `Flexible` (`FlexFit.loose`, the default) only **bounds** the child at its share, letting it keep its own natural size if smaller — proven: the same 50px child stays 50px. | [Core Layout Widgets](/flutter/en/layout-and-rendering/core-layout-widgets/) |
| extension type | A Dart 3.3 zero-cost compile-time wrapper — `dart.dev`: *"extension types are static-only and compiled away at run time"*. `extension type UserId(String value) { ... }` exposes only what it explicitly declares; calling a real `String` member on it is a genuine `undefined_method` compile error, even though `id is String` is still `true` at runtime (there's no wrapper object to be anything else). `implements` a supertype of the representation type to inherit members for free. | [Dart Language Tour](/flutter/en/dart-foundations/dart-language-tour/) |

## F

| Term | Meaning | Lesson |
|------|---------|--------|
| `.family` | A Riverpod provider modifier that parameterizes a provider by an argument, creating one cached instance per distinct parameter value — always pair with `.autoDispose` unless every possible parameter value's state should genuinely be cached forever. | [Provider & Riverpod](/flutter/en/state-management/provider-and-riverpod/) |
| federated plugin | Most first-party Flutter plugins today split into an app-facing package, a platform-interface package, and one implementation package per platform — quoting `docs.flutter.dev` directly: *"splitting the API of a plugin into a platform interface, independent platform implementations... and an app-facing interface."* You depend on the app-facing package; the right platform implementation resolves automatically. | [Platform Channels](/flutter/en/navigation/platform-channels/) |
| `final` (class modifier) | Forbids both `extends` and `implements` outside the declaring library — real error: *"can't be extended outside of its library because it's a final class."* The strictest of the four non-`sealed` modifiers: outside its library the type can only be constructed and used, never subtyped by either mechanism. | [Classes & Mixins](/flutter/en/dart-foundations/classes-and-mixins/) |
| flavors / schemes | Android **flavors** / iOS **schemes** let one codebase produce dev/staging/prod builds with different config (API endpoints, app IDs, icons) without branching code — paired with `--dart-define` to inject the per-environment values, e.g. `flutter build apk --flavor prod --dart-define=API_URL=...`. | [Build & Release](/flutter/en/tooling-and-production/build-and-release/) |
| `flutter analyze` / `flutter_lints` vs. `very_good_analysis` | `flutter analyze` runs the analyzer over the configured lint set. `flutter_lints` (**6.0.0**, the default) layers a small, low-friction set on top of `package:lints/recommended.yaml` — proven to genuinely **not** include the general `prefer_const_constructors` (only the narrower `..._in_immutables` variant), unlike `very_good_analysis` (**11.0.0**, 237 lines of rules), which ships it by default alongside a much stricter overall baseline. | [Project & Tooling](/flutter/en/tooling-and-production/project-and-tooling/) |
| `flutter doctor` | The first command to run when anything's off — diagnoses the SDK, every platform's device toolchain, and IDE plugins, naming the specific missing piece (an unaccepted Android license, a missing Xcode component) rather than a generic failure. Real output on this course's Mac: `Flutter (Channel stable, 3.47.5, ...)`, `Android toolchain (SDK 35.0.0)`, `Xcode 26.2`. | [Project & Tooling](/flutter/en/tooling-and-production/project-and-tooling/) |
| `FlutterError.onError` | Catches errors the **Flutter framework itself** raises (build/layout/paint) — the first of the two channels needed for production crash reporting; `runZonedGuarded` (below) catches the other half, uncaught async errors. Together they're the pairing this course proves catches "two different halves of Flutter's error surface." | [Production Concerns](/flutter/en/tooling-and-production/production-concerns/) |
| frame budget | To hit 60fps you have **~16.6ms** per frame across build→layout→paint→composite→raster; at 120Hz (many modern phones) that halves to **~8.3ms**. Jank is a frame that misses the budget — proven throughout the render-pipeline lesson to come from real, measurable costs (an allocated `Opacity` layer, an un-boundaried repaint), not a vague concern. | [Render Pipeline](/flutter/en/layout-and-rendering/render-pipeline/) |
| `Future` | A value that will exist later — the result of an async operation, unwrapped with `await`. `Future.wait([...])` runs several concurrently, resolving once all do, in **input order** not completion order; `eagerError: true` completes as soon as the *first* one fails instead of waiting for every future to settle (proven with real timing: default ~20ms wall-clock vs. `eagerError: true`'s under 30ms). | [Async in Dart](/flutter/en/dart-foundations/async-in-dart/) |
| `FutureBuilder` | Turns a `Future` into a synchronously-readable `AsyncSnapshot` your `build` reads via `connectionState` → `hasError` → `data`, in that order. The single most common bug: creating the `Future` **inside** `build` — proven directly, this re-triggers the work and resets the snapshot to `waiting` on every unrelated rebuild; create it once (`initState`/`late final`) instead. `snapshot.hasError` (a caught error from the source) and a `throw` inside your own `builder` callback are proven to be genuinely different failure modes — only the second crashes the build. | [Futures & Streams in the UI](/flutter/en/async-and-performance/futures-streams-in-ui/) |

| `SliverFillRemaining` | Inside a `CustomScrollView`, claims whatever viewport space is left after the other slivers — the sliver equivalent of `Expanded` inside a `Column`; `hasScrollBody: false` for content that shouldn't itself scroll (an empty-state message, a bottom-anchored button). | [Slivers & Scrolling](/flutter/en/layout-and-rendering/slivers-and-scrolling/) |
| `StatefulShellRoute.indexedStack` | Gives each branch of a bottom-navigation shell its **own nested `Navigator`**, keeping all branches alive simultaneously in an `IndexedStack` — proven directly: push a detail screen in tab A, switch to tab B and back, and the detail screen is still there. A plain `ShellRoute` shares **one** `Navigator` across branches instead — switching tabs doesn't push/pop anything, it just swaps which top-level route is active, so a per-branch back-stack is lost. | [Declarative Routing](/flutter/en/navigation/declarative-routing/) |
| `StatefulWidget` / `State` | `StatefulWidget` stays immutable like any widget; its mutable data lives in a separate `State` object held by the persistent **element** — proven directly: a parent rebuild with the same key/type keeps the exact same `State` instance (same fields), while a key or type change creates a fresh one from scratch. | [Stateless vs. Stateful](/flutter/en/widgets/stateless-vs-stateful/) |
| `StateNotifier` / `StateProvider` (legacy) | Riverpod's pre-3.0 mutable-state primitives — the migration guide marks them **legacy** in Riverpod 3, superseded by `Notifier`/`AsyncNotifier` (which this course uses throughout). Still present for migration compatibility, not the recommended starting point for new code. | [Provider & Riverpod](/flutter/en/state-management/provider-and-riverpod/) |
| `StatelessWidget` | UI that is a pure function of its constructor inputs — no mutable data of its own, `build` is all there is. Use for anything that doesn't change over time on its own. | [Stateless vs. Stateful](/flutter/en/widgets/stateless-vs-stateful/) |

## T

| Term | Meaning | Lesson |
|------|---------|--------|
| `testWidgets` variant | `variant: someTestVariant` runs the **same** test body once per value in a `TestVariant` — proven with a real `ValueVariant<String>({'en','th','ja'})`: one `testWidgets` call, three separately-reported test runs. `TargetPlatformVariant.all()` is the built-in variant for running one widget test across every `TargetPlatform` without hand-writing a loop. | [Testing](/flutter/en/tooling-and-production/testing/) |
| Ticker / `TickerProvider` | A `Ticker` fires a callback once per animation frame; `SingleTickerProviderStateMixin`/`TickerProviderStateMixin` supply the `vsync:` an `AnimationController` needs. An active `Ticker` left undisposed throws a real, debug-mode-only assert on element removal — the concrete cost `controller.dispose()` exists to avoid. | [Animations](/flutter/en/async-and-performance/animations/) |
| `Timer.run` (event-queue task) | A bare `Future(() {})` is secretly a `Timer.run`-based **event-queue** task, not a microtask — proven directly with real ordering: `scheduleMicrotask`/`await` continuations are true microtasks that fully drain first, before any `Timer`-based task runs, regardless of write order. | [Async in Dart](/flutter/en/dart-foundations/async-in-dart/) |
| `TransferableTypedData` | Hands off raw bytes between isolates **without copying** — ownership transfers instead (the sender's copy becomes unusable; `materialize()` on the sender throws after transfer), confirmed by `api.dart.dev`: *"can be moved between isolates, so sending it... will only take constant time."* Measured on this Mac at 10MB, the win over a plain `compute()` copy is small (fixed isolate-spawn overhead dominates at this size) — the real win shows up at much larger payloads or repeated isolate hops. | [Isolates & compute()](/flutter/en/async-and-performance/isolates-and-compute/) |
| the three trees | Widget tree (immutable description, rebuilt constantly, cheap), Element tree (the living, persistent instance — holds `State`, decides update-in-place vs. tear-down), Render tree (`RenderObject`s that actually lay out and paint — expensive, reused aggressively). Same type + no key at a tree position reuses the element (`createElement` runs once, `didUpdateWidget` on every rebuild, proven with a spy); a different key at the same position tears down and remounts (a fresh `createElement`). | [Widgets and the Tree](/flutter/en/widgets/widgets-and-the-tree/) |

## U

| Term | Meaning | Lesson |
|------|---------|--------|
| `unawaited_futures` | The lint catching a fire-and-forget `async` call (no `await`, no stored `Future`) — proven **not** included in this course's default `flutter_lints/flutter.yaml` (it's in the stricter template only). An error inside an un-awaited `Future` becomes uncaught, visible only to `runZonedGuarded`, never a surrounding `try`/`catch`. `unawaited(fn())` from `dart:async` is the real, no-op-at-runtime way to mark a fire-and-forget call as deliberate. | [Async in Dart](/flutter/en/dart-foundations/async-in-dart/) |
| `UniqueKey` | Forces Flutter to treat a widget as a completely new identity on demand, discarding the old element/`State` on purpose — proven directly: reassigning `UniqueKey()` on a rebuild stamps a fresh `State` (a new instance id), while a plain rebuild with no key change reuses the same `State`. Useful for "reset this form/field to blank" without a dedicated reset method. | [Keys](/flutter/en/widgets/keys/) |
| `use_build_context_synchronously` | The real analyzer lint firing when `context` (or anything derived from it) is used **after** an `await` inside an event handler, without a `mounted` guard in between — the widget may have been unmounted while the awaited work was pending, making that later context use unsafe. | [Build & BuildContext](/flutter/en/widgets/build-and-buildcontext/) |

## V

| Term | Meaning | Lesson |
|------|---------|--------|
| `ValueKey` | Identifies an element by a **data value** (an id, a string) rather than position — the standard fix for the reorder-loses-state bug: proven directly, `ValueKey(label)` makes a checkbox's checked state follow its label across a list swap, where no key left it stuck at the old position. | [Keys](/flutter/en/widgets/keys/) |
| `ValueNotifier` / `ValueListenableBuilder` | A narrower alternative to a naive "lift state up" `setState`: `ValueNotifier<T>` holds a value outside the widget-rebuild path, and only `ValueListenableBuilder`'s own `builder` rebuilds when it changes — proven directly with a build-counter test: a plain lifted `setState` reruns a non-listening sibling's `build` every single time (1→4 across three updates), while the equivalent `ValueListenableBuilder` sibling never moves off 1. | [Stateless vs. Stateful](/flutter/en/widgets/stateless-vs-stateful/) |

## W

| Term | Meaning | Lesson |
|------|---------|--------|
| `WillPopScope` (removed) | The pre-`PopScope` way to intercept the back gesture — deprecated, per its own doc-comment annotation quoted directly from the installed 3.47.5 SDK source. `PopScope` (above) is the real, current replacement, additionally required for predictive-back gesture compatibility. | [Navigator & Routes](/flutter/en/navigation/navigator-and-routes/) |

## Y–Z

| Term | Meaning | Lesson |
|------|---------|--------|
| `--obfuscate --split-debug-info` | Real `flutter build apk --release --obfuscate --split-debug-info=<dir>` obfuscates identifiers in the shipped binary and writes the real, un-obfuscated symbol mapping to `<dir>` separately, needed to later symbolize a real crash's obfuscated stack trace — proven with a real Android build on this Mac; a real, surfaced warning in that exact output notes the generated ELF library still contains unobfuscated **DWARF** debugging info unless `--strip` is also passed. `--obfuscate` alone, without the matching `--split-debug-info` output kept, is proven **not** enough to get readable crash reports later. | [Build & Release](/flutter/en/tooling-and-production/build-and-release/) |
| `--wasm` (`flutter build web --wasm`) | Compiles to WebAssembly instead of dart2js JS — real, reproducible numbers from this course's default counter app: `main.dart.js` (dart2js) **~1.8MB** vs. wasm output (`main.dart.wasm` + `main.dart.mjs`) **~1.4MB** total, genuinely smaller for this app (not a general rule). Real browser catch, quoted from `docs.flutter.dev`: reliable support needs **WasmGC**, which as of this course's SDK means Chromium/Chrome/Edge 119+ only — Safari and Firefox both have open compatibility bugs despite announced support, and Chrome on iOS (WebKit-based) doesn't support WasmGC at all. Also requires specific `Cross-Origin-Embedder-Policy`/`Cross-Origin-Opener-Policy` response headers from whatever serves the build. | [Build & Release](/flutter/en/tooling-and-production/build-and-release/) |
