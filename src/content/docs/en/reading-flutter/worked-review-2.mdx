## The feature

The prompt was: *"A photo gallery screen: a scrollable grid of photos that fade in, a decode step so we're not blocking the UI, and a chunked upload client with a progress panel underneath."* What follows is a first draft that looks reasonable at a skim -- it uses `CustomScrollView`/`SliverGrid` instead of a plain `GridView` (so it *looks* sliver-aware), reaches for `compute()` for the "heavy" work (so it *looks* isolate-aware), and animates each tile in. It has **10 real bugs**, several of them the kind that never show up on a quick scroll through a handful of photos. Read it the way the **[review checklist](/flutter/en/reading-flutter/review-checklist/)** recommends: correctness first (does the isolate/async code even work), then lifecycle (what leaks), then layout, then the platform-specific edges. Every claim below was run for real in this course's own probe (Flutter 3.47.5) -- real `flutter analyze`, real `flutter test`, a real `flutter build web`, and real timing on this Mac.

## The review walk

### 1. `compute()` closure capturing a `ReceivePort`

`decodePhotoReportingProgress` closes over `progress`, a `ReceivePort`, to "report progress back." `compute()` sends its argument to a background isolate as an isolate message -- and the closure itself is part of that message. A `ReceivePort` is a native, isolate-bound handle that cannot be copied across:

```dart
// test/gallery_app/decode_worker_test.dart
import 'dart:isolate';

import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/gallery_app/decode_worker.dart';

void main() {
  test('compute() closure capturing a ReceivePort throws the real isolate-message error', () async {
    final port = ReceivePort();
    addTearDown(port.close);

    await expectLater(
      decodePhotoReportingProgress(100, port),
      throwsA(
        isA<ArgumentError>().having(
          (e) => e.toString(),
          'message',
          contains('Illegal argument in isolate message'),
        ),
      ),
    );
  });
}
```

```text
✓ compute() closure capturing a ReceivePort throws the real isolate-message error

00:00 +1: All tests passed!
```

Same mechanism proven with the identical `ReceivePort`-capture repro in **[Isolates & compute()](/flutter/en/async-and-performance/isolates-and-compute/)**; a `compute()`/`Isolate.run` closure must only capture plain, sendable data (or nothing at all -- prefer a top-level or `static` function).

<SpotTheBug code={`Future<int> decodePhotoReportingProgress(int bytesLength, ReceivePort progress) {
  return compute((int len) {
    final capturedPort = progress; // captures a non-sendable object
    return _fakeDecodedByteCount(len);
  }, bytesLength);
}`}>
`progress` lives outside the closure passed to `compute()`, so Dart must serialize it as part of that closure to hand it to the background isolate -- and a `ReceivePort` (like a `Socket`, a `Timer`, or most class instances holding native resources) has no sendable representation. The fix is a function that captures nothing but its own parameters -- a top-level function, or a closure built entirely from primitives/collections.
</SpotTheBug>

### 2. Decode-adjacent work running synchronously on the calling isolate

`thumbnail_analysis.dart`'s `averageBrightness` -- meant to produce a quick placeholder color before the real image is ready -- is a plain, synchronous, per-pixel Dart loop with no `compute()`/`Isolate.run` around it at all. Call it from `build()` or a frame callback on a full-resolution photo and it blocks that isolate for the whole loop:

```dart
// test/gallery_app/thumbnail_analysis_timing_test.dart

import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/gallery_app/thumbnail_analysis.dart';

void main() {

    final stopwatch = Stopwatch()..start();
    averageBrightness(rgba);
    stopwatch.stop();

            'directly on the calling isolate blows the ~16.6ms frame '
            'budget on its own -- called from build() or a frame '
            'callback, this is a dropped frame, not just slow code');

```

```text

00:00 +1: All tests passed!
```

Measured on this Mac at **25ms** for one 12-megapixel buffer -- already past the **~16.6ms** frame budget proven in **[Render pipeline](/flutter/en/layout-and-rendering/render-pipeline/)**, before any real decode work or a slower device is even in the picture. ### 3. `AnimationController` never disposed

`_PhotoTileState` builds an `AnimationController` and starts it, but has no `dispose()` override at all:

```text
_PhotoTileState#75ce5(ticker active) was disposed with an active Ticker.
_PhotoTileState created a Ticker via its SingleTickerProviderStateMixin, but at the time dispose() was called on the mixin, that Ticker was still active. The Ticker must be disposed before calling super.dispose().
Tickers used by AnimationControllers should be disposed by calling dispose() on the AnimationController itself. Otherwise, the ticker will leak.
```

Same real error text already proven in **[Animations](/flutter/en/async-and-performance/animations/)** -- scroll a gallery grid and every tile that's ever built one of these leaks a `Ticker` when it scrolls out of the built range and gets disposed.

### 4. `Opacity` + `AnimatedBuilder` with the child built inline

`AnimatedBuilder`'s `builder` callback constructs `_TileBody` directly, instead of passing it through `AnimatedBuilder`'s own `child` parameter -- so it's rebuilt on every single animation tick, not just repainted. The second test in the same fence above proves it:

```text
tileBodyBuildCount first=1 after 2 ticks=3

00:00 +2: All tests passed!
```

Per **[Render pipeline](/flutter/en/layout-and-rendering/render-pipeline/)**, `Opacity` and `AnimatedOpacity`/`FadeTransition` cost the *same* compositing layer once non-zero -- the value a purpose-built widget like `FadeTransition` adds isn't a cheaper layer, it's not rebuilding the subtree that doesn't need to change every tick, proven above.

### 5. `cacheExtent` -- deprecated

`GalleryGrid` sets `cacheExtent: 500` directly on `CustomScrollView`. Checked against this SDK (Flutter 3.47.5):

```text
info • 'cacheExtent' is deprecated and shouldn't be used. Use scrollCacheExtent instead. This feature was deprecated after v3.41.0-0.0.pre. Try replacing the use of the deprecated member with the replacement • deprecated_member_use
```

Confirmed directly from `package:flutter`'s own source (`widgets/scroll_view.dart`): `cacheExtent` carries `@Deprecated('Use scrollCacheExtent instead. This feature was deprecated after v3.41.0-0.0.pre.')`. The replacement, `ScrollCacheExtent`, is a real type -- but it is **not** re-exported by `package:flutter/material.dart` (or `widgets.dart`), only by `package:flutter/rendering.dart`, so the fix needs that import too (see the corrected code).

### 6. Missing `RepaintBoundary` around the animated tile

<Callout title="Correction to a common example: a Column INSIDE a ListView does not crash">
If the AI's own fix for this had gone the *other* direction -- moving a `Column` inside a `ListView`'s children -- that would not have fixed anything, because that shape never crashes in the first place. Proven directly: `ListView(children: [Column(children: [...])])` renders fine; a `ListView` item is handed unbounded height so it can report its own size, and a `Column` receiving unbounded height falls back to sizing itself to its children. The real crash needs the *scrollable* to be the one receiving unbounded height from a non-flexible slot -- a bare `ListView`/`GridView`/`CustomScrollView` as a direct, non-`Expanded` child of a `Column`, exactly as `UploadPanel` does above.
</Callout>

### 8. `Image` without `cacheWidth`/`cacheHeight`

The AI's plan for each grid photo was plain `Image.network(url)`, with no decode-size hint. From `package:flutter`'s own `Image` documentation:

```text
The image is stored in memory in uncompressed form (so that it can be rendered). Large images
will use a lot of memory: a 4K image (3840x2160) will use over 30MB of RAM (assuming 32 bits per
pixel).

The Image.asset, Image.network, Image.file, and Image.memory constructors allow a custom decode
size to be specified through cacheWidth and cacheHeight parameters. The engine will then decode
and store the image at the specified size, instead of the image's natural size.

This can significantly reduce the memory usage. For example, a 4K image that will be rendered at
only 384x216 pixels (one-tenth the horizontal and vertical dimensions) would only use 330KB if
those dimensions are specified using the cacheWidth and cacheHeight parameters, a 100-fold
reduction in memory usage.
```

A 100x-membory-fold claim, quoted directly from the widget's own doc comment (`packages/flutter/lib/src/widgets/image.dart`) -- every grid tile decoding and caching a photo at its full camera resolution to display it at a 100px thumbnail is exactly the case this parameter exists for. The same doc comment notes `cacheWidth`/`cacheHeight` are **ignored** for `Image.network` specifically on the web platform, since the web engine delegates decoding to the browser.

| 1 | `compute()` closure captures a `ReceivePort` | Capture nothing but plain data -- proven: `Illegal argument in isolate message` otherwise |
| 2 | Per-pixel decode-adjacent loop runs on the calling isolate | Same `compute()`, applied correctly -- proven: 25ms > the 16.6ms frame budget uncorrected |

## What the reviewer writes in the PR

> Good bones, but this needs work before it ships -- 10 things:
>
> 1. **`compute()` closure captures a `ReceivePort`.** This throws `Illegal argument in isolate message` every time. Only plain data can cross into the background isolate.
> 2. **`averageBrightness` runs synchronously on whatever isolate calls it.** Measured at 25ms for a 12MP buffer on my machine -- that's a dropped frame on its own if it's ever called from `build()`. Wrap it in `compute()` like the decoder already (almost) does.
> 3. **No `dispose()` on `PhotoTile`'s `AnimationController`.** Scroll the grid and every tile that's ever built leaks a `Ticker`.
> 4. **`AnimatedBuilder` builds `_TileBody` inline.** Pass it through `child` instead -- right now it's reconstructed on every animation frame.
> 5. **`cacheExtent` is deprecated** as of 3.41 -- `scrollCacheExtent` replaces it, and it's a different import (`package:flutter/rendering.dart`).
> 6. **No `RepaintBoundary` on the tile.** In a real grid this means one animating tile forces every other tile sharing its canvas to repaint too.
> 7. **`ListView` inside `Column`, no `Expanded`, in `UploadPanel`.** Real crash, `Vertical viewport was given unbounded height`.
> 8. **`Image.network` with no `cacheWidth`/`cacheHeight`.** Per Flutter's own docs this is up to a 100x memory difference for a thumbnail-sized grid tile.
> 9. **`dart:io`'s `File` used with no platform guard.** Builds fine for web, throws `UnsupportedError` the moment it actually runs there.
> 10. **`_uploadAndGetProgress` called directly in `build()`.** Any unrelated rebuild re-fires the upload.
>
> None of these are a redesign -- happy to pair on the fixes.

## Mental Model

Three shapes repeat across this review. First: **"looks isolate-aware" isn't "is isolate-aware"** -- `compute()` appears twice in this PR, once broken by a captured `ReceivePort` and once entirely absent from a function that clearly needed it, and neither mistake shows up until you specifically test for it. Second: **a compiling, building app is not a working one** -- bugs 5 and 8 are analyzer-visible (a deprecation, a doc comment), but bug 9 compiles AND builds successfully for a platform it doesn't actually work on, which is a strictly harder trap than a build failure would be. Third: **every leak/trap in this review is invisible on a short, manual test** -- a few tiles on screen never leak enough tickers to notice, one rebuild rarely happens fast enough to see a reset progress bar, and nobody scrolls to tile 999 by hand. All ten bugs needed either a targeted test or a documented fact to surface, which is exactly the review checklist's point.

## Trade-offs

| Choice | Upside | Cost |
|---|---|---|
| `compute()` for CPU-bound work | Keeps the calling isolate responsive -- proven above with real timing | The closure must be free of anything non-sendable; easy to violate without an error until you run it |
| `FadeTransition` over manual `AnimatedBuilder` + `Opacity` | Child isn't rebuilt every tick, correct disposal semantics baked in | Less flexible than a hand-rolled builder for anything beyond a straight opacity ramp |
| `RepaintBoundary` per grid tile | Isolates each tile's repaint -- proven above | Each boundary is its own layer/memory allocation; fine per-tile, wasteful if applied to every leaf widget indiscriminately |
| `cacheWidth`/`cacheHeight` on every thumbnail | Large, real memory savings per Flutter's own docs | A fixed decode size; needs to be re-picked if the display size changes (e.g. a detail view) |

## Common Misconceptions

- **"If `flutter build web` succeeds, the app works on web."** Proven false above: `UploadClient` compiles and builds cleanly for web, and throws `UnsupportedError` the instant `uploadInChunks` actually runs there. A green build proves the code type-checks and bundles -- nothing about what it does at runtime on that platform.
- **"A `Column` inside a `ListView` is the dangerous nesting, not the other way around."** Corrected above with a direct test: `ListView(children: [Column(...)])` does not crash. The real crash needs the *scrollable* to be the one handed unbounded height from a non-flexible slot.
- **"`Opacity` inside `AnimatedBuilder` is cheaper than `FadeTransition` because it's 'simpler.'"** Both allocate the identical compositing layer once non-zero (proven in Render pipeline); the difference proven here is that the hand-rolled version also rebuilds its child on every tick, which `FadeTransition`'s `child` parameter avoids.
- **"`cacheWidth`/`cacheHeight` matter equally on every platform."** Per the widget's own doc comment, they're ignored specifically for `Image.network` on web, since the web engine delegates decoding to the browser.
