## The review walk

### 1. `MethodChannel` call with no `PlatformException`/`MissingPluginException` handling

`_load()` awaits `batteryChannel.invokeMethod` with no `try`/`catch` at all. The exact mechanism (and this exact channel/method shape) is proven in full in **[Platform channels](/flutter/en/navigation/platform-channels/)**; reproduced here for this app's own channel name:

```dart
// test/cross_app/battery_widget_test.dart
import 'package:flutter/services.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/cross_app/battery_widget.dart';

void main() {
  test('with no platform handler registered, invokeMethod throws the real MissingPluginException text', () async {
    TestWidgetsFlutterBinding.ensureInitialized();
    await expectLater(
      batteryChannel.invokeMethod<int>('getBatteryLevel'),
      throwsA(isA<MissingPluginException>().having(
        (e) => e.toString(),
        'message',
        'MissingPluginException(No implementation found for method getBatteryLevel on channel com.example.crossapp/battery)',
      )),
    );
  });
}
```

```text
✓ with no platform handler registered, invokeMethod throws the real MissingPluginException text

00:00 +1: All tests passed!
```

<SpotTheBug code={`Future<void> _load() async {
  final level = await batteryChannel.invokeMethod<int>('getBatteryLevel');
  setState(() => _level = level);
}`}>
Two real, common causes throw here: a `PlatformException` from the native side reporting a real failure (permission denied, hardware unavailable), and a `MissingPluginException` -- proven above -- whenever nothing is listening on that channel at all (the plugin isn't registered yet, the platform has no implementation, or in a test). Called from `initState` with no `await`, either one becomes an unhandled `Future` rejection with no user-facing error state at all. The fix wraps the call in `try { ... } on MissingPluginException { ... } on PlatformException catch (e) { ... }` and shows something instead of silently staying on "loading...".
</SpotTheBug>

### 2. `kIsWeb` as a conditional-import condition -- syntactically accepted, never actually switches

`platform_broken.dart` conditionally exports a web-safe implementation using `if (kIsWeb)`. This analyzes with **zero errors** -- Dart's conditional-import syntax is just `import/export '<default>' if (<dotted.identifier>) '<alt>';`, and any dotted identifier parses. The condition itself is checked against **compile-time environment declarations** (the same mechanism as `-D` defines and the built-in `dart.library.*` checks), which has nothing to do with `kIsWeb`, a runtime constant from `package:flutter/foundation.dart`. Proven by actually building for web and inspecting which branch was compiled in:

```text
$ flutter build web
...
✓ Built build/web

$ grep -o "SENTINEL_IO_IMPL_USED\|SENTINEL_WEB_IMPL_USED" build/web/main.dart.js | sort | uniq -c
   1 SENTINEL_IO_IMPL_USED
```

Built for **web**, and the compiled output only contains the sentinel from the `io`-branch implementation -- `if (kIsWeb)` never once selects the alternate `platform_web_impl.dart`, on any target, because `kIsWeb` isn't a declared environment key. (A separate, working version using `if (dart.library.html)` -- the real, compiler-recognized condition -- selects the correct branch on the identical build; see the corrected code.)

<Callout title="A second, smaller tell">
`flutter analyze` also flags `platform_broken.dart`'s own `import 'package:flutter/foundation.dart' show kIsWeb;` as `unused_import` -- the analyzer doesn't count `kIsWeb`'s appearance inside the conditional-export condition as a real use of the imported symbol, a small extra sign that the condition isn't wired to anything the analyzer treats as connected to that import at all.
</Callout>

### 3. `runZonedGuarded` as the only error handler -- misses framework errors entirely

The AI's `main.dart` wraps `runApp()` in `runZonedGuarded` and calls it done for error reporting. Proven directly against a widget that throws from `build()`:

```dart
// test/cross_app/zoned_error_demo_test.dart
import 'dart:async';

import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/cross_app/zoned_error_demo.dart';

void main() {
  testWidgets('runZonedGuarded around runApp does not see a build()-phase error', (tester) async {
    Object? caughtByZone;
    FlutterErrorDetails? caughtByFlutterError;

    final originalOnError = FlutterError.onError;
    FlutterError.onError = (details) => caughtByFlutterError = details;
    addTearDown(() => FlutterError.onError = originalOnError);

    await runZonedGuarded(() async {
      await tester.pumpWidget(const MaterialApp(home: BrokenBuild()));
    }, (error, stack) {
      caughtByZone = error;
    });

    expect(caughtByFlutterError, isNotNull,
        reason: 'FlutterError.onError genuinely saw the build() error');
    expect(caughtByZone, isNull,
        reason: 'the framework catches build()/layout()/paint() errors '
            'internally and routes them to FlutterError.onError BEFORE '
            'they could ever reach an ambient Zone -- runZonedGuarded '
            'never saw this error at all, even though it wraps runApp()');
  });
}
```

```text
✓ runZonedGuarded around runApp does not see a build()-phase error

00:00 +1: All tests passed!
```

Per **[Production concerns](/flutter/en/tooling-and-production/production-concerns/)**, this is doubly out of date: Flutter's own **3.3 release notes** state plainly that `PlatformDispatcher.onError` replaces the need for a custom `Zone` at all (*"custom `Zone`s were detrimental to a number of optimizations in Dart's core libraries, which slowed down application start-up time"*), and framework build/layout/paint errors were never a `Zone`'s job to catch in the first place -- `FlutterError.onError` is the only hook that sees them, proven above and in that lesson.

### 4. `print()` calls, on the assumption they're "stripped in release"

Already corrected in **[Production concerns](/flutter/en/tooling-and-production/production-concerns/)**, reading the installed SDK source directly (`~/flutter/packages/flutter/lib/src/foundation/print.dart`): neither `print` nor `debugPrint` is removed in a release build. `debugPrint`'s own doc comment states it plainly: *"The `debugPrint` function logs to console even in release mode."* Every `print()` call left in "for debugging" in this PR ships to real users' device logs in the release build, exactly as written -- the real reason to prefer `debugPrint` over bare `print` is throttling (avoiding Android log-buffer data loss under high-volume output), not release-stripping.

### 6. `analysis_options.yaml` assumes `prefer_const_constructors` ships with `flutter_lints`

It doesn't. Already corrected in **[Rebuilds & performance](/flutter/en/async-and-performance/rebuilds-and-performance/)**, confirmed by reading `flutter_lints` 6.0.0's own `lib/flutter.yaml` directly: it adds only the narrower `prefer_const_constructors_in_immutables` (which only fires on classes explicitly annotated `@immutable`, not the general `StatelessWidget`/`StatefulWidget` case this app actually has). `package:lints/recommended.yaml`, `flutter_lints`' own base, doesn't include the general rule either -- confirmed the same way. `very_good_analysis` does ship the general rule, per the same cited lesson; `flutter_lints` alone does not, and the comment in this PR's `analysis_options.yaml` states the opposite of what's actually enabled.

### 8. `PopScope`/`WillPopScope` mixed in the same app

## The corrected code

```dart
// lib/cross_app_fixed/battery_widget.dart
import 'package:flutter/material.dart';
import 'package:flutter/services.dart';

const batteryChannel = MethodChannel('com.example.crossapp/battery');

class BatteryDisplay extends StatefulWidget {
  const BatteryDisplay({super.key});
  @override
  State<BatteryDisplay> createState() => _BatteryDisplayState();
}

class _BatteryDisplayState extends State<BatteryDisplay> {
  int? _level;
  String? _error;

  @override
  void initState() {
    super.initState();
    _load();
  }

  Future<void> _load() async {
    try {
      final level = await batteryChannel.invokeMethod<int>('getBatteryLevel');
      if (!mounted) return;
      setState(() => _level = level);
    } on MissingPluginException {
      if (!mounted) return;
      setState(() => _error = 'Battery info is not available on this platform');
    } on PlatformException catch (e) {
      if (!mounted) return;
      setState(() => _error = 'Battery info unavailable: ${e.message}');
    }
  }

  @override
  Widget build(BuildContext context) {
    if (_error != null) return Text(_error!);
    return Text(_level == null ? 'loading...' : 'Battery: $_level%');
  }
}
```

## Mental Model

Two things repeat across this whole review. First: **plausible-looking APIs that don't do what they look like they do** -- `if (kIsWeb)` inside a conditional import parses and analyzes cleanly, `runZonedGuarded` genuinely does catch *some* errors, a `--dart-define` genuinely is a real mechanism -- each one is real Dart/Flutter surface, just not wired to the specific job the AI used it for. Second: **claims that would be easy to check and weren't** -- "print is stripped in release," "`flutter_lints` includes `prefer_const_constructors`" are both one grep into the installed source away from being falsified, and both are already-corrected claims elsewhere in this course, for exactly that reason. Across all nine bugs, none of them are hard to fix once found -- the entire review is about *finding* them, not fixing them.

## Trade-offs

| Choice | Upside | Cost |
|---|---|---|
| Conditional imports (`if (dart.library.X)`) over a runtime `kIsWeb` branch inside one file | Genuinely swaps implementations per compile target -- proven above | The condition vocabulary is narrow (`dart.library.*`, environment declarations) -- no arbitrary runtime logic |
| `FlutterError.onError` + `PlatformDispatcher.instance.onError`, no `Zone` | Matches Flutter's own current guidance; avoids the startup cost of a custom `Zone` | Two callbacks to wire instead of one wrapper -- easy to add only one and think you're covered |
| `--dart-define` for environment config | Compile-time constant, no runtime parsing, no secret committed to source | A silent no-op if the key doesn't match on either side -- no error, just the default |
| `Semantics`/`meetsGuideline` in tests | Catches a real, specific accessibility gap mechanically, in CI, with no device | Only covers what the built-in guidelines check, not a substitute for real screen-reader testing |

## Common Misconceptions

- **"`kIsWeb` works as a conditional-import condition because it's `true`/`false` at compile time."** Disproven above with a real `flutter build web` + compiled-output inspection: conditional imports only understand `dart.library.*` checks and declared environment keys, not arbitrary Dart constants, however compile-time-ish they look.
- **"`print()`/`debugPrint()` calls are automatically removed in release builds."** Disproven directly from the installed SDK source, cited above from Production concerns: neither is stripped; `debugPrint`'s own doc comment says it logs "even in release mode."
- **"`runZonedGuarded` around `runApp()` catches all errors, so `FlutterError.onError` is optional."** Disproven above with a real test: a `build()`-phase error never reaches the zone's handler at all, because the framework intercepts and routes it to `FlutterError.onError` first.
- **"`flutter_lints` is a strict, opinionated preset that includes the obvious performance rules like `prefer_const_constructors`."** Disproven by reading its own `lib/flutter.yaml`: it adds a short, deliberately narrow list on top of `package:lints/recommended.yaml`, and `prefer_const_constructors` (the general rule, not the `_in_immutables` variant) isn't on it.
