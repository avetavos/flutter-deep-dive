## State & lifecycle

### 1. Forgot `ProviderScope`

Riverpod's `ref.watch`/`ref.read` need a `ProviderContainer` to read from. `ProviderScope` is the widget that creates one and makes it reachable. Skip it, and every `ConsumerWidget` throws the moment it tries to read a provider.

```dart
// lib/ai-bug-catalog/01-provider-scope.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final nameProvider = Provider<String>((ref) => 'Milo');

class NameOnly extends ConsumerWidget {
  const NameOnly({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final name = ref.watch(nameProvider);
    return Text(name);
  }
}

// AI-generated: forgot to wrap the app in ProviderScope.
Widget buggyApp() => const MaterialApp(home: Scaffold(body: NameOnly()));
```

**Symptom — real `flutter test` failure, captured fresh for this module:**

```dart
// test/ai-bug-catalog/01-provider-scope_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/01-provider-scope.dart';

void main() {
  testWidgets('no ProviderScope -> throws', (tester) async {
    await tester.pumpWidget(buggyApp());
    final exception = tester.takeException();
    expect(exception, isA<StateError>());
    expect(exception.toString(), contains('No ProviderScope found'));
  });
}
```

```text
✓ no ProviderScope -> throws
00:00 +1: All tests passed!
```

The real exception is a `StateError` with message **"Bad state: No ProviderScope found"**.

**Fix:**

```dart
Widget fixedApp() => const ProviderScope(
      child: MaterialApp(home: Scaffold(body: NameOnly())),
    );
```

**Caught by:** a `riverpod_lint` `missing_provider_scope` finding (proven live in **[Verification Tools](/flutter/en/reading-flutter/verification-tools/)**), or the crash on the very first screen that reads a provider.

### 2. `setState` after `await` with no `mounted` guard

A `State` can be disposed (user navigates away, list item scrolled out of a lazily-built list) while a `Future` it kicked off is still pending. When it resolves and calls `setState`, there is no widget left to rebuild.

```dart
// lib/ai-bug-catalog/02-mounted-guard.dart
import 'package:flutter/material.dart';

class BuggyLoader extends StatefulWidget {
  const BuggyLoader({super.key, required this.future});
  final Future<String> future;
  @override
  State<BuggyLoader> createState() => _BuggyLoaderState();
}

class _BuggyLoaderState extends State<BuggyLoader> {
  String _text = 'loading';
  @override
  void initState() {
    super.initState();
    // AI-generated: no `mounted` guard after the await.
    widget.future.then((value) => setState(() => _text = value));
  }

  @override
  Widget build(BuildContext context) => Text(_text);
}
```

**Symptom — real, unedited `flutter test` failure, captured fresh for this module:**

```text
setState() called after dispose(): _BuggyLoaderState#5aa37(lifecycle state: defunct, not mounted)
This error happens if you call setState() on a State object for a widget that no longer appears in
the widget tree (e.g., whose parent widget no longer includes the widget in its build). This error
can occur when code calls setState() from a timer, from an animation callback, or after an
asynchronous operation (such as an awaited network request or other Future) completes after the
widget has been removed from the tree.
The preferred solution is to cancel the timer or stop listening to the animation in the dispose()
callback. Another solution is to check the "mounted" property of this object before calling
setState() to ensure the object is still in the tree.
```

**Fix, proven passing:**

```dart
// lib/ai-bug-catalog/02-mounted-guard-fixed.dart
import 'package:flutter/material.dart';

class FixedLoader extends StatefulWidget {
  const FixedLoader({super.key, required this.future});
  final Future<String> future;
  @override
  State<FixedLoader> createState() => _FixedLoaderState();
}

class _FixedLoaderState extends State<FixedLoader> {
  String _text = 'loading';
  @override
  void initState() {
    super.initState();
    widget.future.then((value) {
      if (!mounted) return;
      setState(() => _text = value);
    });
  }

  @override
  Widget build(BuildContext context) => Text(_text);
}
```

```dart
// test/ai-bug-catalog/02-mounted-guard-fixed_test.dart
import 'dart:async';
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/02-mounted-guard-fixed.dart';

void main() {
  testWidgets('mounted-guarded setState after dispose is a silent no-op', (tester) async {
    final completer = Completer<String>();
    await tester.pumpWidget(MaterialApp(home: FixedLoader(future: completer.future)));
    await tester.pumpWidget(const MaterialApp(home: SizedBox()));
    completer.complete('Milo');
    await tester.pump();
    expect(tester.takeException(), isNull);
  });
}
```

```text
✓ mounted-guarded setState after dispose is a silent no-op
00:00 +1: All tests passed!
```

**Caught by:** nothing automatic — `flutter analyze` sees a perfectly valid method call either way. Only a widget disposed mid-`await` surfaces it, in a **[Testing](/flutter/en/tooling-and-production/testing/)** suite or in production.

### 3. `setState` called from a sibling's `build()` (cross-sibling)

A widget that calls a callback synchronously from inside its own `build()`, and that callback calls `setState` on a *different* widget that is still mid-build, hits Flutter's "don't mutate what you're building" guard.

```dart
// lib/ai-bug-catalog/03-setstate-during-build.dart
import 'package:flutter/material.dart';

class Reporter extends StatelessWidget {
  const Reporter({super.key, required this.onBuild});
  final VoidCallback onBuild;
  @override
  Widget build(BuildContext context) {
    // AI-generated: reports "I built" straight from build(), synchronously.
    onBuild();
    return const SizedBox.shrink();
  }
}

class BuggyParent extends StatefulWidget {
  const BuggyParent({super.key});
  @override
  State<BuggyParent> createState() => _BuggyParentState();
}

class _BuggyParentState extends State<BuggyParent> {
  int _count = 0;
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        Text('$_count'),
        if (_count == 0) Reporter(onBuild: () => setState(() => _count++)),
      ],
    );
  }
}
```

**Symptom — real, unedited output, captured fresh for this module:**

```text
setState() or markNeedsBuild() called during build.
This BuggyParent widget cannot be marked as needing to build because the framework is already in the
process of building widgets. A widget can be marked as needing to be built during the build phase
only if one of its ancestors is currently building. This exception is allowed because the framework
builds parent widgets before children, which means a dirty descendant will always be built.
The widget on which setState() or markNeedsBuild() was called was:
  BuggyParent
The widget which was currently being built when the offending call was made was:
  Reporter
```

**Fix, proven passing:** defer the `setState` past the current build phase with `addPostFrameCallback`.

```dart
// lib/ai-bug-catalog/03-setstate-during-build-fixed.dart
import 'package:flutter/material.dart';

class FixedParent extends StatefulWidget {
  const FixedParent({super.key});
  @override
  State<FixedParent> createState() => _FixedParentState();
}

class _FixedParentState extends State<FixedParent> {
  int _count = 0;
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        Text('$_count'),
        if (_count == 0)
          _Reporter(
            onBuild: () => WidgetsBinding.instance
                .addPostFrameCallback((_) => setState(() => _count++)),
          ),
      ],
    );
  }
}

class _Reporter extends StatelessWidget {
  const _Reporter({required this.onBuild});
  final VoidCallback onBuild;
  @override
  Widget build(BuildContext context) {
    onBuild();
    return const SizedBox.shrink();
  }
}
```

```text
✓ deferring to addPostFrameCallback does not throw
00:00 +1: All tests passed!
```

**Caught by:** the framework, immediately and loudly — but only once this exact widget actually builds while its target is mid-build. A test that only pumps once and never triggers the reporting path misses it entirely.

### 4. `late` field read before it is assigned

`late` defers a field's initialization but does not change *when* callers expect to read it — an AI assistant that copies a `late` field without auditing every branch that might read it before the assigning method has run ships a real crash on first read, not first write.

```dart
// lib/ai-bug-catalog/04-late-field.dart
class Session {
  // AI-generated: assumed `configure()` always runs before `token` is read,
  // but nothing enforces that ordering.
  late String token;

  void configure(String value) => token = value;
}
```

**PROOF:**

```dart
// test/ai-bug-catalog/04-late-field_test.dart
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/04-late-field.dart';

void main() {
  test('reading a late field before it is set throws LateInitializationError', () {
    final session = Session();
    expect(() => session.token, throwsA(isA<Error>()));
  });

  test('configuring first makes the read safe', () {
    final session = Session()..configure('abc123');
    expect(session.token, 'abc123');
  });
}
```

```text
✓ reading a late field before it is set throws LateInitializationError
✓ configuring first makes the read safe
00:00 +2: All tests passed!
```

**Fix:** either make the field nullable and check for `null`, give it a real default, or make the constructor require the value instead of a separate `configure()` step.

**Caught by:** nothing static — `late` is a promise to the compiler, not a guarantee the analyzer checks. Only a real read on an unconfigured instance throws, and it throws at the READ, not at the skipped assignment, which makes the stack trace point at an innocent-looking line far from the actual bug.

### 5. `StateProvider`/`StateNotifierProvider` imported as if they were still top-level Riverpod 3 API

AI training data spans Riverpod 2, where `StateProvider` and `StateNotifierProvider` were front-and-center in the main `flutter_riverpod.dart` export. Riverpod 3 moved both (plus `ChangeNotifierProvider`) behind an explicit `legacy.dart` import — they still exist, they just are not where an AI assistant trained on older docs expects.

```dart
// lib/ai-bug-catalog/05-state-provider.dart — @expect-error StateProvider moved behind package:flutter_riverpod/legacy.dart in Riverpod 3; the main export no longer has it
import 'package:flutter_riverpod/flutter_riverpod.dart';

// AI-generated (trained on Riverpod 2 docs).
final counterProvider = StateProvider<int>((ref) => 0);
```

**Symptom — real `flutter analyze` diagnostic, captured fresh against `flutter_riverpod` 3.4.3:**

```text
error • The function 'StateProvider' isn't defined. Try importing the library that defines
'StateProvider', correcting the name to the name of an existing function, or defining a function
named 'StateProvider' • lib/ai-bug-catalog/05-state-provider.dart:5:25 • undefined_function
```

**Fix, analyzes clean:**

```dart
// lib/ai-bug-catalog/05-state-provider-fixed.dart
import 'package:flutter_riverpod/legacy.dart';

// Still works in Riverpod 3, but only via the explicit legacy import --
// prefer NotifierProvider/@riverpod codegen for new code instead.
final counterProvider = StateProvider<int>((ref) => 0);
```

**Caught by:** `flutter analyze` — but only after the reader already knows to look, since the error message names a real function that genuinely does not exist under that import, giving no hint that it moved rather than vanished.

## Widget tree & keys

### 6. No `key` on a reorderable list of stateful children

Without a `key`, Flutter matches a rebuilt widget to its `State` by **type and position**, not identity. Reorder the list, and each `State` object stays pinned to its screen position instead of following its data.

```dart
// lib/ai-bug-catalog/06-missing-key.dart
import 'package:flutter/material.dart';

class ColorBox extends StatefulWidget {
  const ColorBox({super.key, required this.label});
  final String label;
  @override
  State<ColorBox> createState() => _ColorBoxState();
}

class _ColorBoxState extends State<ColorBox> {
  bool _tapped = false;
  @override
  Widget build(BuildContext context) {
    return GestureDetector(
      onTap: () => setState(() => _tapped = true),
      child: Text(_tapped ? '${widget.label} (tapped)' : widget.label),
    );
  }
}

// AI-generated: no key, so Flutter matches by TYPE + POSITION, not identity.
class BuggyList extends StatelessWidget {
  const BuggyList({super.key, required this.labels});
  final List<String> labels;
  @override
  Widget build(BuildContext context) {
    return Column(children: [for (final l in labels) ColorBox(label: l)]);
  }
}
```

**PROOF:**

```dart
// test/ai-bug-catalog/06-missing-key_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/ai-bug-catalog/06-missing-key.dart';

void main() {
  testWidgets('no key: tapped state sticks to POSITION, not the item', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: BuggyList(labels: ['Milo', 'Rex'])));
    await tester.tap(find.text('Milo'));
    await tester.pump();
    expect(find.text('Milo (tapped)'), findsOneWidget);

    // Reorder: Rex now occupies position 0. No key -> Flutter reuses the
    // SAME State object for position 0 -- the "tapped" flag follows the
    // POSITION, not Milo.
    await tester.pumpWidget(const MaterialApp(home: BuggyList(labels: ['Rex', 'Milo'])));
    expect(find.text('Rex (tapped)'), findsOneWidget);
    expect(find.text('Milo (tapped)'), findsNothing);
  });
}
```

```text
✓ no key: tapped state sticks to POSITION, not the item
00:00 +1: All tests passed!
```

**Fix, proven passing:** a `ValueKey` per item ties the `State` to the DATA, not the position.

```dart
// lib/ai-bug-catalog/06-missing-key-fixed.dart
import 'package:flutter/material.dart';

class ColorBox extends StatefulWidget {
  const ColorBox({super.key, required this.label});
  final String label;
  @override
  State<ColorBox> createState() => _ColorBoxState();
}

class _ColorBoxState extends State<ColorBox> {
  bool _tapped = false;
  @override
  Widget build(BuildContext context) {
    return GestureDetector(
      onTap: () => setState(() => _tapped = true),
      child: Text(_tapped ? '${widget.label} (tapped)' : widget.label),
    );
  }
}

class FixedList extends StatelessWidget {
  const FixedList({super.key, required this.labels});
  final List<String> labels;
  @override
  Widget build(BuildContext context) {
    return Column(children: [for (final l in labels) ColorBox(key: ValueKey(l), label: l)]);
  }
}
```

```text
✓ ValueKey: tapped state stays attached to the correct item
00:00 +1: All tests passed!
```

**Caught by:** nothing automatic — this renders correctly on the first pass every time; only a manual reorder-then-inspect during review (or a regression test seeded with a reorder step) catches it.

### 7. The same `GlobalKey` reused across sibling widgets

An AI assistant that reaches for a single, module-level `GlobalKey` to mean "the currently featured item" — assuming only one widget will ever hold it at a time — breaks the moment two widgets carrying that key exist in the same frame.

```dart
// lib/ai-bug-catalog/07-global-key-reused.dart
import 'package:flutter/material.dart';

// AI-generated: ONE GlobalKey reused for "the featured item".
final featuredKey = GlobalKey();

class BuggyTwoPanes extends StatelessWidget {
  const BuggyTwoPanes({super.key});
  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        Container(key: featuredKey, width: 100, height: 100, color: Colors.blue),
        Container(key: featuredKey, width: 100, height: 100, color: Colors.red),
      ],
    );
  }
}
```

**Symptom — real, unedited `flutter test` failure, captured fresh for this module:**

```text
Duplicate keys found.
If multiple keyed widgets exist as children of another widget, they must have unique keys.
Row(direction: horizontal, mainAxisAlignment: start, crossAxisAlignment: center) has multiple
children with key [GlobalKey#52079].
```

**Fix, proven passing:** a `UniqueKey()` (or no key at all, if identity across rebuilds doesn't matter) per widget.

```dart
// lib/ai-bug-catalog/07-global-key-reused-fixed.dart
import 'package:flutter/material.dart';

class FixedTwoPanes extends StatelessWidget {
  const FixedTwoPanes({super.key});
  @override
  Widget build(BuildContext context) {
    return Row(
      children: [
        Container(key: UniqueKey(), width: 100, height: 100, color: Colors.blue),
        Container(key: UniqueKey(), width: 100, height: 100, color: Colors.red),
      ],
    );
  }
}
```

```text
✓ a distinct key per widget does not throw
00:00 +1: All tests passed!
```

**Caught by:** the framework, immediately and loudly, the instant two widgets carrying the same key exist in one build — but only that specific arrangement (siblings, or two branches built the same frame); a `GlobalKey` reused across builds that never overlap in time can hide for much longer.

### 8. `Scaffold.of(context)` called with the `Scaffold`'s own build context

`Scaffold.of(context)` needs a context that is a **descendant** of the `Scaffold` — the context the `Scaffold` widget's own `build()` method receives is an ancestor of it, not a descendant, so the lookup fails.

```dart
// lib/ai-bug-catalog/08-scaffold-of.dart
import 'package:flutter/material.dart';

// AI-generated: calls Scaffold.of(context) with the SAME context the
// Scaffold itself was built with.
class BuggyPage extends StatelessWidget {
  const BuggyPage({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Buggy')),
      body: Center(
        child: ElevatedButton(
          onPressed: () => Scaffold.of(context).showBottomSheet(
            (_) => const SizedBox(height: 100, child: Text('Sheet')),
          ),
          child: const Text('Open sheet'),
        ),
      ),
    );
  }
}
```

**Symptom — real, unedited `flutter test` failure, captured fresh for this module:**

```text
Scaffold.of() called with a context that does not contain a Scaffold.
No Scaffold ancestor could be found starting from the context that was passed to Scaffold.of().
This usually happens when the context provided is from the same StatefulWidget as that whose build
function actually creates the Scaffold widget being sought.
```

**Fix, proven passing:** a `Builder` introduces a fresh context that IS a `Scaffold` descendant.

```dart
// lib/ai-bug-catalog/08-scaffold-of-fixed.dart
import 'package:flutter/material.dart';

class FixedPage extends StatelessWidget {
  const FixedPage({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Fixed')),
      body: Center(
        child: Builder(
          builder: (innerContext) => ElevatedButton(
            onPressed: () => Scaffold.of(innerContext).showBottomSheet(
              (_) => const SizedBox(height: 100, child: Text('Sheet')),
            ),
            child: const Text('Open sheet'),
          ),
        ),
      ),
    );
  }
}
```

```text
✓ Scaffold.of(context) from a Builder descendant works
00:00 +1: All tests passed!
```

**Caught by:** nothing until the button is actually tapped — this compiles and even *builds* fine; the lookup only runs, and fails, when the callback fires.

## Layout

### 9. `ListView` given unbounded height by a plain `Column`

`Column` gives its children **unbounded height** along the main axis. `ListView` needs a bounded height to know how big its viewport is. Drop one straight into the other with nothing between them, and layout fails.

```dart
// lib/ai-bug-catalog/09-unbounded-listview.dart
import 'package:flutter/material.dart';

// AI-generated: a ListView dropped straight into a Column.
class BuggyPage extends StatelessWidget {
  const BuggyPage({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const Text('Header'),
        ListView(children: const [Text('one'), Text('two'), Text('three')]),
      ],
    );
  }
}
```

**Symptom — real, unedited output, captured fresh for this module:**

```text
Vertical viewport was given unbounded height.
Viewports expand in the scrolling direction to fill their container. In this case, a vertical
viewport was given an unlimited amount of vertical space in which to expand. This situation
typically happens when a scrollable widget is nested inside another scrollable widget.
```

**Fix, proven passing:** `Expanded` gives the `ListView` a bounded height — whatever space is left in the `Column`. **The real rule, precisely:** an unbounded-height ancestor (a `Column`'s main axis) needs a bounded box SOMEWHERE between it and a scrollable/flexible child. The reverse direction — a `Column` *inside* a `ListView` — needs nothing extra at all: a scrollable already gives its children a bounded cross-axis and unbounded main-axis, exactly what a naturally-sized `Column` wants.

```dart
// lib/ai-bug-catalog/09-unbounded-listview-fixed.dart
import 'package:flutter/material.dart';

class FixedPage extends StatelessWidget {
  const FixedPage({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const Text('Header'),
        Expanded(
          child: ListView(children: const [Text('one'), Text('two'), Text('three')]),
        ),
      ],
    );
  }
}

// The reverse needs NO extra widget:
class ColumnInsideListView extends StatelessWidget {
  const ColumnInsideListView({super.key});
  @override
  Widget build(BuildContext context) {
    return ListView(children: [Column(children: const [Text('a'), Text('b'), Text('c')])]);
  }
}
```

```text
✓ Expanded around the ListView fixes it
✓ a Column INSIDE a ListView needs no extra widget at all
00:00 +2: All tests passed!
```

**Caught by:** the framework, immediately and loudly. The nuance to catch in review is the DIRECTION — the same fix pattern is often over-applied to the reverse case, which never needed it.

### 10. `Expanded` used outside a `Flex`

`Expanded` relies on `ParentData` that only a `Row`/`Column`/`Flex` sets up for its direct children. Placed inside a `Center`, a `Container`, or anything else, it fails.

```dart
// lib/ai-bug-catalog/10-expanded-outside-flex.dart
import 'package:flutter/material.dart';

// AI-generated: Expanded directly inside a Center, which is not a Flex.
class BuggyBox extends StatelessWidget {
  const BuggyBox({super.key});
  @override
  Widget build(BuildContext context) {
    return Center(child: Expanded(child: Container(color: Colors.blue)));
  }
}
```

**Symptom — real, unedited output, captured fresh for this module:**

```text
Incorrect use of ParentDataWidget.
The ParentDataWidget Expanded(flex: 1) wants to apply ParentData of type FlexParentData to a
RenderObject, which has been set up to accept ParentData of incompatible type BoxParentData.
Usually, this means that the Expanded widget has the wrong ancestor RenderObjectWidget. Typically,
Expanded widgets are placed directly inside Flex widgets.
The offending Expanded is currently placed inside a Center widget.
```

**Fix, proven passing:**

```dart
// lib/ai-bug-catalog/10-expanded-outside-flex-fixed.dart
import 'package:flutter/material.dart';

class FixedBox extends StatelessWidget {
  const FixedBox({super.key});
  @override
  Widget build(BuildContext context) {
    return Row(children: [Expanded(child: Container(color: Colors.blue))]);
  }
}
```

```text
✓ Expanded is a child of a Row -- lays out fine
00:00 +1: All tests passed!
```

**Caught by:** the framework, immediately, and the error message even names the exact ancestor it found instead — the fastest diagnostic in this whole catalog to fix once seen, but the message alone doesn't say "wrap in a Row/Column," a reader still has to know that rule.

### 11. `RenderFlex` overflow from fixed-size children with no escape hatch

A `Row`/`Column` of fixed-size children that together exceed the available space, with no `Expanded`/`Flexible`/scrolling to absorb the difference, overflows — visibly, in a debug build (the yellow-and-black stripes), and as a real assertion underneath.

```dart
  const BuggyRow({super.key});

      children: List.generate(
        20,
        (i) => Container(width: 100, height: 40, color: Colors.primaries[i % Colors.primaries.length]),
      ),
    );
  }
}
```

**Symptom — real, unedited output, captured fresh for this module:**

```text
A RenderFlex overflowed by 1200 pixels on the right.
The overflowing RenderFlex has an orientation of Axis.horizontal.
```

### 13. `compute()` closure capturing a `BuildContext`

Modern Dart's `compute()` runs on `Isolate.run`, which genuinely can send well-behaved closures across the isolate boundary — a closure capturing a plain `int`, even a bound instance method, crosses fine on this course's pinned Dart 3.13.4. What still cannot cross is anything reachable from the widget tree: a `BuildContext` transitively reaches a `Zone`, and a `Zone` is never sendable.

```dart
// lib/ai-bug-catalog/13-compute-context.dart

    return const SizedBox();

}
```

### 21. `FlutterError.onError` set with no `runZonedGuarded` (or vice versa)

`FlutterError.onError` only fires for errors the FRAMEWORK catches — during build, layout, and paint. An error thrown from a bare `Future`, a `Timer`, or any plain async code outside the framework's own try/catch points never reaches it at all.

```dart
// lib/ai-bug-catalog/21-zone-errors.dart
import 'dart:async';

// AI-generated: sets FlutterError.onError, assumes that's "global error

Future<void> triggerAsyncErrorOutsideFramework() {

}
```

**Fix, proven passing:** `runZonedGuarded` wraps the WHOLE zone, catching errors `FlutterError.onError` never sees.

```dart

  runZonedGuarded(body, onError);
}
```

```text
AnimationController itself. Otherwise, the ticker will leak.
```

**Fix, proven passing:**

```dart
// lib/ai-bug-catalog/22-animation-controller-fixed.dart
import 'package:flutter/material.dart';

class FixedSpinner extends StatefulWidget {
  const FixedSpinner({super.key});
  @override
  State<FixedSpinner> createState() => _FixedSpinnerState();
}

class _FixedSpinnerState extends State<FixedSpinner> with SingleTickerProviderStateMixin {
  late final AnimationController _controller =
      AnimationController(vsync: this, duration: const Duration(seconds: 1))..repeat();

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) =>
      RotationTransition(turns: _controller, child: const Icon(Icons.sync));
}
```

```text
✓ disposing the controller in dispose() leaves no leaked ticker
00:00 +1: All tests passed!
```

**Caught by:** `flutter_test` itself, unconditionally, if the widget is ever torn down in a test at all — but a widget that is simply never disposed during a short manual demo session never trips it, and the leak (a live Ticker firing frames forever) keeps costing CPU and battery in production regardless.

### 23. `Opacity(opacity: 1.0)` still allocates a real compositing layer

The `Opacity` widget's own doc comment says "Values 1.0 and 0.0 are painted with a fast path" — which is true, but only describes the PAINT cost. Reading `RenderOpacity`'s actual source: `isRepaintBoundary => alwaysNeedsCompositing`, and `alwaysNeedsCompositing => child != null && _alpha > 0`. That is TRUE for `opacity: 1.0` (alpha 255) exactly as much as for `opacity: 0.5` — only `opacity: 0.0` (alpha 0) skips compositing entirely. `Opacity(opacity: 1.0)` is not free; it is a real repaint boundary with a real `OpacityLayer`.

**PROOF — read directly off the live `RenderObject`, not assumed from the doc comment:**

```dart
// test/ai-bug-catalog/23-opacity-layer_test.dart
import 'package:flutter/material.dart';
import 'package:flutter/rendering.dart';
import 'package:flutter_test/flutter_test.dart';

void main() {
  testWidgets('Opacity(opacity: 1.0) is STILL a repaint boundary', (tester) async {
    await tester.pumpWidget(
      const MaterialApp(home: Opacity(opacity: 1.0, child: ColoredBox(color: Colors.blue))),
    );
    final render = tester.renderObject<RenderOpacity>(find.byType(Opacity));
    expect(render.isRepaintBoundary, isTrue);
    expect(render.alwaysNeedsCompositing, isTrue);
  });

  testWidgets('Opacity(opacity: 0.0) is the ONE value that skips compositing entirely', (tester) async {
    await tester.pumpWidget(
      const MaterialApp(home: Opacity(opacity: 0.0, child: ColoredBox(color: Colors.blue))),
    );
    final render = tester.renderObject<RenderOpacity>(find.byType(Opacity));
    expect(render.isRepaintBoundary, isFalse);
    expect(render.alwaysNeedsCompositing, isFalse);
  });
}
```

```text
✓ Opacity(opacity: 1.0) is STILL a repaint boundary
✓ Opacity(opacity: 0.0) is the ONE value that skips compositing entirely
00:00 +2: All tests passed!
```

**Fix:** if the opacity is a compile-time constant `1.0` (a widget conditionally shown/hidden by swapping it out entirely, say), skip `Opacity` altogether — return the child directly, or use `Visibility`/a ternary that removes the widget instead of dimming it. Reserve `Opacity`/`AnimatedOpacity`/`FadeTransition` for opacity that genuinely varies.

**Caught by:** nothing automatic, and this is a genuinely nuanced correction: `Opacity(opacity: 1.0)` does not crash and does not even mis-render — it just always pays for a layer it usually does not need to, and the framework's own doc comment can be read (incorrectly) as saying otherwise.

### 24. `cacheExtent` deprecated → `scrollCacheExtent` (a new sealed-class type, not just a rename)

`cacheExtent` (a plain `double`) was deprecated in Flutter 3.41 in favor of `scrollCacheExtent` — but the replacement is not a drop-in rename: `scrollCacheExtent` takes a NEW sealed class, `ScrollCacheExtent`, with factory constructors `.pixels(double)` and `.viewport(double)`, and that type is not even re-exported by `package:flutter/material.dart` — it needs an explicit `package:flutter/rendering.dart` import.

```dart
// lib/ai-bug-catalog/24-cache-extent.dart
import 'package:flutter/material.dart';

// AI-generated (trained on older Flutter docs).
Widget buggyList() => ListView.builder(
      cacheExtent: 500,
      itemCount: 100,
      itemBuilder: (context, i) => Text('$i'),
    );
```

**Symptom — real `flutter analyze` diagnostic, captured fresh:**

```text
info • 'cacheExtent' is deprecated and shouldn't be used. Use scrollCacheExtent instead. This
feature was deprecated after v3.41.0-0.0.pre. Try replacing the use of the deprecated member with
the replacement • deprecated_member_use
```

A naive rename to `scrollCacheExtent: 500` fails differently:

```text
error • The argument type 'int' can't be assigned to the parameter type 'ScrollCacheExtent?' •
argument_type_not_assignable
```

**Fix, analyzes clean:**

```dart
// lib/ai-bug-catalog/24-cache-extent-fixed.dart
import 'package:flutter/material.dart';
import 'package:flutter/rendering.dart' show ScrollCacheExtent;

Widget fixedList() => ListView.builder(
      scrollCacheExtent: ScrollCacheExtent.pixels(500),
      itemCount: 100,
      itemBuilder: (context, i) => Text('$i'),
    );
```

**Caught by:** `flutter analyze` for the deprecation, and `dart fix --dry-run` correctly identifies it as fixable (proven in **[Verification Tools](/flutter/en/reading-flutter/verification-tools/)**) — but a reflexive find-and-replace rename, without reading the new type, trades one diagnostic for a different one.

### 25. `prefer_const_constructors` is NOT in `flutter_lints` 6

`flutter_lints` 6.0.0 ships `prefer_const_constructors_in_immutables` (const inside an `@immutable` class's own `build()`) but not the general `prefer_const_constructors` rule that flags ANY missed `const` opportunity — confirmed by reading the package's own `flutter.yaml` rule list directly.

```dart
// lib/ai-bug-catalog/25-prefer-const.dart
import 'package:flutter/material.dart';

// AI-generated: missing const -- flutter_lints 6 says nothing about it.
Widget buildGreeting() {
  return Text('hello');
}
```

**Symptom — real `flutter analyze`, under this course's pinned `flutter_lints: ^6.0.0`:**

```text
Analyzing 25-prefer-const.dart...
No issues found!
```

**Contrast — the SAME file, with `prefer_const_constructors: true` added explicitly to `analysis_options.yaml`:**

```text
info • Use 'const' with the constructor to improve performance. Try adding the 'const' keyword to
the constructor invocation • prefer_const_constructors
```

**Fix:** either add `const`, or explicitly enable `prefer_const_constructors` (or adopt `very_good_analysis`, which does include it) if the team wants the general rule enforced.

**Caught by:** nothing, under this course's exact pinned lint set — a reviewer relying on "the linter would have caught it" for `const` specifically is relying on a rule that is not actually enabled.

### 26. `print()` is not stripped from a release build

Nothing in Flutter's default release pipeline strips `print()` calls. The literal string survives verbatim into the compiled output.

```dart
// lib/ai-bug-catalog/26-print-release.dart
void main() {
  print('READING_FLUTTER_PRINT_MARKER_7f3a9c'); // AI-generated: "it's just a debug print"
}
```

**Symptom — real `flutter build web --release`, then grepping the actual output bundle, captured fresh for this module:**

```text
$ flutter build web --release
✓ Built build/web
$ grep -c READING_FLUTTER_PRINT_MARKER_7f3a9c build/web/main.dart.js
1
```

The marker string is present, verbatim, once, inside the minified release JS bundle.

**Fix:** use `dart:developer`'s `log()` (which respects log levels and can be stripped/filtered by tooling) instead of `print()` for anything that should not ship in release, or gate debug-only prints behind `kDebugMode` from `package:flutter/foundation.dart`.

**Caught by:** nothing automatic — no lint in this course's pinned `flutter_lints` 6 flags a bare `print()` by default (`avoid_print` IS enabled, worth noting as the one exception: it fires as a lint, but nothing enforces fixing lints before a release build ships).

### 27. Non-exhaustive `switch` on a `sealed class`

An AI assistant trained on the old "abstract class + `is`-check" style for state unions sometimes still forgets a case even when using a modern `sealed class` + `switch` expression — but here, the analyzer can actually PROVE the switch is incomplete, at compile time, because the class is sealed.

```dart
// lib/ai-bug-catalog/27-non-exhaustive-switch.dart — @expect-error non_exhaustive_switch_expression -- see the real diagnostic below
sealed class LoadState {}
class Loading extends LoadState {}
class Loaded extends LoadState {
  Loaded(this.data);
  final String data;
}
class LoadError extends LoadState {
  LoadError(this.message);
  final String message;
}

// AI-generated: forgot the LoadError case entirely.
String buggyDescribe(LoadState state) {
  return switch (state) {
    Loading() => 'loading',
    Loaded(:final data) => 'loaded: $data',
  };
}
```

**Symptom — real `flutter analyze` diagnostic, captured fresh:**

```text
error • The type 'LoadState' isn't exhaustively matched by the switch cases since it doesn't match
the pattern 'LoadError()'. Try adding a wildcard pattern or cases that match 'LoadError()' •
non_exhaustive_switch_expression
```

**Fix, analyzes clean:**

```dart
// lib/ai-bug-catalog/27-non-exhaustive-switch-fixed.dart
sealed class LoadState {}
class Loading extends LoadState {}
class Loaded extends LoadState {
  Loaded(this.data);
  final String data;
}
class LoadError extends LoadState {
  LoadError(this.message);
  final String message;
}

String fixedDescribe(LoadState state) {
  return switch (state) {
    Loading() => 'loading',
    Loaded(:final data) => 'loaded: $data',
    LoadError(:final message) => 'error: $message',
  };
}
```

**Caught by:** `flutter analyze`, as a real, hard ERROR (not a lint an AI's confidence can wave away) — this is Dart 3's own exhaustiveness checking, and it is the single strongest argument in this whole catalog for adopting `sealed class` state unions over the old `abstract class` style: a fourth subtype added later makes every existing switch fail to compile again until it is handled.

### 28. Hallucinated API: a named parameter and a method that do not exist

An AI assistant blending several widgets/APIs it has seen invents a plausible-sounding named parameter or method name that does not actually exist on the class in question.

```dart
// lib/ai-bug-catalog/28-hallucinated-api-fixed.dart
```
