## The feature

The prompt was: *"Build a small todo app: a list screen, an add-todo screen, a details screen, and a settings tab -- use Riverpod's `@riverpod` code generation for state and go_router for navigation, with a bottom nav bar that keeps each tab's own back stack."* What follows is the kind of first draft an AI assistant hands back for exactly that prompt: every file compiles (once you generate the codegen output it forgot to include, itself the first bug), the happy path genuinely works if you follow the exact sequence the AI tested, and it *looks* like idiomatic Riverpod 3 + go_router 18. Read it the way the **[review checklist](/flutter/en/reading-flutter/review-checklist/)** recommends: state ownership first (who reads/writes what, and when), then navigation structure, then lifecycle. It has **10 real bugs**; most map directly onto categories in the **[AI bug catalog](/flutter/en/reading-flutter/ai-bug-catalog/)**. Every claim below was run for real in this course's own probe (Flutter 3.47.5 / `flutter_riverpod` 3.4.3 / `go_router` 18.0.1 / `riverpod_generator` 4.0.9) -- real `flutter analyze`, real `flutter test`, real generated `.g.dart` output, nothing pasted from memory.

## The review walk

### 1. No `ProviderScope` -- every `ConsumerWidget` throws the moment it reads a provider

`main.dart` never wraps `TodoApp` in a `ProviderScope`. `OnboardingScreen` doesn't touch a provider, so the AI's own test (and a quick manual look at the first screen) never surfaces this -- the crash only fires once navigation reaches a real `ConsumerWidget`, proven here by completing onboarding and going to `/todos`:

```text
StateError: Bad state: No ProviderScope found
```

<SpotTheBug code={`void main() {
  runApp(const TodoApp());
}`}>
Exactly the trap proven in **[Provider & Riverpod](/flutter/en/state-management/provider-and-riverpod/)**: every `ref.watch`/`ref.read` needs a `ProviderContainer` reachable via `ProviderScope`, and Riverpod does not create one for you. The fix is one line at the root: `runApp(const ProviderScope(child: TodoApp()))`.
</SpotTheBug>

### 2. Missing `part 'todos_provider.g.dart';` -- a real, separate compile error

Not in the shipped `todos_provider.dart` above (that one has its `part` directive), but the same mistake showed up in an earlier revision of this exact class, and it's common enough to be worth isolating on its own. The real, unedited `flutter analyze` output for the snippet in the previous section:

```text
error • Classes can only extend other classes. Try specifying a different superclass, or removing the extends clause • extends_non_class
warning • The method doesn't override an inherited method • override_on_non_overriding_member
error • Undefined name 'state'. Try correcting the name to one that is defined, or defining the name • undefined_identifier
error • Undefined name 'state'. Try correcting the name to one that is defined, or defining the name • undefined_identifier
```

`_$TodosNotifier` doesn't exist without the `part` directive pulling in the generated file that defines it -- the analyzer reads `extends _$TodosNotifier` as extending an undefined name, and `state` (which `_$TodosNotifier` would provide) as undefined too, twice, once per use on the same line.

### 3. Route order: `/todos/:id` declared before `/todos/new`

Inside the Todos branch, `router.dart` declares the parameterized details route **before** the literal `/todos/new` route. go_router matches a branch's own route list top to bottom, first match wins:

```dart
// test/todo_app/route_order_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/todo_app/router.dart';

void main() {
  testWidgets('"/todos/new" is swallowed by ":id" declared first -- NewTodoScreen never builds', (tester) async {
    onboarding.complete();
    await tester.pumpWidget(
      ProviderScope(child: MaterialApp.router(routerConfig: todoRouter)),
    );
    todoRouter.go('/todos/new');
    await tester.pumpAndSettle();

    expect(find.byType(TextField), findsNothing,
        reason: 'NewTodoScreen (which has a TextField) never built');
    expect(find.text('Not found'), findsOneWidget,
        reason: '":id" matched first with id="new" -- TodoDetailsScreen '
            'looked up a todo with id "new", found none, and shows '
            '"Not found" instead of the new-todo form');
  });
}
```

```text
✓ "/todos/new" is swallowed by ":id" declared first -- NewTodoScreen never builds

00:00 +1: All tests passed!
```

Same trap proven for a top-level pair of routes in **[Declarative routing](/flutter/en/navigation/declarative-routing/)**; it applies identically to routes declared inside one `StatefulShellBranch`'s own list.

### 4. `context.go` where `push` was needed -- the back stack is gone

`TodosListScreen` opens details with `context.go('/todos/${todo.id}')`. `go` sets the current location outright; it does not push on top of whatever was there:

```dart
// test/todo_app/go_vs_push_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/todo_app/router.dart';
import 'package:my_app/todo_app/todos_provider.dart';

void main() {
  testWidgets('tapping a todo uses context.go -- the Todos list is gone from the back stack', (tester) async {
    onboarding.completed = false;
    final container = ProviderContainer();
    addTearDown(container.dispose);
    container.listen(todosProvider, (_, _) {}); // keep alive: todosProvider is .autoDispose by default
    container.read(todosProvider.notifier).add('Buy milk'); // id '0'

    await tester.pumpWidget(
      UncontrolledProviderScope(
        container: container,
        child: MaterialApp.router(routerConfig: todoRouter),
      ),
    );
    onboarding.complete();
    todoRouter.go('/todos');
    await tester.pumpAndSettle();

    await tester.tap(find.text('Buy milk'));
    await tester.pumpAndSettle();
    expect(find.text('not done'), findsOneWidget, reason: 'details screen opened');

    expect(find.byTooltip('Back'), findsNothing,
        reason: 'context.go() replaced the list route instead of pushing '
            'on top of it -- the back stack lost the Todos list entirely');
  });
}
```

### 5. `redirect` with no `refreshListenable` -- onboarding can complete and the app never notices

`router.dart`'s top-level `redirect` checks `onboarding.completed`, but nothing tells the router to re-run `redirect` when `onboarding` itself changes -- only navigation triggers a re-evaluation:


The button's own `onPressed` masks this completely -- it calls `onboarding.complete()` **and then** `context.go('/todos')` itself, so the happy path always works. It's any *other* path to completing onboarding (a restored session, a background auth callback) that gets stuck.

### 6. `StateNotifierProvider` used without importing `package:flutter_riverpod/legacy.dart`

Elsewhere in the same PR, a filter toggle was written with `StateNotifier`/`StateNotifierProvider` -- legacy Riverpod 1/2 APIs. In Riverpod 3, `flutter_riverpod/flutter_riverpod.dart` no longer exports them at all; they moved to a separate `legacy.dart` entry point, confirmed directly from the installed package:

```text
// flutter_riverpod-3.4.3/lib/legacy.dart
export 'src/internals.dart'
    show
        StateNotifier,
        StateController,
        StateNotifierProvider,
        StateProvider,
        ChangeNotifierProvider,
        ChangeNotifierProviderFamily,
        StateNotifierProviderFamily,
        StateProviderFamily;
```

The real, unedited `flutter analyze` output for the snippet above, importing only the main barrel:

```text
error • Classes can only extend other classes. Try specifying a different superclass, or removing the extends clause • extends_non_class
error • Too many positional arguments: 0 expected, but 1 found. Try removing the extra arguments • extra_positional_arguments
error • Undefined name 'state'. Try correcting the name to one that is defined, or defining the name • undefined_identifier
error • The function 'StateNotifierProvider' isn't defined. Try importing the library that defines 'StateNotifierProvider', correcting the name to the name of an existing function, or defining a function named 'StateNotifierProvider' • undefined_function
```

Switching the import to `package:flutter_riverpod/legacy.dart` alone makes this exact snippet analyze clean -- but that's a half-fix. Per Riverpod's own [migration guide](https://riverpod.dev/docs/migration/from_state_notifier), `StateNotifier`/`StateNotifierProvider` are legacy; the real fix in an app that's already using `@riverpod` codegen everywhere else (like this one) is a `Notifier`/`@riverpod` class, not a second import unlocking a deprecated API.

### 8. `ref.watch` inside `onPressed` -- doesn't throw, but is still wrong

`NewTodoScreen`'s submit button reads `ref.watch(todosProvider.notifier)` from inside a callback instead of `ref.read`. The common assumption is that this throws immediately, the way `ref.listen` does (`ref.listen can only be used within the build method of a ConsumerWidget`, a real `assert` in `flutter_riverpod`'s own source). `watch` has **no such assertion** -- checked directly against the installed package. Proven with a build counter: tapping a button that calls `ref.watch` does not throw, and does not itself trigger a rebuild -- but it silently registers a subscription that a real `build()` pass would have cleaned up, so a later, unrelated state change causes a rebuild nothing in `build()` asked for:

```dart
// lib/wr1_examples/watch_in_callback.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final counterProvider = NotifierProvider<CounterNotifier, int>(CounterNotifier.new);

class CounterNotifier extends Notifier<int> {
  @override
  int build() => 0;
  void increment() => state++;
}

int buildCount = 0;

class BadWatchInCallback extends ConsumerWidget {
  const BadWatchInCallback({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    buildCount++;
    return ElevatedButton(
      onPressed: () {
        final count = ref.watch(counterProvider); // AI comment: "grab the latest count"
        debugPrint('count: $count');
      },
      child: const Text('tap'),
    );
  }
}
```

### 10. `setState` after an unguarded `await`, no `mounted` check

`TodoDetailsScreen._confirmView` awaits a delayed result, then calls `setState` unconditionally. If the screen is removed from the tree while that `Future` is still pending (its todo deleted from another tab, the branch's stack changed), the widget is already disposed by the time it resolves. This is the exact mechanism proven end to end in the **[setState and lifecycle](/flutter/en/state-management/setstate-and-lifecycle/)** lesson's `mounted`-guard section; reproduced here for this screen's own shape:

## What the reviewer writes in the PR

> Solid structure, but this can't merge as-is -- 10 things, in the order they'd actually bite:
>
> 1. **No `ProviderScope`.** Your own test never reaches a `ConsumerWidget`, so it passed -- but the first real screen throws `Bad state: No ProviderScope found`. Wrap `TodoApp` in `ProviderScope` at the root.
> 2. **A `TodosNotifier` shipped without its `part` directive** in an earlier revision -- `extends _$TodosNotifier` doesn't resolve without it. Double-check every `@riverpod` file has `part '<file>.g.dart';` right after the imports.
> 3. **Route order.** `/todos/:id` is declared before `/todos/new` in the Todos branch -- `/todos/new` matches the id route first. Literal routes before parameterized ones, always.
> 4. **`context.go` for details.** This drops `/todos` from the back stack -- users can't get back to the list. Use `context.push`.
> 5. **`redirect` has no `refreshListenable`.** Fine for the button's own flow (it calls `go()` itself), but anything else that completes onboarding -- a restored session, a background callback -- leaves the user stuck on the onboarding screen forever. Wire `refreshListenable: onboarding`.
> 6. **`StateNotifierProvider` needs `package:flutter_riverpod/legacy.dart`** in Riverpod 3 -- it's not in the main barrel anymore. But since this app already uses `@riverpod` everywhere else, just migrate this one too instead of unlocking the legacy import.
> 7. **`ref.read` in `TodosListScreen.build`.** The list never updates after adding a todo. Should be `ref.watch`.
> 8. **`ref.watch` inside `onPressed`.** Doesn't throw (that's `ref.listen`'s job), but it leaves a stray subscription behind that causes unrelated rebuilds later. Should be `ref.read` -- it's a one-shot action, not something to subscribe to.
> 9. **`selectedTodoProvider` never disposes.** It's hand-written, not generated, so it skips `.autoDispose` entirely -- every todo ID ever viewed stays cached for the app's whole lifetime. Generate it with `@riverpod` instead.
> 10. **Missing `mounted` guard** in `_confirmView`. If this screen goes away mid-await, `setState` throws `setState() called after dispose()`.
>
> None of these need a redesign -- happy to pair on the fixes.

## Mental Model

Only two of these ten bugs (2, 6) are compile errors the analyzer catches for free -- both are the same underlying mistake in two different clothes: codegen and legacy APIs both require an extra import/directive that an AI assistant, trained mostly on pre-3.0 Riverpod snippets and complete files, easily drops. The other eight all compile and run fine on the one path the AI actually exercised: a `ConsumerWidget` deep enough in the tree that a manual smoke test never reaches it, a route order that only matters once you try the literal path, a `push`-shaped bug that's invisible until you check for a Back button, a `redirect` that's masked by the one button that calls `go()` itself, `ref.watch`/`ref.read` swapped in ways that don't throw either way, a provider that's only "wrong" once you watch it for disposal, and a lifecycle guard that only matters once something actually disposes mid-await. This is the same shape as every worked review in this module: **the compiler is a floor, not a ceiling** -- it catches missing directives and undefined names, never "this technically-valid code does the wrong thing under a condition nobody happened to trigger yet."

## Trade-offs

| Choice | Upside | Cost |
|---|---|---|
| `@riverpod` codegen everywhere | Consistent `.autoDispose` defaults, less boilerplate | Every family/details-style provider needs to actually BE generated -- hand-writing one silently opts out |
| `StatefulShellRoute.indexedStack` | Each tab keeps its own back stack and screen state | All branches stay resident in memory; state that leaks (bug 9) leaks per-branch too |
| `redirect` + `refreshListenable` | Reacts to state changes with zero extra navigation calls | One more object (a `Listenable`) to wire and keep in sync |
| `push` for drill-down, `go` for tab-level jumps | Predictable back stack | Easy to reach for `go` out of habit everywhere, including where `push` was meant |

## Common Misconceptions

- **"`ref.watch` outside `build` throws, just like `ref.listen`."** Proven above: it doesn't. `flutter_riverpod`'s own source only asserts `debugDoingBuild` inside `listen`, never inside `watch` -- `watch` silently registers a subscription that a real build pass would have cleaned up, producing a rebuild leak instead of a crash.
- **"A hand-written `.family` provider is just as safe as a generated one."** Proven above: `@riverpod` defaults to `.autoDispose`; a hand-written `Provider.family` does not opt into anything unless you write `.autoDispose.family` yourself. Skipping codegen for "just one more provider" silently drops that default.
- **"If the AI's own test passes, the screen it claims to test is fine."** The AI's widget test only pumped `OnboardingScreen`, which never touches a provider -- it proved nothing about bug 1, the single bug that crashes every other screen in the app.
