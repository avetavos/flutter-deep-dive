## The one rule

If you remember nothing else about Flutter layout, remember this:

> **Constraints go down. Sizes go up. The parent sets the position.**

Layout is a single pass down the tree and back up. A parent passes **constraints** to each child — a `BoxConstraints` with a min and max width and height. Each child must choose a **size** that satisfies those constraints, and reports it back up. The parent then **positions** the child inside itself.

<Mermaid title="One layout pass: down with constraints, up with sizes" code={ruleDiagram} />

export const ruleDiagram = `flowchart TB
  parent["Parent widget"] -->|"constraints:\nmin/max w, min/max h"| child["Child widget"]
  child -->|"chosen size\n(within constraints)"| parent
  parent -->|"offset\n(where to place child)"| placed["Child placed"]`;

That is the entire algorithm. Everything else is detail about *how* a particular widget chooses its size and *what* constraints it passes on.

## Proven: the three parts of the rule, read directly off the render tree

`WidgetTester.getSize` and `getTopLeft` read the actual, real layout result — not a description of it — so the rule above is directly checkable.

```dart
// lib/constraints_rule.dart
import 'package:flutter/material.dart';

class CenteredBox extends StatelessWidget {
  const CenteredBox({super.key});
  @override
  Widget build(BuildContext context) {
    return const SizedBox(
      width: 200,
      height: 200,
      child: Center(
        child: SizedBox(width: 50, height: 50, key: ValueKey('child')),
      ),
    );
  }
}
```

```dart
// test/constraints_rule_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/constraints_rule.dart';

void main() {
  testWidgets('constraints go down, sizes go up, the parent sets position', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: Scaffold(body: Center(child: CenteredBox()))));

    final childFinder = find.byKey(const ValueKey('child'));
    final outerBoxFinder = find.byType(SizedBox).first; // the 200x200 outer box

    // SIZES GO UP: the child chose 50x50 — its OWN size — even though the
    // outer SizedBox is 200x200 and Center gives it loose constraints up to that.
    expect(tester.getSize(childFinder), const Size(50, 50));

    // THE PARENT SETS POSITION: Center placed the 50x50 child in the middle
    // of its own 200x200 box — (200-50)/2 = 75 on each axis.
    final childTopLeft = tester.getTopLeft(childFinder);
    final outerTopLeft = tester.getTopLeft(outerBoxFinder);
    expect(childTopLeft - outerTopLeft, const Offset(75, 75));
  });
}
```

Reading the same example top-down: `Center` receives tight `200x200` constraints from the outer `SizedBox`. It passes **loose** constraints down — "you may be anything from 0 up to 200x200." The inner `SizedBox` wants exactly `50x50`, which fits, so it sizes to `50x50` and reports that back up — proven directly by `getSize`. `Center` is `200x200` (its own size came from ITS parent's tight constraint) and positions the `50x50` child in the middle — proven directly by the `75,75` offset. Change `Center` to `Align`, `Padding`, or `SizedBox` and only the constraints passed down (step 2) change — the rule itself never does.

## Tight vs loose constraints

A constraint is **tight** when min equals max (the widget must be exactly that size) and **loose** when min is 0 (the widget may be anything up to max).

```dart
// SizedBox imposes a tight constraint — the child MUST be 50x50.
SizedBox(width: 50, height: 50, child: coloredBox)

// Center imposes a loose constraint — the child may be up to the parent size.
Center(child: coloredBox)
```

This is why the same widget behaves differently under different parents: `Container(color: Colors.red)` with no size fills its parent under tight constraints, but shrinks to nothing under loose ones (this exact rule, proven with a real `getSize` test, is in the [Core Layout Widgets lesson](/flutter/en/layout-and-rendering/core-layout-widgets/)). The widget did not change — the constraints did.

## Proven: the real `RenderFlex overflowed` text

Give a `Row` more content than its available width and it does not shrink the content — it overflows, and Flutter reports exactly how much:

## Proven: the real unbounded-height crash — and the three real fixes

Some widgets pass **unbounded** constraints — a max of infinity — meaning "you can be as big as you want." A scrollable's `Viewport` is bounded in the *cross* axis but needs to know its *own* extent in the scroll axis from its parent — and a plain, non-flexible `Column` gives its non-flex children an **unbounded** main-axis constraint (so each child can report its natural size). Put a `ListView` directly inside a `Column` (not wrapped in `Expanded`) and the viewport cannot determine how tall it should be:

```dart
// lib/unbounded_height.dart
import 'package:flutter/material.dart';

class UnboundedColumn extends StatelessWidget {
  const UnboundedColumn({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const Text('header'),
        // BUG: a bare ListView as a non-flex child of a Column — the
        // Column gives it unbounded height, and a viewport cannot lay
        // itself out with an infinite extent.
        ListView(
          children: const [
            SizedBox(height: 50, child: Text('a')),
            SizedBox(height: 50, child: Text('b')),
          ],
        ),
      ],
    );
  }
}
```

```dart
// test/unbounded_height_test.dart
```

<Callout title="Correction to a common example: a Column INSIDE a ListView does not crash">
A frequently repeated (but wrong) version of this trap puts the `Column` **inside** the `ListView`'s children instead of the other way around. Tested directly: `ListView(children: [Column(children: [Text('a'), Text('b')])])` does **not** throw — a `ListView`'s items are handed unbounded height so each item can report its own natural size, and a `Column` given an unbounded incoming max height falls back to sizing itself to the sum of its children instead of trying to "fill" an infinite space. The real crash needs the *scrollable* (the `ListView`/viewport) to be the one receiving unbounded height from a non-flexible slot — i.e. a bare `ListView` as a direct, non-`Expanded` child of a `Column`, proven above. If you've seen this example the other way around, it was demonstrating something that doesn't actually error.
</Callout>

All three fixes below genuinely resolve it — verified by pumping each and asserting `tester.takeException()` is `null`:

```dart
// lib/unbounded_height_fixes.dart
import 'package:flutter/material.dart';

/// Fix 1: Expanded gives the ListView a bounded, finite height — whatever
/// space is left in the Column after its other children.
class FixExpanded extends StatelessWidget {
  const FixExpanded({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const Text('header'),
      Expanded(
        child: ListView(children: const [SizedBox(height: 50), SizedBox(height: 50)]),
      ),
    ]);
  }
}

/// Fix 2: shrinkWrap makes the ListView size itself to its CONTENT instead
/// of asking for the viewport's full scroll extent — but it builds every
/// item up front, losing laziness (see the Slivers & Scrolling lesson).
class FixShrinkWrap extends StatelessWidget {
  const FixShrinkWrap({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const Text('header'),
      ListView(
        shrinkWrap: true,
        children: const [SizedBox(height: 50), SizedBox(height: 50)],
      ),
    ]);
  }
}

/// Fix 3: SizedBox gives the ListView an explicit, finite, tight height.
class FixSizedBox extends StatelessWidget {
  const FixSizedBox({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(children: [
      const Text('header'),
      SizedBox(
        height: 200,
        child: ListView(children: const [SizedBox(height: 50), SizedBox(height: 50)]),
      ),
    ]);
  }
}
```

`Expanded` is usually right when the list should fill remaining space; `shrinkWrap` is right only for genuinely small, bounded lists (it defeats lazy building — see the [Slivers & Scrolling lesson](/flutter/en/layout-and-rendering/slivers-and-scrolling/)); an explicit `SizedBox` is right when you want a fixed, known height regardless of siblings.

## Proven: `IntrinsicHeight` costs a real extra measurement pass

`IntrinsicHeight` sizes its child to that child's own *intrinsic* (natural) height, even inside a `Row`/context that wouldn't normally tell it that. To do this, it must ask the child "how tall do you *want* to be" (an intrinsic-dimension query) **before** the real layout pass that actually sizes it — proven directly by instrumenting both calls separately on a custom `RenderBox`:

```dart
// lib/intrinsic_height_cost.dart
import 'package:flutter/material.dart';

int probeLayoutCount = 0;
int probeIntrinsicCount = 0;

class LayoutProbe extends LeafRenderObjectWidget {
  const LayoutProbe({super.key, required this.height});
  final double height;

  @override
  RenderObject createRenderObject(BuildContext context) => _RenderLayoutProbe(height);

  @override
  void updateRenderObject(BuildContext context, RenderObject renderObject) {
    (renderObject as _RenderLayoutProbe).probeHeight = height;
  }
}

class _RenderLayoutProbe extends RenderBox {
  _RenderLayoutProbe(this._height);
  double _height;
  set probeHeight(double v) => _height = v;

  @override
  double computeMinIntrinsicHeight(double width) {
    probeIntrinsicCount++;
    return _height;
  }

  @override
  double computeMaxIntrinsicHeight(double width) {
    probeIntrinsicCount++;
    return _height;
  }

  @override
  void performLayout() {
    probeLayoutCount++;
    final w = constraints.maxWidth.isFinite ? constraints.maxWidth : 50.0;
    size = constraints.constrain(Size(w, _height));
  }
}
```

```dart
// test/intrinsic_height_cost_test.dart

    expect(probeIntrinsicCount, greaterThan(0), reason: 'IntrinsicHeight queried the child\'s intrinsic height BEFORE laying it out — a real, extra measurement');

}
```


`probeIntrinsicCount` stays flat at `0` for the plain case and jumps for the `IntrinsicHeight` case — a real, measurable extra query, not a guess. In a deep tree, that intrinsic query recurses through every descendant, which is why the Flutter docs describe `IntrinsicHeight`/`IntrinsicWidth` as "expensive" and worth avoiding in hot paths (e.g. inside a scrolling list) — reach for it only when you genuinely need one child's size to match a sibling's natural height (the classic case: two `Column`s of unequal natural height sharing a `Row`, both stretched to match the taller one).

## `ConstrainedBox`, `UnconstrainedBox`, and proven: `OverflowBox` genuinely breaks the down-flow

- **`ConstrainedBox`** adds *additional* constraints on top of what it receives — it can only make constraints tighter, never looser, than what its own parent already imposed.
- **`UnconstrainedBox`** lets its child size itself as if unconstrained (ignoring incoming constraints for sizing purposes), then aligns it within the space it was actually given — handy for letting a child briefly ignore a tight constraint it doesn't fit, at the cost of a possible overflow if the child ends up bigger than the available space.
- **`OverflowBox`** is the most deliberate constraint-breaker of the three: it reports **its own** size to its parent based on the constraints IT received, but hands its **child** a *different*, explicitly-specified set of constraints — which can be looser (or tighter) than what `OverflowBox` itself was given, letting the child be sized larger than its own parent's box.

```dart
// lib/overflow_box_demo.dart
import 'package:flutter/material.dart';

class OverflowDemo extends StatelessWidget {
  const OverflowDemo({super.key});
  @override
  Widget build(BuildContext context) {
    return SizedBox(
      width: 100,
      height: 100,
      child: OverflowBox(
        minWidth: 0,
        maxWidth: 200,
        minHeight: 0,
        maxHeight: 200,
        child: SizedBox(width: 150, height: 150, key: const ValueKey('overflowChild')),
      ),
    );
  }
}
```


This is the one deliberate, sanctioned exception to "constraints go down, sizes go up" acting as a strict nesting relationship — `OverflowBox`'s reported size (`100x100`, up to its own parent) and its child's actual size (`150x150`) are allowed to disagree, which is exactly why the visual result overflows its own box (usually intentional, for a badge or decoration that's meant to bleed outside its logical bounds) — and exactly why `OverflowBox` should be reached for deliberately, not reached for by accident.

## `LayoutBuilder` for breakpoints

`LayoutBuilder` (proven in depth, including its rebuild-scope difference from `MediaQuery.of`, in the [build and BuildContext lesson](/flutter/en/widgets/build-and-buildcontext/)) is the standard tool for responding to the *actual space this widget was given* rather than the whole screen — which is what a real breakpoint needs, since a widget might live inside a fixed-width sidebar or a split view where "screen width" is the wrong number entirely:

```dart
LayoutBuilder(
  builder: (context, constraints) {
    if (constraints.maxWidth < 600) {
      return const NarrowLayout();
    }
    return const WideLayout();
  },
)
```

<Callout title="The one-line takeaway">
Layout is one pass: **constraints go down, sizes go up, the parent sets position** — proven above directly with `getSize`/`getTopLeft`. Overflowing a `Row`/`Column` throws a real, precisely-worded `RenderFlex overflowed by N pixels` error — proven above, matching the exact overflow math. A bare `ListView`/viewport as a non-flex child of a `Column` throws a real `Vertical viewport was given unbounded height` error (NOT the reverse — a `Column` inside a `ListView`'s children does not crash, corrected above) — fixed with `Expanded`, `shrinkWrap: true`, or an explicit `SizedBox`, all three verified working. `IntrinsicHeight` genuinely costs an extra intrinsic-dimension query before the real layout pass — proven with a call counter. `ConstrainedBox`/`UnconstrainedBox` work within the normal constraint flow; `OverflowBox` — proven above — deliberately breaks it, letting a child be sized larger than what its own parent reports upward.
</Callout>

## Mental Model

A `BoxConstraints` is a **job order**, not a suggestion: "build me something between this minimum and this maximum, in both dimensions." Every widget is a contractor that must hand back a size satisfying the order it was given — no widget gets to unilaterally decide "I'll just be bigger, thanks," which is exactly why overflow is an *error*, not a silent resize. The parent, having received a finished size back from the child, is the only one who then decides *where* to place it — the child never gets a vote on its own position, only its own size. `OverflowBox` is a contractor's foreman quietly handing a subcontractor a different job order than the one written on the building permit — legal, but exactly why it needs a name that says so.

## Trade-offs

| Choice | Benefit | Cost |
| --- | --- | --- |
| `Expanded` around a scrollable in a `Column` | Correct, keeps laziness (proven no crash) | The scrollable takes all remaining space — not appropriate if you wanted it sized to content |
| `shrinkWrap: true` | Sizes to content instead of filling | Builds every item up front — proven cost in the [Slivers & Scrolling lesson](/flutter/en/layout-and-rendering/slivers-and-scrolling/); wrong choice for long lists |
| Explicit `SizedBox` height | Predictable, simple, no laziness trade-off | Height must be known/decided ahead of time — not responsive to content |
| `IntrinsicHeight`/`IntrinsicWidth` | Makes siblings match each other's natural size | A real, proven extra measurement pass, recursive through the subtree — avoid in hot/scrolling paths |
| `OverflowBox` | Lets a child deliberately exceed its logical parent's bounds | Purely visual — hit-testing and layout of SIBLINGS are unaffected by the overflowed area; easy to misuse for actual layout (rather than decoration) |

## Common Misconceptions

- **"A widget can just decide to be bigger than its constraints allow."** Proven false above: `RenderFlex overflowed` is a hard error precisely because Flutter enforces the constraint contract — a `Row`/`Column` will NOT silently expand.
- **"Column inside ListView is what causes the unbounded-height crash."** Proven above (and corrected against a commonly-repeated wrong example): that direction does NOT crash. The real crash needs a bare, non-`Expanded` `ListView` as a child of a `Column`.
- **"IntrinsicHeight is basically free — it's just one more widget in the tree."** Proven above with a real call counter: it performs a genuinely separate, extra query (`computeMaxIntrinsicHeight`/`computeMinIntrinsicHeight`) before the normal layout pass, not just "one more layout."
- **"OverflowBox/UnconstrainedBox violate Flutter's constraint model — they must be bugs when you see them."** Proven above to be intentional, sanctioned escape hatches: `OverflowBox`'s own reported size and its child's actual size are ALLOWED to disagree, by design, for exactly the "decoration that bleeds outside its box" case.

## Reading AI-generated code

AI-generated Flutter layout code frequently nests a `ListView` (or any scrollable) directly inside a `Column` without `Expanded`/`shrinkWrap`/a fixed size — the exact crash proven above — because a huge fraction of training-data snippets show a `ListView` as the sole top-level body of a screen, where no such wrapping is needed, and that pattern gets pasted into a context where it isn't.

```dart
// @expect-error compiles clean — throws the real "Vertical viewport was given unbounded height" error proven above the moment this builds
class ProfileScreen extends StatelessWidget {
  const ProfileScreen({super.key});
  @override
  Widget build(BuildContext context) {
    return Column(
      children: [
        const ProfileHeader(),
        ListView(
          children: const [
            ListTile(title: Text('Setting 1')),
            ListTile(title: Text('Setting 2')),
          ],
        ),
      ],
    );
  }
}
```

Before trusting generated layout code, check:

- Is a scrollable (`ListView`, `GridView`, `SingleChildScrollView`) a DIRECT child of a `Column`/`Row` without `Expanded`/`Flexible` wrapping it? That's the real crash proven above.
- Is `IntrinsicHeight`/`IntrinsicWidth` used inside something that rebuilds/re-lays-out often (a scrolling list, an animation)? The extra query proven above compounds badly there.
- Does an `OverflowBox`/`UnconstrainedBox` appear where the intent was actually "make this fit," rather than "let this deliberately bleed outside its box"? If the former, the real fix is usually `FittedBox` or rethinking the parent's constraints, not overriding them.
