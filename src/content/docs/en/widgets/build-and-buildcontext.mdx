## The build contract

`build` has one job: **return a widget tree that describes the UI for the current state**. It should be a pure, fast function of the widget's fields and state — nothing more.

The rule that matters: **build can be called very often** — every frame of an animation, every `setState`, every time an ancestor rebuilds. So build must be cheap and free of side effects.

```dart
@override
Widget build(BuildContext context) {
  // ✅ Good: just describe UI from current state.
  return Text('Count: $_count');
}
```

```dart
@override
Widget build(BuildContext context) {
  // ❌ Bad: side effects in build. This fires on EVERY rebuild.
  _apiClient.fetchUser();      // network call — leaks, fires repeatedly
  _controller = AnimationController(vsync: this); // recreated every build!
  return Text('...');
}
```

Side effects — network calls, creating controllers, subscribing to streams — belong in `initState` (once) or event handlers, never in `build`. Treat build as read-only rendering.

## What BuildContext actually is

Every `build` receives a `BuildContext`. It is not a bag of globals — it **is the element**. `BuildContext` is an abstract interface; the concrete object handed to you is the `Element` at that position in the tree (proven directly in the [Widgets and the Tree lesson](/flutter/en/widgets/widgets-and-the-tree/), where a spied `createElement`/`didUpdateWidget` showed exactly what that object's lifecycle looks like). That identity is what lets a widget look *up* the tree to find inherited data.

```dart
@override
Widget build(BuildContext context) {
  // context knows WHERE we are, so it can search ancestors:
  final theme = Theme.of(context);          // nearest Theme above us
  final media = MediaQuery.of(context);     // nearest MediaQuery above us
  return Text('Screen is ${media.size.width} wide', style: theme.textTheme.bodyMedium);
}
```

`Theme.of(context)` walks up from this element to find the nearest `Theme` ancestor. This is why context matters: the *same* `.of(context)` call returns different results depending on where in the tree the widget sits.

## Proven: the real `Scaffold.of()` wrong-scope crash, and the `Builder` fix

Because `.of(context)` searches *upward*, a very common bug is using a context that sits **above** the widget you're looking for. The textbook case: calling `Scaffold.of(context)` inside the *same* `build` method that constructs the `Scaffold` — that context is the context of the widget sitting above the `Scaffold`, not below it.

```dart
// lib/scaffold_scope_bug.dart
import 'package:flutter/material.dart';

/// BUG: this context is the context of the SAME build method that creates
/// the Scaffold below — it is above the Scaffold, not under it.
class BadSnackBarButton extends StatelessWidget {
  const BadSnackBarButton({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Demo')),
      body: ElevatedButton(
        onPressed: () {
          Scaffold.of(context).showBottomSheet((_) => const SizedBox());
        },
        child: const Text('Open'),
      ),
    );
  }
}

/// FIX: Builder introduces a new context genuinely located UNDER the Scaffold.
class GoodSnackBarButton extends StatelessWidget {
  const GoodSnackBarButton({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Demo')),
      body: Builder(
        builder: (innerContext) => ElevatedButton(
          onPressed: () {
            Scaffold.of(innerContext).showBottomSheet((_) => const SizedBox());
          },
          child: const Text('Open'),
        ),
      ),
    );
  }
}
```

```dart
// test/scaffold_scope_test.dart

import 'package:my_app/scaffold_scope_bug.dart';

  testWidgets('Scaffold.of with the wrong-scope context throws the real error', (tester) async {

    await tester.tap(find.byType(ElevatedButton));
    await tester.pump();

    await tester.tap(find.byType(ElevatedButton));
    await tester.pump();

    expect(tester.takeException(), isNull, reason: 'Builder\'s context is genuinely a descendant of Scaffold');

}
```

`Theme.of(context)` and `Navigator.of(context)` fail the exact same way for the exact same reason — a context above the ancestor they're searching for, or no such ancestor at all. `Navigator`'s own source states the analogous case plainly (`~/flutter/packages/flutter/lib/src/widgets/navigator.dart`): *"Navigator operation requested with a context that does not include a Navigator. The context used to push or pop routes from the Navigator must be that of a widget that is a descendant of a Navigator widget."* The fix is always the same shape: a `Builder` (or splitting into a child widget) to obtain a context genuinely located **under** the target ancestor.

## Proven: the real `use_build_context_synchronously` lint, and `mounted`

`await` inside an event handler is a real trap: the widget can be unmounted while the `Future` is pending (the user navigated away, the screen was popped), and using `context` — or anything derived from it — *after* that `await` can operate on a tree that no longer exists.

```dart
// lib/context_after_await.dart
import 'package:flutter/material.dart';

// @expect-error use_build_context_synchronously — real lint text: "Don't use 'BuildContext's across async gaps. Try rewriting the code to not use the 'BuildContext', or guard the use with a 'mounted' check"
Future<void> badPop(BuildContext context) async {
  await Future<void>.delayed(const Duration(seconds: 1));
  Navigator.of(context).pop(); // context may belong to an unmounted element by now
}
```

The real analyzer diagnostic, captured from a live `flutter analyze` run against the snippet above (unwrapped, so the lint actually fires):

```text
info • Don't use 'BuildContext's across async gaps. Try rewriting the code to not use the 'BuildContext', or guard the use with a 'mounted' check • use_build_context_synchronously
```

Inside a `State`, the fix is the `mounted` getter — `false` once `dispose()` has run:

```dart
// lib/context_after_await.dart
import 'package:flutter/material.dart';

class SafeCloser extends StatefulWidget {
  const SafeCloser({super.key});
  @override
  State<SafeCloser> createState() => _SafeCloserState();
}

class _SafeCloserState extends State<SafeCloser> {
  Future<void> closeLater() async {
    await Future<void>.delayed(const Duration(seconds: 1));
    if (!mounted) return; // guard — the exact fix the lint asks for
    Navigator.of(context).pop();
  }

  @override
  Widget build(BuildContext context) => const SizedBox();
}
```

A bare top-level function like `badPop` has no `mounted` to check — that's exactly why the lint is worded "rewrite the code to not use the `BuildContext`" *or* "guard... with a `mounted` check": the guard only exists inside a `State`. Outside one, the real fix is to not hold onto `context` across the gap at all — capture what you need from it *before* the `await`.

## Proven: `LayoutBuilder` vs `MediaQuery.of` — a genuinely different rebuild scope

Both let you react to available space, but they are **not interchangeable**, and the difference is measurable: `MediaQuery.of(context)` (no aspect) registers a dependency on the **whole** `MediaQueryData` — text scale, padding, brightness, size, everything — so *any* field changing anywhere in `MediaQueryData` rebuilds every widget that called it. `LayoutBuilder` defers its `builder` call to **layout time** and only re-invokes it when the actual `BoxConstraints` this widget receives from its parent change (or the `LayoutBuilder` widget itself is reconstructed) — a change to `MediaQueryData.textScaler` with the screen size unchanged does not, by itself, touch the constraints `LayoutBuilder` receives at all.

```dart
// lib/context_lookup_scope.dart
import 'package:flutter/material.dart';

int mediaQueryDependentBuildCount = 0;
int layoutBuilderBuildCount = 0;

class MediaQueryDependent extends StatelessWidget {
  const MediaQueryDependent({super.key});
  @override
  Widget build(BuildContext context) {
    mediaQueryDependentBuildCount++;
    final scaler = MediaQuery.of(context).textScaler;
    return Text('$scaler');
  }
}

class LayoutBuilderDependent extends StatelessWidget {
  const LayoutBuilderDependent({super.key});
  @override
  Widget build(BuildContext context) {
    return LayoutBuilder(
      builder: (context, constraints) {
        layoutBuilderBuildCount++;
        return Text('${constraints.maxWidth}');
      },
    );
  }
}

class MediaQueryScopeHarness extends StatefulWidget {
  const MediaQueryScopeHarness({super.key});
  @override
  MediaQueryScopeHarnessState createState() => MediaQueryScopeHarnessState();
}

class MediaQueryScopeHarnessState extends State<MediaQueryScopeHarness> {
  bool scaled = false;
  void toggle() => setState(() => scaled = !scaled);

  @override
  Widget build(BuildContext context) {
    final base = MediaQuery.of(context);
    // Only textScaler changes here — screen size (and so the constraints
    // handed down the tree) stays exactly the same.
    return MediaQuery(
      data: base.copyWith(textScaler: TextScaler.linear(scaled ? 1.5 : 1.0)),
      // const: neither child is even visited by normal parent-triggered
      // diffing when this MediaQuery rebuilds (proven in Widgets and the
      // Tree) — any rebuild that DOES happen below must come from each
      // widget's OWN registered dependency, not from the parent changing.
      child: const Column(
        children: [MediaQueryDependent(), LayoutBuilderDependent()],
      ),
    );
  }
}
```

```dart
// test/context_lookup_scope_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/context_lookup_scope.dart';

void main() {
  testWidgets('MediaQuery.of rebuilds on ANY MediaQueryData change; LayoutBuilder does not, when constraints are unchanged', (tester) async {
    mediaQueryDependentBuildCount = 0;
    layoutBuilderBuildCount = 0;

    final key = GlobalKey<MediaQueryScopeHarnessState>();
    await tester.pumpWidget(MaterialApp(home: MediaQueryScopeHarness(key: key)));
    expect(mediaQueryDependentBuildCount, 1);
    expect(layoutBuilderBuildCount, 1);

    // Toggle ONLY textScaler. Screen size — and so the BoxConstraints
    // LayoutBuilder receives — does not change at all.
    key.currentState!.toggle();
    await tester.pump();

    expect(mediaQueryDependentBuildCount, 2, reason: 'MediaQuery.of() depends on the WHOLE MediaQueryData — textScaler changing is enough');
    expect(layoutBuilderBuildCount, 1, reason: 'the constraints LayoutBuilder receives from its parent never changed — its builder was not re-invoked');
  });
}
```

Pick `MediaQuery.of` (or better, the aspect-scoped `MediaQuery.sizeOf`/`textScalerOf`, which only notify on that one field — the same `InheritedModel` mechanism proven in the [InheritedWidget lesson](/flutter/en/state-management/inherited-widget/)) when you need *ambient* device/platform information. Pick `LayoutBuilder` when you need to react specifically to *the box this widget was actually given* — a `LayoutBuilder` inside a fixed-width sidebar never rebuilds just because the phone's text scale setting changed.

## Proven: `context.findRenderObject()` before layout — the real crash

`BuildContext.findRenderObject()` returns the render object already associated with this element's subtree — and during `initState()`, no layout has happened yet, so for most widgets there isn't one to return.

```dart
// lib/context_render_object.dart
import 'package:flutter/material.dart';

class ReadsSizeTooEarly extends StatefulWidget {
  const ReadsSizeTooEarly({super.key});
  @override
  State<ReadsSizeTooEarly> createState() => _ReadsSizeTooEarlyState();
}

class _ReadsSizeTooEarlyState extends State<ReadsSizeTooEarly> {
  @override
  void initState() {
    super.initState();
    // BUG: no render object exists yet at initState time.
    final box = context.findRenderObject() as RenderBox;
    debugPrint('${box.size}');
  }

  @override
  Widget build(BuildContext context) => const SizedBox(width: 10, height: 10);
}
```

<Callout title="The one-line takeaway">
`build` must be a cheap, side-effect-free function that describes UI from the current state. `BuildContext` **is** the element — `.of(context)` searches upward, so calling `Scaffold.of`/`Navigator.of`/`Theme.of` with a context that sits *above* the ancestor you want throws a real, named error (proven above); `Builder` fixes it by handing you a context genuinely underneath. `await` inside a handler risks a stale `context` — the real `use_build_context_synchronously` lint text says exactly that, and the fix is a `mounted` guard (inside `State`) or not holding `context` across the gap at all. `MediaQuery.of` and `LayoutBuilder` are not interchangeable: proven above, one rebuilds on any ambient data change, the other only when its own actual layout constraints change. `context.findRenderObject()` before the first layout (e.g. in `initState`) crashes for real — wait for a later phase instead.
</Callout>

## Mental Model

`BuildContext` is a **"you are here" pin on a map**, not a database connection. The pin itself does nothing — every `.of(context)` call is a *new* walk starting from that exact pin, up through the ancestors, until it finds what it's looking for or falls off the top of the map. Move the pin (use a different, deeper context — a `Builder`'s) and the same `.of(context)` call can find something it couldn't before, because the walk starts from a different spot. And because the pin only exists on a **built, laid-out map**, asking it "how big is the room you're standing in" (`findRenderObject()...size`) before the map has finished being drawn (before layout) is a question with no answer yet.

## Trade-offs

| Choice | Benefit | Cost |
| --- | --- | --- |
| `Builder` to fix wrong-scope `.of(context)` | Minimal, local, no restructuring | One more nesting level in the widget tree |
| Splitting into a child widget instead of `Builder` | No anonymous closures, a real named/testable widget | More files/classes for a small scope fix |
| `mounted` guard after `await` | Correct, minimal, works inside any `State` | Not available outside a `State` — a bare async function needs a different fix |
| `MediaQuery.of` (whole data) | Simple, one call gets everything | Rebuilds on fields you don't care about — proven above |
| `MediaQuery.sizeOf`/aspect-scoped variants | Narrower rebuild — only that aspect | You must know which aspect you actually need |
| `LayoutBuilder` | Reacts to the widget's OWN actual constraints, ignores unrelated ambient changes | Deferred to layout time — cannot be used to influence intrinsic sizing of its own parent |

## Common Misconceptions

- **"BuildContext is just a convenience object Flutter passes around."** It **is** the `Element` — proven in the [Widgets and the Tree lesson](/flutter/en/widgets/widgets-and-the-tree/) with a spied `createElement`; every `.of(context)` call is a real upward tree walk starting from that exact object.
- **"Scaffold.of(context) should always work as long as there's a Scaffold in the widget."** Proven false above: it depends on *where the context comes from*, not whether a `Scaffold` exists somewhere in the file — the same build method that creates the `Scaffold` has a context that sits above it.
- **"The use_build_context_synchronously lint is just being overly cautious."** Proven above with the real crash-shaped scenario: the element behind a stale context can be gone by the time the `await` resolves; the lint's own wording explicitly offers the `mounted` guard as the fix, not just a suggestion to silence it.
- **"MediaQuery.of and LayoutBuilder are two ways to do the same thing."** Proven above with real build counters: one is ambient-data-based (rebuilds on any field), the other is actual-constraints-based (rebuilds only when its own box constraints change) — picking the wrong one either over-rebuilds or misses real layout changes.
- **"context.findRenderObject() is safe to call anywhere, since context is always available."** Proven above: `context` being non-null doesn't mean a render object exists yet — `initState` runs before the first layout pass, and the cast crashes for real.

## Reading AI-generated code

AI-generated Flutter code frequently pulls `Scaffold.of(context)`/`Navigator.of(context)`/`ScaffoldMessenger.of(context)` straight from the enclosing `build`'s own context, especially inside a single-file "quick demo" — exactly the pattern proven to crash above — because training data has plenty of correct *usage* of these calls but far less signal about *which* context object is valid at each call site.

```dart
// @expect-error compiles clean — throws the real Scaffold.of() error proven above the first time the button is tapped
class QuickForm extends StatelessWidget {
  const QuickForm({super.key});
  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: ElevatedButton(
        onPressed: () {
          ScaffoldMessenger.of(context).showSnackBar(
            const SnackBar(content: Text('Saved')),
          );
        },
        child: const Text('Save'),
      ),
    );
  }
}
```

Before trusting generated code that calls `X.of(context)`, check:

- Is this `context` genuinely a descendant of the widget being searched for, or does it come from the same `build` method that constructs it? (`ScaffoldMessenger.of` actually walks to the root `Navigator`-adjacent overlay in modern Flutter and is more forgiving than `Scaffold.of` here — but the same class of bug applies to `Scaffold.of`/`Navigator.of` reliably, as proven above.)
- Does any `context` use happen after an `await`? If so, is it guarded by `mounted` (inside a `State`) or captured before the gap?
- Is `MediaQuery.of(context)` used where only one narrow aspect (size, text scale) is actually read? A narrower `MediaQuery.sizeOf`/`LayoutBuilder` may be the more correct, more efficient choice.
