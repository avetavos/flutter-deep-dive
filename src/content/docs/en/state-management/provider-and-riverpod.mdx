## Provider: InheritedWidget with ergonomics

Writing `InheritedWidget` by hand is boilerplate. **Provider** wraps that pattern with a clean API, and pairs it with `ChangeNotifier` — a simple class that holds state and calls `notifyListeners()` when it changes.

```dart
// 1. A model that notifies listeners when it changes.
class CartModel extends ChangeNotifier {
  final List<String> _items = [];
  List<String> get items => List.unmodifiable(_items);

  void add(String item) {
    _items.add(item);
    notifyListeners();   // tell listening widgets to rebuild
  }
}

// 2. Provide it above the widgets that need it.
ChangeNotifierProvider(
  create: (_) => CartModel(),
  child: const MyApp(),
);

// 3. Read it. watch() rebuilds on change; read() does not.
final cart = context.watch<CartModel>();      // rebuilds when cart changes
context.read<CartModel>().add('Book');         // one-off action, no rebuild
```

The `watch` vs `read` distinction is the whole game. `context.watch<T>()` subscribes — the widget rebuilds when the model notifies. `context.read<T>()` grabs it once without subscribing — use it in callbacks (like `onPressed`) where you want to *act*, not *listen*. Mixing them up is the most common Provider bug (either missing rebuilds or rebuilding too much).

## Riverpod: providers without the tree

**Riverpod** is a reimagining by the same author ([rrousselGit](https://github.com/rrousselGit)) that fixes Provider's rough edges. Its key move: providers are **top-level objects, not tied to the widget tree**, which makes them compile-safe (you can't read a provider that isn't there) and easy to test and combine.

```dart
// A provider declared at top level — not in the widget tree.
final counterProvider = NotifierProvider<Counter, int>(Counter.new);

class Counter extends Notifier<int> {
  @override
  int build() => 0;             // the initial state, returned from build()

  void increment() => state++;  // reassigning `state` notifies listeners
}

// In a ConsumerWidget, `ref` reads providers:
class CounterView extends ConsumerWidget {
  const CounterView({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final count = ref.watch(counterProvider);          // rebuilds on change
    return TextButton(
      onPressed: () => ref.read(counterProvider.notifier).increment(),
      child: Text('$count'),
    );
  }
}
```

A `Notifier<T>` returns its initial state from `build()` (not a constructor `super(initial)`), and mutating `state` notifies listeners. Notice the same `watch`/`read` split via `ref`. The difference from Provider is structural: no `BuildContext` lookup, no "provider not found" at runtime — *unless you forget the one piece of tree wiring Riverpod still needs.* That's next.

## `ProviderScope` is not optional — proof

Every example above quietly assumed something: a `ProviderScope` sits above the widget tree. Riverpod's `ref.watch`/`ref.read` still need *somewhere* to store provider state — that somewhere is a `ProviderContainer`, and `ProviderScope` is the widget that creates one and makes it reachable. Skip it, and every `ConsumerWidget` throws the moment it tries to read a provider.

```dart
// lib/no_scope_counter.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

final counterProvider = NotifierProvider<Counter, int>(Counter.new);

class Counter extends Notifier<int> {
  @override
  int build() => 0;

  void increment() => state++;
}

class CounterView extends ConsumerWidget {
  const CounterView({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final count = ref.watch(counterProvider);
    return Text('$count');
  }
}
```

```dart
// test/no_scope_counter_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/no_scope_counter.dart';

void main() {
  testWidgets('a ConsumerWidget with no ProviderScope ancestor throws', (tester) async {
    await tester.pumpWidget(const MaterialApp(home: CounterView()));
    final exception = tester.takeException();
    expect(exception, isA<StateError>());
    expect(exception.toString(), contains('No ProviderScope found'));
  });

  testWidgets('wrapping the same tree in ProviderScope fixes it', (tester) async {
    await tester.pumpWidget(
      const ProviderScope(child: MaterialApp(home: CounterView())),
    );
    expect(tester.takeException(), isNull);
    expect(find.text('0'), findsOneWidget);
  });
}
```

```text

00:00 +2: All tests passed!
```

The real exception, captured verbatim from the probe (`flutter_riverpod` 3.4.3): `StateError` with message **"Bad state: No ProviderScope found"**. The fix is the one line the intro examples skipped:

```dart
void main() {
  runApp(
    const ProviderScope(          // <-- wraps the whole app, once, at the root
      child: MyApp(),
    ),
  );
}
```

<Callout title="Rule of thumb">
If a lesson, tutorial, or AI-generated snippet uses `ConsumerWidget`/`ref.watch` and you don't see a `ProviderScope` anywhere in `main()`, it is incomplete — it will crash the instant it runs, not just log a warning.
</Callout>

## Code generation: `@riverpod`

Hand-writing `NotifierProvider<Counter, int>(Counter.new)` is fine for one provider. For a real app, Riverpod's code generator (`riverpod_generator`, driven by the `@riverpod` annotation from `riverpod_annotation`, via `build_runner`) derives the provider declaration, its generic types, and its `.autoDispose` default for you — you write the logic, it writes the boilerplate.

```yaml
# pubspec.yaml
dependencies:
  riverpod_annotation: ^4.0.7

dev_dependencies:
  riverpod_generator: ^4.0.9
  build_runner: ^2.16.1
```

```dart
// lib/todos_provider.dart
import 'package:riverpod_annotation/riverpod_annotation.dart';

part 'todos_provider.g.dart';

// Function provider — codegen infers `FutureProvider<List<String>>` from the
// Future return type. `Ref` is the one generic ref type (not a bespoke
// generated subtype) as of riverpod_generator 3+.
@riverpod
Future<List<String>> fetchTodos(Ref ref) async {
  await Future<void>.delayed(const Duration(milliseconds: 10));
  return const ['Buy milk', 'Walk the dog'];
}

// Class provider — codegen infers `NotifierProvider<TodoList, List<String>>`.
// `_$TodoList` is generated; you extend it instead of `Notifier<List<String>>`.
@riverpod
class TodoList extends _$TodoList {
  @override
  List<String> build() => const [];

  void add(String todo) => state = [...state, todo];
}
```

## Rebuild control: `.autoDispose`, `.family`, `.select`, `ref.listen`

Four tools that separately answer "when does this provider's state get created/destroyed?" and "when does *this widget* rebuild?":

- **`.family`** — one provider instance per argument (e.g. per user id). Without it, a provider can only ever hold one value.
- **`.autoDispose`** — tears the provider's state down once its last listener unsubscribes, instead of caching it for the app's lifetime. Combine with `.family` for anything scoped to a parameter (a per-item detail screen, a per-user profile) — otherwise you leak one cached instance *per distinct argument ever watched*, forever.
- **`ref.watch(provider.select((s) => s.field))`** — subscribes to only one derived value. The watching widget rebuilds only when that specific value changes, not on every change to the provider's state.
- **`ref.listen(provider, (previous, next) { ... })`** — runs a callback on change (for side effects: showing a `SnackBar`, navigating) **without** subscribing the calling widget to rebuilds.

```dart
// lib/family_and_select.dart
import 'package:flutter_riverpod/flutter_riverpod.dart';

// .family + .autoDispose: one FutureProvider instance PER userId, disposed
// automatically once the last widget watching that userId unmounts.
final userNameProvider =
    FutureProvider.autoDispose.family<String, int>((ref, userId) async {
  await Future<void>.delayed(const Duration(milliseconds: 5));
  return 'user-$userId';
});

// A tiny probe for the disposal test below: records disposal via ref.onDispose.
final disposeProbeProvider = Provider.autoDispose<int>((ref) {
  ref.onDispose(() => disposeProbeLog.add('disposed'));
  return 0;
});
final disposeProbeLog = <String>[];

class Profile {
  const Profile({required this.name, required this.age});
  final String name;
  final int age;
}

final profileProvider = NotifierProvider<ProfileNotifier, Profile>(ProfileNotifier.new);

class ProfileNotifier extends Notifier<Profile> {
  @override
  Profile build() => const Profile(name: 'Ada', age: 30);

  void birthday() => state = Profile(name: state.name, age: state.age + 1);
  void rename(String name) => state = Profile(name: name, age: state.age);
}
```

```dart
// test/family_and_select_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/family_and_select.dart';

int nameBuildCount = 0;

class NameOnly extends ConsumerWidget {
  const NameOnly({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    nameBuildCount++;
    // select() rebuilds this widget ONLY when the selected field changes.
    final name = ref.watch(profileProvider.select((p) => p.name));
    return Text(name);
  }
}

class _FakeProfileNotifier extends ProfileNotifier {
  @override
  Profile build() => const Profile(name: 'Overridden', age: 99);
}

void main() {
  testWidgets('select() skips rebuild when an unrelated field changes', (tester) async {
    nameBuildCount = 0;
    await tester.pumpWidget(
      ProviderScope(child: MaterialApp(home: Scaffold(body: const NameOnly()))),
    );
    expect(nameBuildCount, 1);

    final container = ProviderScope.containerOf(tester.element(find.byType(NameOnly)));

    container.read(profileProvider.notifier).birthday(); // age changes, name does not
    await tester.pump();
    expect(nameBuildCount, 1, reason: 'age is not selected — no rebuild');

    container.read(profileProvider.notifier).rename('Grace'); // name changes
    await tester.pump();
    expect(nameBuildCount, 2, reason: 'name changed — rebuild');
    expect(find.text('Grace'), findsOneWidget);
  });

  testWidgets('ref.listen fires a side effect without causing its own rebuild', (tester) async {
    final events = <int>[];
    int buildCount = 0;

    await tester.pumpWidget(
      ProviderScope(
        child: MaterialApp(
          home: Consumer(
            builder: (context, ref, _) {
              buildCount++;
              ref.listen<Profile>(profileProvider, (previous, next) {
                events.add(next.age);
              });
              return const SizedBox.shrink();
            },
          ),
        ),
      ),
    );
    expect(buildCount, 1);
    expect(events, isEmpty, reason: 'listen does not fire on initial build');

    final container = ProviderScope.containerOf(tester.element(find.byType(Consumer)));
    container.read(profileProvider.notifier).birthday();
    await tester.pump();

    expect(events, [31], reason: 'listener fired once with the new state');
    expect(buildCount, 1, reason: 'ref.listen never rebuilds the widget that registered it');
  });

  testWidgets('ProviderScope(overrides:) replaces a provider for the whole subtree', (tester) async {
    await tester.pumpWidget(
      ProviderScope(
        overrides: [
          // Override with a fake Notifier subclass: initial state comes from
          // build(), never from setting `state` before build() has run.
          profileProvider.overrideWith(_FakeProfileNotifier.new),
        ],
        child: MaterialApp(home: Scaffold(body: const NameOnly())),
      ),
    );
    expect(find.text('Overridden'), findsOneWidget);
  });

  testWidgets('.autoDispose disposes provider state once the last widget watching it unmounts', (tester) async {
    disposeProbeLog.clear();
    final container = ProviderContainer();
    addTearDown(container.dispose);

    await tester.pumpWidget(
      UncontrolledProviderScope(
        container: container,
        child: MaterialApp(
          home: Consumer(
            builder: (context, ref, _) {
              ref.watch(disposeProbeProvider);
              return const SizedBox.shrink();
            },
          ),
        ),
      ),
    );
    expect(disposeProbeLog, isEmpty, reason: 'still mounted — not disposed yet');

    // Unmount the only widget watching it.
    await tester.pumpWidget(
      UncontrolledProviderScope(container: container, child: const SizedBox()),
    );
    await tester.pump();

    expect(disposeProbeLog, ['disposed'], reason: 'autoDispose tore the provider down with no watchers left');
  });
}
```

That third test is also the pattern for **unit/widget-testing anything built on Riverpod**: never let a test touch the real provider (a real network call, a real database) — override it inside `ProviderScope(overrides: [...])` (or `UncontrolledProviderScope(container: ...)` for a container you built and want to inspect directly) with a fake that returns known data.

## Async state: `AsyncNotifier` and `AsyncValue.when`

For state loaded asynchronously, `AsyncNotifier<T>`'s `build()` returns a `Future<T>`, and the provider exposes `AsyncValue<T>` — a union of loading/data/error that `.when()` forces you to handle exhaustively (no forgetting the error case, unlike a raw `try`/`catch` sprinkled through the UI).

```dart
// lib/weather_async_notifier.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';

/// Toggle to force the fake fetch to throw, proving the error branch.
bool weatherShouldFail = false;

final weatherProvider = AsyncNotifierProvider<WeatherNotifier, String>(WeatherNotifier.new);

class WeatherNotifier extends AsyncNotifier<String> {
  @override
  Future<String> build() async {
    await Future<void>.delayed(const Duration(milliseconds: 5));
    if (weatherShouldFail) {
      // Throwing an Error (not Exception) skips Riverpod 3's automatic
      // retry and settles straight into a terminal AsyncError — see below
      // for what happens if you throw a plain Exception instead.
      throw StateError('weather service unavailable');
    }
    return 'Sunny, 22°C';
  }
}

class WeatherView extends ConsumerWidget {
  const WeatherView({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final weather = ref.watch(weatherProvider);
    // AsyncValue.when forces you to handle all three states explicitly.
    return weather.when(
      loading: () => const Text('loading'),
      error: (err, st) => Text('error: $err'),
      data: (value) => Text('data: $value'),
    );
  }
}
```

```dart
// test/weather_async_notifier_test.dart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:my_app/weather_async_notifier.dart';

void main() {
  testWidgets('AsyncNotifier: loading, then data', (tester) async {
    weatherShouldFail = false;
    await tester.pumpWidget(const ProviderScope(child: MaterialApp(home: WeatherView())));
    // First frame: the Future hasn't resolved yet.
    expect(find.text('loading'), findsOneWidget);

    await tester.pump(const Duration(milliseconds: 10));
    expect(find.text('data: Sunny, 22°C'), findsOneWidget);
  });

  testWidgets('AsyncNotifier: loading, then error', (tester) async {
    weatherShouldFail = true;
    addTearDown(() => weatherShouldFail = false);
    await tester.pumpWidget(const ProviderScope(child: MaterialApp(home: WeatherView())));
    expect(find.text('loading'), findsOneWidget);

    await tester.pump(const Duration(milliseconds: 10));
    expect(find.textContaining('error: Bad state: weather service unavailable'), findsOneWidget);
  });
}
```

```text
00:00 +2: All tests passed!
```

### A gotcha the tests above deliberately dodge: `AsyncNotifier` retries by default

The `WeatherNotifier.build()` above throws a `StateError`, not an `Exception`, on purpose. Riverpod 3 gives every provider an automatic retry policy — reading `ProviderContainer.defaultRetry` directly from the installed `riverpod` 3.4.3 source (`lib/src/core/provider_container.dart`):

```dart
static Duration? defaultRetry(
  int retryCount,
  Object error, {
  int maxRetries = 10,
  Duration maxDelay = const Duration(milliseconds: 6400),
  Duration minDelay = const Duration(milliseconds: 200),
}) {
  if (retryCount >= maxRetries) return null;
  if (error is ProviderException || error is Error) return null;

  final delay = minDelay * math.pow(2, retryCount).toInt();
  if (delay > maxDelay) return maxDelay;

  return delay;
}
```

The condition `error is ProviderException || error is Error` is the whole story: throw a Dart `Error` (`StateError`, `ArgumentError`, an assertion) and Riverpod treats it as unrecoverable — immediate terminal `AsyncError`, exactly what the test above proves. Throw a plain `Exception` instead (the more common instinct for "something failed, like a network call"), and Riverpod retries up to 10 times with exponential backoff (200ms, 400ms, 800ms... capped at 6.4s) *before* ever reaching that terminal error — proven directly against a `ProviderContainer` in this probe, listening to `weatherProvider` after changing `throw StateError(...)` to `throw Exception(...)`:

```text
LISTENER: AsyncLoading<String>(error: Exception: weather service unavailable, stackTrace: ..., retrying)
```

Notice the state is still `AsyncLoading` — with an attached `error` and `retrying: true` — not `AsyncError`. `AsyncValue.when()`'s `loading` callback fires, not `error`, for as long as retries are in flight. This is exactly why the `WeatherView` example above stayed on `'loading'` indefinitely the first time this lesson's tests were written against `Exception` — a real trap, not a hypothetical one. If you want a network failure to surface as an error *immediately* in a widget test (rather than after up to ~30+ seconds of retries), either throw an `Error` subtype for genuinely-unrecoverable failures, or pass your own `retry:` callback to `AsyncNotifierProvider`/`@Riverpod(retry: ...)` to opt out.

## `StateNotifier`, `StateProvider`, `ChangeNotifierProvider`: legacy in Riverpod 3

Older Riverpod code (and a lot of tutorials still in circulation) uses APIs that the [official migration guide](https://riverpod.dev/docs/migration/from_state_notifier) now steers you away from:

> "Along with Riverpod 2.0, new classes were introduced: `Notifier` / `AsyncNotifier`. `StateNotifier` is now discouraged in favor of those new APIs."
>
> "Since `StateNotifierProvider` is deprecated, `StateProvider` is to be avoided, too. Furthermore, as of now, there is no `StateProvider` equivalent for the new APIs."

| Old API | Status | Replacement |
| --- | --- | --- |
| `StateNotifier` / `StateNotifierProvider` | discouraged/deprecated | `Notifier` / `NotifierProvider` (or `@riverpod class`) |
| `StateProvider` | to be avoided | `Notifier` holding a primitive, or `@riverpod` function provider |
| `ChangeNotifierProvider` (Riverpod's own, not `package:provider`'s) | transitional only | `AsyncNotifier` / `Notifier` |

Riverpod's own `ChangeNotifierProvider` is a separate thing from `package:provider`'s widget of the same name — the [migration guide](https://riverpod.dev/docs/migration/from_change_notifier) is direct about its purpose: *"Within Riverpod, `ChangeNotifierProvider` is meant to be used to offer a smooth transition from pkg:provider"* — a bridge for porting an existing Provider app, not a pattern to reach for in new Riverpod code.

## Provider vs Riverpod, honestly

<Mermaid title="Provider vs Riverpod at a glance" code={compareDiagram} />

export const compareDiagram = `flowchart TB
  prov["Provider\nInheritedWidget + ChangeNotifier\ntied to the tree, runtime lookup"] --> use1["great for smaller apps,\nteams already using it"]
  rp["Riverpod\ntop-level providers\ncompile-safe, testable, composable"] --> use2["preferred for new apps,\ncomplex or testable state"]`;

Both packages are maintained by the same author (Remi Rousselet, `rrousselGit`) — Riverpod is not a competitor so much as Provider's own sequel, built to remove the two things Provider structurally can't fix without a `BuildContext`: compile-time provider-not-found errors, and providers that don't need a widget tree at all to exist (easy unit testing, providers that depend on other providers). `package:provider` (6.1.5+1 on pub.dev) is **not** officially deprecated — it's simpler, has less to learn, and is still a completely reasonable choice for a small app or a team already fluent in it. What you lose sticking with Provider: no `.autoDispose`/`.family` equivalents, no `ref.listen`/`.select()`-style granular subscriptions, and any "provider not found" mistake is a runtime crash instead of impossible by construction.

| Need | Use |
| --- | --- |
| Small app, team already knows Provider, `InheritedWidget`-shaped state | Provider |
| Compile-safe access, per-parameter caching (`.family`), fine-grained rebuilds (`.select`), first-class async (`AsyncNotifier`) | Riverpod |
| Testing providers without a widget tree at all | Riverpod (`ProviderContainer` directly) |
| Migrating an existing Provider app incrementally | Riverpod's own `ChangeNotifierProvider` as a bridge, then move off it |

## Mental Model

Provider is "give `InheritedWidget` a nicer API" — state still physically lives in the tree, found by walking up from a `BuildContext`. Riverpod is "take state *out* of the tree entirely" — providers are plain top-level declarations, `ProviderScope` just holds the one `ProviderContainer` that stores their live state, and `ref` is your handle into that container, resolved by the *provider object itself*, not by walking widgets. That's why a missing `ProviderScope` fails the same way a missing `MaterialApp` around a `Theme.of(context)` call does — the read has nowhere to resolve against — and why Riverpod providers can depend on each other (`ref.watch(otherProvider)` inside a provider) with no widget involved at all.

## Trade-offs

| Choice | Benefit | Cost |
| --- | --- | --- |
| Provider (`ChangeNotifierProvider` + `context.watch`) | Small API surface, no codegen, ubiquitous | Runtime "provider not found", coarser rebuild control, `BuildContext`-bound |
| Riverpod, hand-written providers | No codegen step, still compile-safe | You write `NotifierProvider<X, Y>(X.new)` boilerplate yourself |
| Riverpod + `@riverpod` codegen | Least boilerplate, inferred types, `.autoDispose` by default | `build_runner` in the loop; generated code is real code your analyzer checks |
| `.family` + `.autoDispose` | No per-parameter memory leak | Must remember to pair them — `.family` alone never disposes |
| `AsyncNotifier` + `.when()` | Exhaustive loading/data/error handling, no forgotten catch | Default retry-on-`Exception` can hide a failure behind "loading" far longer than expected |

## Common Misconceptions

- **"Riverpod doesn't need any widget at all."** It needs exactly one: `ProviderScope` at the root, to own the `ProviderContainer`. Proven above — remove it and every `ConsumerWidget` throws `Bad state: No ProviderScope found`.
- **"`.family` alone is enough to avoid memory growth."** `.family` creates state **per argument**; without `.autoDispose` it caches every distinct argument's state forever, for the app's whole lifetime.
- **".g.dart files are safe to hand-edit for a quick fix."** They're regenerated wholesale on the next `build_runner build`, silently discarding any manual edit — fix the annotated source, not the generated file.
- **"An `AsyncValue` in `error` state means the request definitely failed."** Only for a genuinely terminal `AsyncError`. A `Exception`-thrown failure can sit in `AsyncLoading(error: ..., retrying: true)` for several retries first — proven above from `ProviderContainer.defaultRetry`'s own source.
- **"`ref.watch` and `ref.listen` do the same thing."** `watch` subscribes *and* rebuilds the calling widget. `listen` runs a callback for side effects and never rebuilds the widget that registered it — proven above (`buildCount` stayed `1` through a state change).

## Reading AI-generated code

A generator (or an AI assistant) writing `@riverpod` code makes a specific, very common mistake: writing the annotated class or function correctly, but forgetting the file only compiles once codegen has run — a normal state mid-edit, but a real bug if shipped or copy-pasted into a lesson without the `part` directive.

```dart
// @expect-error missing `part` directive — extends_non_class + undefined_identifier, proven below
import 'package:riverpod_annotation/riverpod_annotation.dart';

@riverpod
class Counter extends _$Counter {
  @override
  int build() => 0;

  void increment() => state++;
}
```

Missing `part 'counter.g.dart';` — the real `flutter analyze` output from this exact snippet, run standalone in the probe:

```text
error • Classes can only extend other classes. Try specifying a different superclass, or removing the extends clause • extends_non_class
warning • The method doesn't override an inherited method • override_on_non_overriding_member
error • Undefined name 'state' • undefined_identifier
```

`_$Counter` doesn't exist without the `part` directive pulling in the generated file that defines it — so the analyzer sees `extends _$Counter` as extending an undefined name, and `state` (which `_$Counter`/`Notifier` would normally provide) as undefined too. Before trusting any AI-generated `@riverpod` snippet, check for:

- A `part '<filename>.g.dart';` line matching the file's own name, immediately after the imports.
- That the corresponding `.g.dart` actually exists (or a note that `build_runner` still needs to run) — a snippet with the `part` line but no generated file is just as broken until you run it.
- `.autoDispose`/`@Riverpod(keepAlive: true)` intent matching the provider's real lifetime — codegen defaults to `.autoDispose`, which surprises anyone expecting Riverpod 1/2's non-generated default (which was **not** autoDispose).
- A caught `Exception` where an `Error` was meant (or vice versa) inside an `AsyncNotifier.build()` — changes whether Riverpod retries silently or fails immediately, proven above.

<SpotTheBug code={`// AI-generated: "add ProviderScope overrides for testing"
Widget buildTestApp() {
  return ProviderScope(
    overrides: [
      profileProvider.overrideWith(
        () => ProfileNotifier()..state = const Profile(name: 'Test', age: 1),
      ),
    ],
    child: const MaterialApp(home: NameOnly()),
  );
}`}>
This compiles, but throws at runtime: `ProfileNotifier()..state = ...` sets `state` in the cascade **before** Riverpod has called `build()` on the fresh notifier — the exact "uninitialized state" trap proven in the probe (`Bad state: Tried to use a notifier in an uninitialized state`, with the fix suggestion "move your logic inside the `build` method instead"). The correct override is a Notifier **subclass** whose `build()` returns the desired state: `profileProvider.overrideWith(() => _FakeProfileNotifier())` where `_FakeProfileNotifier extends ProfileNotifier { @override Profile build() => const Profile(name: 'Test', age: 1); }` — exactly the pattern the `ProviderScope(overrides:)` test above uses.
</SpotTheBug>

<Callout title="The one-line takeaway">
**Provider** makes `InheritedWidget` + `ChangeNotifier` ergonomic — the core skill is `context.watch<T>()` vs `context.read<T>()`. **Riverpod** moves providers out of the widget tree entirely, but still needs exactly one widget, `ProviderScope`, at the root — skip it and every `ConsumerWidget` throws `Bad state: No ProviderScope found`, proven above. Prefer `@riverpod` codegen over hand-written providers (it defaults to `.autoDispose` and infers types), pair `.family` with `.autoDispose` to avoid per-parameter leaks, use `.select()`/`ref.listen` to control rebuilds precisely, and remember `AsyncNotifier` retries a thrown `Exception` up to 10 times before settling into a terminal `AsyncError` — throw an `Error` for anything that should fail immediately. `StateNotifier`/`StateProvider` are legacy per Riverpod's own migration guide; `Notifier`/`AsyncNotifier` (or their `@riverpod` codegen forms) are the current default.
</Callout>
