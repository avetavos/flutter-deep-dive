## What this module is for

Every earlier module in this course taught you to *use* Flutter: build widgets, manage state, navigate, lay out screens, ship a build. None of it required knowing what `setState` actually does underneath, what a "relayout boundary" is, why Impeller's PSOs are "precompiled," or what `gen_snapshot` actually produces. That gap is exactly where a confident-sounding explanation of Flutter (human- or AI-written) goes wrong in ways `flutter analyze` alone won't catch -- a plausible-sounding claim about "the UI and raster threads merging" or "each isolate having its own totally separate heap" reads as authoritative right up until you check the actual source or run the actual command.

This module answers five internals questions, each proven against the real, installed Flutter 3.47.5 / Dart 3.13.4 source (revision `6a19cca564`) or a real command run on this Mac, never asserted from memory:

1. **What actually happens between a widget rebuilding and a pixel changing?** ([The Three Trees, From the Source](/flutter/en/flutter-internals/three-trees/) -- `Widget.canUpdate`, `Element.updateChild`'s real four-case table, a custom `RenderObjectWidget` proving `createRenderObject`/`updateRenderObject`/`performLayout`/`paint` are four separately-triggerable hooks, and `GlobalKey` reparenting proven with `identical()`)
2. **What turns "a widget called `setState`" into "a frame actually runs," and in what order?** ([Build Scheduling and Frames](/flutter/en/flutter-internals/build-scheduling-and-frames/) -- the real `SchedulerPhase` enum, `WidgetsBinding.drawFrame`'s own 8-step doc comment, and a real test proving two synchronous `setState` calls coalesce into exactly one build)
3. **Where, precisely, does a chain of `markNeedsLayout` calls stop climbing the tree?** ([Layout and Paint Internals](/flutter/en/flutter-internals/layout-and-paint-internals/) -- the exact relayout-boundary rule quoted from source, proven with a custom `RenderBox` pair and a real `debugDumpRenderTree` showing the boundary annotation appear and disappear)
4. **What does Impeller actually replace, and is "UI+raster merged" even true?** ([Impeller and the GPU](/flutter/en/flutter-internals/impeller-and-the-gpu/) -- the engine's own README and `Entity`/`Contents`/`RenderPass` source, and a real correction: the documented 3.29+ thread merge is UI+**platform**, not UI+raster)
5. **What does `flutter build` actually run, and what does a Dart isolate's memory model really look like?** ([The Dart VM and Isolates](/flutter/en/flutter-internals/dart-vm-and-isolates/) -- real, verbose `flutter build apk`/`flutter build web` output, a real ELF `libapp.so` extracted and inspected with `file(1)`, and a live, grepped proof that a `kDebugMode` branch is deleted from a release build)

<Callout title="The one-line takeaway">
Every one of these five mechanisms is provable from the outside with tools you already have -- the installed `~/flutter` source itself, `flutter test`, `debugDumpRenderTree`/`debugDumpApp`, and `flutter build -v` -- not something you have to trust from a diagram or a confident-sounding paragraph. This module's job is to show you those tools pointed at the real, pinned Flutter 3.47.5 / Dart 3.13.4 installed for this course, so that when you read someone else's (or an AI's) claim about "what Flutter does under the hood," you know exactly which command or source file would prove or disprove it.
</Callout>

## Mental Model

Every lesson in this module is the same idea applied to a different layer: **Flutter's internals are not a black box -- they are a fixed set of source files and real, runnable commands that will always show you the actual mechanism directly.** "Rebuilding is expensive" is not a slogan; it's `Widget.canUpdate`'s exact two-field test, provable with a spy. "A relayout boundary stops the climb" is not a metaphor; it's one literal line, `_isRelayoutBoundary = !parentUsesSize || sizedByParent || constraints.isTight || parent == null`, provable with a counter and a real `debugDumpRenderTree`. "Impeller removed shader jank" is not marketing; it's `ContentContextOptions`' own doc comment bounding PSO variants at "hundreds, not 10,000s." Once you know which source file or which command proves which claim, "trust me, that's how Flutter works under the hood" stops being necessary -- for your own claims, and for judging an AI's.

## Common Misconceptions

- **"A widget rebuilding always means a new `RenderObject`."** [The Three Trees](/flutter/en/flutter-internals/three-trees/) proves the opposite with a real counter: `createRenderObject` runs once; same-key rebuilds only ever pay for `updateRenderObject`.
- **"Calling `setState` twice always triggers two rebuilds."** [Build Scheduling and Frames](/flutter/en/flutter-internals/build-scheduling-and-frames/) proves `Element.markNeedsBuild`'s own `if (dirty) return;` guard coalesces two synchronous calls into exactly one.
- **"Marking a widget as needing layout always relays out everything above it."** [Layout and Paint Internals](/flutter/en/flutter-internals/layout-and-paint-internals/) proves a relayout boundary genuinely absorbs the dirty flag -- a real `debugDumpRenderTree` confirms it from a second, independent angle.
- **"Impeller merged the UI thread and the raster thread."** [Impeller and the GPU](/flutter/en/flutter-internals/impeller-and-the-gpu/) proves, with real `docs.flutter.dev` quotes, that the actual 3.29+ merge is UI+platform on iOS/Android -- the raster thread, where Impeller/Skia actually talk to the GPU, was never merged with the UI thread.
- **"Each Dart isolate has its own completely separate heap."** [The Dart VM and Isolates](/flutter/en/flutter-internals/dart-vm-and-isolates/) proves, from `dart-lang/sdk`'s own glossary, that isolates in the same group share a heap -- and then proves, fresh, that `compute()`'s message passing still copies rather than aliases regardless.

<SpotTheBug code={`// A comment an AI assistant added above a custom RenderBox
// "sizedByParent means the framework never needs to re-check this
// widget's layout when its internal state changes -- just call
// markNeedsLayout() like any other render object."
class _RenderFixedHeightBox extends RenderBox {
  @override
  bool get sizedByParent => true;

  double _height = 40;
  set targetHeight(double v) {
    _height = v;
    markNeedsLayout();
  }

  @override
  Size computeDryLayout(BoxConstraints constraints) =>
      constraints.constrain(Size(constraints.maxWidth, _height));
}`}>
Proven wrong in [Layout and Paint Internals](/flutter/en/flutter-internals/layout-and-paint-internals/), with a real, run test: a `sizedByParent: true` object is unconditionally its own relayout boundary (proven from the exact source rule that lesson quotes), which means plain `markNeedsLayout()` never notifies the parent when this object's *own size* changes -- the parent silently keeps a stale size. `sizedByParent`'s own doc comment requires `markNeedsLayoutForSizedByParentChange()` instead for exactly this case, and that lesson's test proves the difference directly: with the plain call, the parent's observed child width stayed stuck at the old value; with the correct call, it updated.
